# mobile_android — file inventory

What every file under `lib/` is for. Split out of this app's `CLAUDE.md`, which
is loaded in full whenever a session touches a file in this app: the inventory
had reached 153 KB, roughly 38,000 tokens, to answer a question a session only
asks about the handful of files it is about to open.

`CLAUDE.md` keeps the scope rules, the stack, the i18n contract, the analyzer
policy and the gotchas. This file is the reference behind them — grep it for a
screen or a store before adding one, so you extend the existing file rather than
minting a second one beside it.

Paths are relative to `apps/mobile_android/`. Per
[decisions.md § 39](../../docs/architecture/decisions.md), `lib/` and `test/`
are byte-identical to `apps/mobile_ios/`, so every entry describes both apps.

- `setup_wizard_screen.dart` — post-signup account-setup wizard, mobile twin of web's 7-step `/onboarding`. Gated on `user_profiles.onboarded_at`: `home_screen.dart` fetches the profile after the first frame and pushes this once when the column is null, then `Finish` / header-`Skip setup` stamps it via `ApiClient.completeOnboarding` / `markOnboarded`. Collects display name → units → primary goal (`primary_goal` bag) → demographics (gender + DOB + weight) under the Art 9 health-consent gate (mirrors `settings_body_metrics_screen` — gender + consent stamp only under the checkbox; DOB written unconditionally for the minor-exclusion floor) → privacy default → notifications (`push_notifications` bag) → done. Pure contract in `onboarding.dart` (TS↔Dart pair with web `onboarding.ts`). **Distinct from `onboarding_screen.dart`** (first-launch permission flow). 10 unit/widget tests (`onboarding_test.dart` + `setup_wizard_screen_test.dart`).
- `sign_in_screen.dart` — email/password + Google sign-in
- `sign_up_screen.dart` — email/password registration + Google sign-in, linked from sign-in. Asks for the password **twice** (`auth_gates.dart#checkPasswordPair`, checked before `signUp` — a typo in a single field is silently baked into the account and locks its owner out permanently); the GDPR Art 8 age + ToS gates are inline here as `_checkGates`
- `home_screen.dart` — the multi-modal nav shell (G5, Fitness-hub redesign): a `BottomAppBar` (Home / Fitness / Social / You) + a docked centre Log FAB, over a `PageView` whose pages are `[Home(0), Fitness(1=FitnessHubScreen), Run(2=_pageRun), Gym(3=_pageGym), Nutrition(4=_pageFood), Social(5), You(6=_pageYou=YouScreen)]`. Run / Gym / Nutrition have no nav destination but stay keep-alive dwell-in capture pages reached via the Log action so a session survives. Log FAB: tap → `showLogSpeedDial` fans the capture options above the button and navigates to the picked modality's page (or one-tap run start when `keepRunPrimary`), long-press → repeat last (or the speed-dial). At expanded widths (≥840dp, `widthClassOf`) the same destinations + Log action render as a `NavigationRail` (Log in the leading slot, speed-dial fanning from the button's anchor) instead of the BottomAppBar + docked FAB — chrome swap only, same pages (decisions §256). Hosts the dashboard on page 0. **Swipe-lock during recording (#490):** the `PageView` physics flips to `NeverScrollableScrollPhysics` while a run is actively recording, driven by the process-global `runRecordingActive` `ValueNotifier<bool>` that `run_screen.dart` sets from its `_state` (recording — which includes a mid-session pause — locks; idle/countdown/finished swipeable). Only the swipe drag is blocked; nav-bar/rail taps still navigate (they `jumpToPage` directly). Fail-open: the notifier defaults false and resets false on `RunScreen.dispose`.
- `fitness_hub_screen.dart` — the Fitness modality hub (G5): a `TabController(length: 4)` + top `AppTabBar` strip (History / Runs / Gym / Nutrition) over a `TabBarView`. History = `RunsScreen` WITH gym+food stores + `showKindChips: false` (the absorbed History timeline); Runs = `RunsScreen` WITHOUT a gym store + `surfacePeers` + `showSyncActions: false` + `titleText: "Runs"` (the dedicated run list, statically titled like its Gym/Nutrition siblings — the range + count status renders in the filter header instead; the cloud sync/refresh slot lives only on the History tab — side-by-side duplication overflowed the Runs AppBar title); Gym = `GymScreen`; Nutrition = `NutritionScreen`. Each sub-tab body owns its own Scaffold/AppBar/composer; the hub provides only the tab-strip chrome (mirrors `social_screen.dart`). Both take ui_kit's `AppTabBar`, which derives `isScrollable` from whether the labels fit — the two hubs used to disagree on it and on `TabAlignment`, so the strip jumped 26dp taller and slid 52dp right when you switched destinations (#666 C6). FitnessHubScreen takes a required `TrainingService` (`training`, threaded from `home_screen`) so it can build `PlansScreen`, and owns a `RaceService` for the Races peer (`RacesScreen` is reachable with no provider key and while signed out — the search is a public RPC; the MapTiler key for "near a place" is read defensively from dotenv). "Start with this route" lands on the keep-alive recorder page through the global `pendingStartRunWithRoute` notifier, which every route surface sets directly — there is no `onStartRun` callback threaded down the push path. DISTINCT from the keep-alive capture pages.

Reachable from the Routes tab on `club_detail_screen`
- `live_spectator_screen.dart` — read-only mirror of web `/live/[run_id]`. On hydrate it reads the run's terminal state via `fetchPublicRunById` (mirror of web's `runIsFinished` + the `is_dnf` column, migration `20261207_001`): a **DNF** (race-marked) or **Finished** (`runIsFinished` — saved duration ends >2 min ago) run freezes on its saved totals and never opens the realtime subscription. Otherwise it hydrates existing `live_run_pings`, subscribes via `Supabase.channel.onPostgresChanges(insert)` filtered by `run_id`, and renders the trace on `LiveRunMap` (follow-runner). The status badge has five distinct states — **DNF** (danger) / **Finished** (neutral, terminal) / **Delayed** (amber — a *live* runner whose last ping went stale, NOT terminal) / **Live** (green) / Idle / Connecting; the terminal verdict outranks the live/stale freshness axis. Since issue #613 it also reads `concluded_at` from `public_runs` as the positive finish marker (winning over the duration inference on load, and a ~15 s poll flips a mid-watch run when the marker appears); a concluded run renders a **conclusion card** ("Run complete" + a view-the-full-run CTA → `PublicRunScreen`), and while live the page adds a recent-pace tile + a course-progress bar (when the run follows a known route). `runIsFinished` is `@visibleForTesting`

- `runs_screen.dart` — dual-purpose: the Fitness hub's **All** sub-tab AND (mounted without a `gymStore`) the dedicated **run-list** screen (the hub's **Runs** sub-tab + the "View all" / period drill-ins). **History-tab / timeline mode** (gym+food stores wired): renders the day-grouped cross-modality timeline (`widgets/activity_timeline_list.dart`). The `surfacePeers` list (set by the hub's Runs tab) renders the labelled `Runs · Routes · Plans · Races` strip above the body — planning tools are named destinations, not tooltip-only AppBar glyphs (decisions §488). Shows All/Runs/Lifts/Meals kind chips once a second modality has data and — mirroring web — **every chip (including Runs) renders the day-grouped cross-modality timeline** (`widgets/activity_timeline_list.dart`). The timeline is assembled from the **local stores** by `lib/local_activities.dart` (`buildLocalActivities` over `LocalRunStore` + `LocalGymStore` + `LocalFoodStore`) — offline-first, always all modalities, rebuilt on any store change (so a lift/meal logged from the Log FAB shows at once). Run rows open run-detail (local lookup, else `fetchRunById`), lift rows open `GymDetailScreen`, meals are read-only. The **add FAB is per-chip** (mirroring web's `/history` Log action): on the cross-modal **All** chip it opens the run/lift/meal `showLogSheet` picker → that modality's one-shot composer; a single-modality chip adds straight in (Add run → `AddRunScreen`, Log lift → `showGymComposeSheet`, Log food → `showNutritionLogSheet`); a lift/meal save kicks a best-effort store sync. **Run-list mode** (no `gymStore`, or a pure runner with no lift/meal): the full run list with sorting / source / date-range filters, bulk-delete, pagination, FAB → `add_run_screen`. The inline run list is NOT an offline fallback (the timeline is local-first and renders offline) — it's just what a single-modality (run-only) user sees. - `routes_heatmap_screen.dart` — route-discovery browser; mobile mirror of web `/routes/heatmap` (decisions §§ 99–102, layout § 112). Heat-density background + clustered discoverable pins (pure-Dart `heatmap_clustering.dart`), a Filters bottom sheet (lens `popular`/`friends`/`featured`/`hidden_gems` + multi-select race-distance bands via `distance_bands.dart`). - `run_heatmap_screen.dart` — personal run-track heatmap; mobile mirror of web `/runs/heatmap`. A Strava-style "everywhere you've run" map of the user's OWN tracks (distinct from `routes_heatmap_screen.dart`, the public route-discovery heatmap). Sources tracks from the **union of the local store and the server**: `LocalRunStore.runs` carry their track inline, so they need no download and no session (signed-out recording is a supported flow — reading only the server told a signed-out runner with local tracks "No mapped runs yet", issue #239); the server leg then downloads only the runs that aren't already local, via the owner-only `fetchTrackByPath` (newest-first `getRuns`, `_maxTracks` cap + bounded concurrency), and is skipped entirely when signed out. Aggregates the union with the pure `run_heatmap.dart`, and renders heat cells as low-opacity `CircleLayer` dots that crossfade into the actual track `PolylineLayer` as you zoom past street level (flutter_map has no GPU heatmap layer). Owner-only path → no privacy-zone clip. Signed out with nothing local, the empty state offers sign-in rather than claiming the runner has never run. Reached from the labelled "Run heatmap" button in the Routes screen's Discover strip (`routes_screen.dart`) — every map/discovery entry point is consolidated there; icon-only AppBar entries proved undiscoverable (field reports for both heatmaps).
- `route_detail_screen.dart` — route map + metadata + reviews + public/private toggle + star-for-watch toggle (owner-only). The toolbar is built by `widgets/app_bar_actions.dart` and holds three slots: the share menu (pinned), one promoted action (bookmark for a non-owner, offline pin for an owner), and an overflow carrying the rest — star, visibility, transfer-to-club and delete for an owner; offline pin and report for a non-owner. Six concurrent owner actions measured 0dp of title on a 360dp phone. Share menu offers **Share link** (the intuitive send-to-a-follower path — flips the route public if the owner hasn't, then hands the `/share/route/[id]` URL to the OS share sheet via `routeShareUrl` + `shareTextFrom`; gated to public/owner so no dead link) alongside the image / GPX / GPX+markers / KML file exports and — behind the loopback-backend dev rail the Sim Watch link uses (`devBackendUrl`, decisions §209) — a **Send to watch** entry that pushes the route to the custom watch as a `CRS1` breadcrumb course (`courseFromWaypoints` + `encodeCourse` + `chunkCourse` over `WatchSyncClient.pushCourse`, decisions §370) **and, when the route carries course markers, the `RBK1` race schedule those markers imply** (`buildRoadbook` → `watchRoadbookFromRoadbook` → `encodeRoadbook` + `chunkRoadbook` over `WatchSyncClient.pushRoadbook`, decisions §413). The two ride one action because every checkpoint is a distance *along the course* — a schedule alone would arm Roadbook / CutoffEta / Fuel pages that can never resolve a position. That push reads `_displayWaypoints` (privacy-clipped for non-owners, §33) like the GPX exporter does, thins an over-long route to the 256-point frame budget rather than cutting it, and refuses what it cannot represent with a banner — never a partial course. The schedule half is held to the same bar: an over-cap one is reduced deliberately (cut-offs never dropped, farthest-point fill), a route with more cut-offs than the frame holds is refused with the count and the cap, a clock-only cut-off that could not resolve is **counted and reported** rather than silently missing, and a marker-fetch failure degrades to a course-only push (the course already landed). The goal time is `kRoadbookDefaultSecPerKm` from `roadbook_screen.dart` — the crew sheet's own opening default, shared so the arrivals on the wrist and on the sheet cannot drift. The **Start run** FAB hands off through the global `pendingStartRunWithRoute` notifier (decisions §298) rather than popping the route back to the caller — so it works from any pusher (incl. the shared-file import landing).
- `route_builder_screen.dart` — full-screen in-app route builder (Phase 3, web-parity). Tap-to-place waypoints with OSRM road / trail / straight modes; long-press a pin → tap-to-move drag-reshape; snap-to-start (pulsing halo on the start pin when 3+ waypoints) closes the loop with a tap near the start; MapTiler place search in the AppBar; "Locate me" FAB; live elevation gain via Open-Meteo; purple over-stroke on out-and-back retraced sections (`route_overlap.dart`); undo / clear / save (name + public toggle) → `ApiClient.saveRoute` + `LocalRouteStore.save`. Reached from the second "Build" FAB on `routes_screen`. Pure helpers live in `routing.dart`, `elevation.dart`, `geocoding.dart`, `route_overlap.dart`, `widgets/snap_to_start.dart`. **OSRM degrade (`routing.dart#isOsrmSnapAvailable`):** on a release build with no `OSRM_URL`, the prod privacy guard refuses the public demo — so Trail/Road placement would `throw` out of `snapToRoad` and silently drop the tap ("route builder won't let me tap waypoints"). The screen checks `_snapAvailable` up front and, when snapping is unavailable, treats Trail/Road as straight-line placement (`_effectiveStraight`) so a tap always drops a pin, disclosing it once via `routeBuilderSnapUnavailable`. Set `MOBILE_OSRM_URL` (deployment.md) to make snapping actually work.
- `period_summary_screen.dart` — browsable weekly/monthly/all-time summary with stats, run list, and share (text or screenshot). The dashboard's Week / Month / All-time stat cards and a tap on any "Last 20 Weeks" heatmap column open it (`PeriodType.all` = lifetime, nav arrows disabled). Mirrors web's `PeriodSummary`.
- `recap_screen.dart` — the "Wrapped" recap, reached from the dashboard toolbar. **One screen covers both web routes** (`/recap/[year]` + `/recap/[year]/[month]`): a `RecapPeriod` Year / Month `SegmentedButton` picks which engine builds the card (`buildYearInRunningRecap` / `buildMonthInRunningRecap` from `recap.dart`, the TS↔Dart parity pair) and the chevrons under it step by year or by calendar month — `DateTime(_year, _month ± 1)` normalises the year rollover, and the next chevron disables on the current period so the card can never show a window that hasn't happened. Distinct from `period_summary_screen.dart`, which is a plain per-period stats + run-list drill-in.

- `settings_screen.dart` — Settings landing. Mirrors the web `/settings` left-nav shape (`apps/web/src/routes/settings/+layout.svelte`) with three sections — **Profile** (Account, Preferences, Safety, Coaching, Guided runs), **Apps & data** (Integrations, Signed-in devices, Gear), **Account & legal** (Pro & support, About & updates) — each tile drilling into a dedicated sub-screen. - `settings_account_screen.dart` — email + sign-in/out, Profile photo (avatar upload/remove via `ApiClient.uploadAvatar`/`removeAvatar` → public `avatars` bucket, EXIF-stripped client-side; mirrors web `/settings/account`), Display name, Sentry opt-out, the AI-disclosure consent pair (a review/accept tile whenever the versioned record is not current — missing **or** stale — plus the withdraw tile whenever anything is on record; both over `ai_disclosure.dart` + the shared `widgets/ai_disclosure_notice.dart`, decisions § 573), Import / **Account export** / Full backup / CSV export / Restore-from-backup, Change email, Change password, Delete account — fourteen rows. The two archive rows are deliberately separate ([decisions § 724](../../docs/architecture/decisions.md)): **Account export** enqueues the server's Art 20 build (`POST /v1/export/jobs`), watches it with the shared backoff, and resumes from `GET /v1/export/jobs/latest` on mount — so an app the OS killed mid-build finds it waiting, with nothing persisted on the device — while **Full backup** is the on-device writer that carries runs / routes / profile / prefs / gym / food but NOT the account-record set, and says so in a persistent notice once it has produced one. `BackupService` no longer reaches for the server at all: its old silent fall-back turned a refused Art 20 request into a narrower file nobody was told was narrower. Guided runs and Privacy zones moved out (issue #666 I7 / I11) and so did a third "View profile" link to the viewer's own `ProfileScreen`, which the You tab already carries directly above this screen's host (I12); the two that remain — the You tile and the dashboard toolbar — now say "Your profile" in both places.

- `local_run_store.dart` / `local_route_store.dart` — `ChangeNotifier`-style on-disk stores. **`LocalRunStore` is windowed** (decisions § 135): cold-load reads a compact `index.json` (one `RunSummary` per run — scalars only, no track) into the full in-memory `summaries`, and hydrates only a **resident window** of full `Run`s into `_runs` — newest `kResidentWindow` (200) by date **∪ all unsynced** (the residency invariant the sync drain relies on). Read the right seam: `summaries` / `summaryRuns` (full history, track-less) for all-time stats / filters; `runs` (the resident window) + `runById(id)` (resident → on-disk hydrate) for display / detail-nav; `recentWindow(N)` for the timeline feed; `hasRun(id)` for a whole-history existence check (`contains` only sees the window). The index is a batched, atomic, crash-safe **cache** of the per-run files (never the source of truth) — a missing / drifted index self-heals via the full parallel walk on cold-load. **Don't reintroduce a full-history read of `runs`** — it's the window now; reach for `summaries`/`summaryRuns`. `residentWindow` is `@visibleForTesting`-injectable. **Every sidecar of both stores is a merge-under-lock, never a whole-file replace** (decisions § 303 + § 309) — `background_sync.dart` runs a second instance of each over the same directory, so a snapshot write silently discards the other isolate's work. `index.json` merges per id on `last_modified_at`; the run sidecars decide a known id from memory; the three route sidecars let additions win and carry removals in an explicit cleared-ledger, because for routes the losing direction is a cross-account transfer. Any local mutation that makes a run unsynced must also write `synced_ids.json` — the index's flag does not survive cold load (§ 308).

- `offline_sync_store.dart` — the disk-backed per-row sync-state machine the gear / gym / food / routine / meal-template / recipe / crossings / session stores extend. **A screen that constructs one of these must call `init()` on it, never a bare `loadAll()`** — `loadAll` tolerates a null `dir` and returns, so the store reads as alive while every write refuses; `nutrition_screen.dart` shipped in that state and its saved meals + recipes never reached disk or the server. Every write path (`persist` / `dropRow`) goes through `requireInitialised` and raises a named `StateError` **before** touching `rowsById`, so an undurable write leaves no row behind for the UI to present as saved. The rule is enforced source-level by the `a screen-owned OfflineSyncStore is init()ed` group in `architecture_guards_test.dart`. **Every directory-mutating entry point (`persist` / `dropRow` / `rewriteAll` / `restoreFromBackup` / `clear` / `loadAll`) runs on one serial write chain keyed on the DIRECTORY, not the instance** — a new one must go on it too. An atomic write is atomic against itself only: unserialised, sign-out's `clear()` deleted the `.tmp` of an in-flight `persist` (a `PathNotFoundException` naming a temp path the caller never saw) and a delete overtaken by a write to the same id left the row's file back on disk with `rowsById` saying it was gone, resurrecting it at the next cold load. Instance-keying would not have covered the first: `offline_store_wipe.dart` wipes from a throwaway instance precisely because all instances of a type share one directory ([decisions § 821](../../docs/architecture/decisions.md)). **In a widget test, the in-memory row lands a frame before the file does** — `persist` installs it synchronously — so waiting on a UI signal and then deleting the temp directory tears the `.tmp` out mid-rename; wait on the file, or on `debugWritesSettled`. **It also owns the family's two timestamp readers** — `parseServerTimestamp` (a `timestamptz` column off a row map, normalised to UTC) and `storedClockOrEpoch` (the record's own clock off disk or a backup archive, falling back to the EPOCH so an unknown clock loses every newer-wins comparison rather than freezing the row against the server, [decisions § 1342](../../docs/architecture/decisions.md)) — beside `outsideFetchWindow`. The read used to exist nineteen times in five spellings across the family, and `store_timestamp_reader_guard_test.dart` now derives the family from `extends OfflineSyncStore<` and refuses any other `DateTime.parse` / `tryParse` in it unless the site states a `zone-verbatim:` reason. There is no standing exemption any more: gear's private `_parseDate` is now the shared `parseCalendarDate`, the second named reader in the same file, and the guard additionally pins that `offline_sync_store.dart` holds exactly ONE `DateTime.tryParse` — inside `parseIsoStrict`, which range-checks every component because `tryParse` ROLLS an impossible date over rather than refusing it (`2026-06-32` is the 2nd of July, and `gear.purchased_at` goes straight back to a `date` column). The two readers differ only in the `.toUtc()`, which `parseCalendarDate` must NOT have: normalising local midnight moves the calendar day itself for a device AHEAD of UTC ([decisions § 1289](../../docs/architecture/decisions.md) + [§ 1344](../../docs/architecture/decisions.md), which corrects § 1289's hemisphere).
