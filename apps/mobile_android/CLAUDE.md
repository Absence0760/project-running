# mobile_android — AI session notes

The most mature Flutter target in the monorepo. Almost every "Android" checkbox in [../../docs/product/roadmap.md](../../docs/product/roadmap.md) Phase 1 is ticked. Treat this app as the reference implementation — when in doubt about what a feature *should* look like on mobile, look here first.

## Scope — read before writing code

**Web is the canonical feature surface. This app mirrors web and adds device-only capabilities.** See [../../docs/architecture/decisions.md § 24](../../docs/architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive) and the live matrix at [../../docs/product/parity.md](../../docs/product/parity.md).

**One-Dart-codebase rule.** `apps/mobile_android/lib/` and `apps/mobile_ios/lib/` are kept byte-for-byte identical, plus `apps/mobile_android/test/` and `apps/mobile_ios/test/`. Every change you make under `lib/` or `test/` must be applied to the iOS twin in the same commit. Platform-specific runtime behaviour goes inside the unified files via `Platform.isAndroid` / `Platform.isIOS`. The pubspec deltas between the two apps are limited to `name` and `description` — every dependency, version, and asset stays in lockstep. Verify with `diff -rq apps/mobile_android/lib apps/mobile_ios/lib` (should be empty).

**Build here:**

- **Device-led features** (the physical-exception list in §24): live GPS recording + foreground service, auto-pause, on-device crash recovery, BLE chest-strap HR, pedometer / cadence, haptic / TTS pace alerts, OS share sheets, OS share-target intents (GPX / KML import), Health Connect import, disk-backed tile cache, background sync via WorkManager.
- **Mirroring** of an already-shipped web feature into a Flutter screen + api_client method + (when needed) a domain model in `core_models`. Driven by `parity.md` rows where web is `✓` and android is `✗` / `Partial`.

**Don't build here first:**

- A user-facing feature that doesn't yet exist on web — build it on web first, mirror after. This applies even when the request lands on an Android session ("can you add X to Android?"); push back, ship X on web, then mirror. The exception is the device-led list above.
- New abstractions / DI frameworks. `StatefulWidget + setState + ChangeNotifier` is the entire UI stack. No Provider, no Riverpod, no Bloc. If a screen needs cross-cutting state, add a `ChangeNotifier` and wire `addListener` / `removeListener` in `initState` / `dispose`.
- Direct `Supabase.instance.client.from(...)` calls in screens. Route through `packages/api_client` so the typed client stays the single Supabase entry point. (Realtime channels are the documented exception.)
- Comments, decision docs, READMEs, or "removed X" markers under `lib/`. Conventions in [../../docs/architecture/conventions.md](../../docs/architecture/conventions.md) apply here in full — comments only for non-obvious *why*.

When closing a parity gap, the order is: row classes (already generated) → `api_client` typed methods → domain model in `core_models` if the shape isn't 1:1 → ChangeNotifier or screen-local state → screen. See [../../docs/product/mobile_android_backlog.md](../../docs/product/mobile_android_backlog.md) for the live execution order.

**Multi-modal expansion (Phase 4 — Fitness-hub redesign shipped, G5).** The bottom nav is now `Home / Fitness / [+]Log / Social / You` (`home_screen.dart`): the `Run` tab is gone as a top-level destination, the centre `Log` slot is a raised FAB that fans a Log-run / Log-lift / Log-food **speed-dial** — three **icon-only** buttons in a shallow arc around the button (one top-centre, one down-left, one down-right), not a vertical stack of labelled rows (`widgets/log_speed_dial.dart`; most-recently-used takes the top-centre slot, labels live on tooltips/semantics, long-press repeats the last modality). (The History Log FAB in `runs_screen.dart` keeps the `showLogSheet` bottom sheet — only the centre nav FAB is a speed-dial.) Each action lands on that modality's **dwell-in capture page** — the same in-shell keep-alive `PageView` page model the live recorder uses, so all three behave identically: run → the recorder page (`_pageRun`), lift → `GymScreen` (`_pageGym`), food → `NutritionScreen` (`_pageFood`). You arrive on a workspace you operate in for as long as the session lasts (record the run, build the workout over several sets, log the day's meals), the bottom nav stays visible, and the page's own composer (`showGymComposeSheet` / `showNutritionLogSheet` from the screen's `+`) is one tap away. **Don't route a Log action to a one-shot modal** — the dwell-in page is the contract (an earlier build opened the composer directly; users wanted to stay on a page and keep adding). All three are keep-alive capture pages with no nav destination (so an in-progress recording / half-built workout / day's food log survives swiping to Home and back) — **do not demote any of them to a pushed route.** The `PageView` is `[Home(0), Fitness(1), Run(2=_pageRun), Gym(3=_pageGym), Nutrition(4=_pageFood), Social(5), You(6=_pageYou)]`.

**Fitness is the modality hub** (`fitness_hub_screen.dart`) — a review/plan destination DISTINCT from the keep-alive capture pages. A top sub-tab strip switches four surfaces: **History** = the unified cross-modal activity timeline (the former standalone History tab, *absorbed* here — the tab used to read "All" over a child AppBar reading "History", two names for one surface stacked, issue #666 I9 — `RunsScreen` mounted WITH the gym+food stores and `showKindChips: false` so the hub's TabBar owns the kind axis); **Runs** = the dedicated offline-first run list (`RunsScreen` WITHOUT a gym store) under a labelled **peer strip** `Runs · Routes · Segments · Plans · Races` (`RunsScreen.surfacePeers`, rendered by `widgets/surface_peer_strip.dart`, mirroring web's `RunSurfaceTabs.svelte`) that pushes `RoutesScreen` / `GlobalSegmentsScreen` / `PlansScreen` / `RacesScreen` — the hub threads the existing `TrainingService` in from `home_screen` and owns a `RaceService` for this; **Gym** = `GymScreen` (which carries its own `Log · Routines · Sessions · Records` strip); **Nutrition** = `NutritionScreen`. The hub's Gym/Nutrition tabs host SEPARATE instances from the keep-alive `_pageGym`/`_pageFood` capture pages. The self-hiding contract holds — empty Gym/Nutrition render their own onboarding state. **There is no standalone History destination anymore** — don't re-add one.

**You is profile + Settings** (`you_screen.dart`) — a thin host that puts a profile-header tile above the unchanged `SettingsScreen` body. Settings vacated its own nav slot and folds in here; `SettingsScreen`'s public constructor is unchanged (its mount site just moved). **Coach has no nav slot** — `dashboard_screen.dart` (Home) pins an always-visible "Ask your coach" entry at the top of the body (one tap → `CoachScreen`, gated on `api != null && training != null`).

`GymScreen` / `NutritionScreen` are *also* reachable via the self-hiding Home today's-lift / nutrition-rings cards + the dashboard "View all" (those push a separate instance). The reshape ships **ungated** with a `Preferences.keepRunPrimary` "Run as primary action" toggle (the protect-the-core-runner mechanism). The 5-slot ceiling is why the centre slot is an action, not a tab — don't add a sixth nav destination. See [decisions.md § 63](../../docs/architecture/decisions.md#63-single-app-multi-modal-expansion-run--gym--nutrition-under-one-nav-one-db) + [multi_modal.md](../../docs/features/multi_modal.md).

## Stack

- **Flutter** stable, Dart 3.x
- **State management:** `StatefulWidget` + `setState` throughout. Stores (`LocalRunStore`, `LocalRouteStore`, `Preferences`) are plain `ChangeNotifier`-style singletons that screens subscribe to via `addListener` in `initState` and unsubscribe in `dispose`. No Provider, no Riverpod, no Bloc. If you add a new screen, follow the same pattern — do not introduce a DI framework.
- **Hot-path exception — `run_screen.dart`:** the per-second `_onSnapshot` handler does NOT call `setState`. It updates mirror fields (for `_saveInProgress`, `_refreshLockScreenNotification`, and the `_formattedX` getters) then publishes to a `ValueNotifier<_LiveStats>`. The affected subtrees (map, off-route banner, route-remaining badge, stats panel) are wrapped in `ValueListenableBuilder`, so the rest of the recording tree (activity chips, GPS-lost / permission-revoked banners, layout) doesn't rebuild at GPS rate. If you add a new stat that updates per snapshot, put it behind the notifier, not in a `setState`. Control-state changes (state transitions, manual pause, lap mark) still go through `setState` — that cadence is low enough that a full rebuild is fine.
- **Maps:** `flutter_map` with a MapLibre-compatible raster tile source. Cached via `flutter_map_cache` + `dio_cache_interceptor` for the disk-backed persistent tile cache. See [decisions.md § 8](../../docs/architecture/decisions.md) and [§ 5](../../docs/architecture/decisions.md). **Every `FlutterMap` builds its raster layer with `basemapTileLayer` and mounts a `MapAttribution`** (`widgets/live_run_map.dart` + `widgets/map_attribution.dart`): `flutter_map` renders no attribution of its own, and MapTiler + OSM both require a visible, linked credit — `map_attribution_test.dart` enumerates the `FlutterMap`s in `lib/` and fails a new map that skips either (decisions §491).
- **Recording:** delegates to `packages/run_recorder` — state machine, GPS filter chain, auto-pause, off-route detection, all live there. This app holds the UI and the screens; the recording logic is a package so the iOS and Wear OS apps can eventually reuse it.
- **Auth / backend:** `packages/api_client` for Supabase. Google Sign-In is wired via the native `google_sign_in` package → exchanges the ID token through `ApiClient.signInWithGoogleIdToken`. Apple Sign-In is wired via `sign_in_with_apple` → `ApiClient.signInWithAppleIdToken`. Both buttons render on `sign_in_screen.dart` and `sign_up_screen.dart`. parkrun athlete-number import lives behind a Settings tile rather than a true OAuth flow (parkrun has no public OAuth surface).

## Internationalization (i18n)

Localized via the standard Flutter stack — `flutter_localizations` + `intl` + gen-l10n. See [decisions.md § 113](../../docs/architecture/decisions.md#113-mobile-i18n-uses-flutter-gen-l10n--arb-with-committed-non-synthetic-output-and-a-per-device-locale).

- **Catalogues:** `lib/l10n/app_<locale>.arb` for the **seven** locales `en/de/fr/es/ja/pt/pt_BR`. **`app_pt.arb` is European Portuguese and its canonical tag is `pt-PT`, not `pt`** — 1,182 of its 3,846 strings genuinely differ from Brazilian (measured 2026-09-05; 1,164 of 3,793 when decisions § 760 was written). The FILE keeps the bare name because `flutter gen-l10n` refuses to generate at all when a country-coded catalogue exists without a bare base of the same language, so `app_pt_PT.arb` cannot be the only Portuguese base; every tag a reader, the OS or the runtime sees — `supportedLocales`, `localeLabels`, `_exact`, `_baseToLocale`, `locales_config.xml`, `CFBundleLocalizations` — says `pt-PT`, and the locale-reach guard's `arbTagOverride` holds the two spellings together. `pt-PT` / `pt-AO` / bare `pt` resolve to it; `pt-BR` matches exactly. **The order of `supportedLocales` is load-bearing**: following the device locale leaves `MaterialApp.locale` null and Flutter resolves against that list itself, so `Locale('pt','PT')` must precede `Locale('pt','BR')` or a bare-`pt` device silently lands on Brazilian. Web ships `pt-PT.ts` since decisions § 755, so this is no longer a locale mobile carries alone. **Both Portuguese catalogues address the reader in the `você` register** — `seu`/`sua`, `-lhe`, third-person verbs, subject pronoun elided (decisions § 755, § 782) — and `architecture_guards_test.dart § locale reach` fails a string that slips back into `tu`. It is two tests because the markers are two kinds: a token list is exact for the forms nothing else spells the same way (`teu`/`tua`, the `-te` enclitic, `contigo`, the tu-only finite verbs), while the affirmative imperative is unlistable — its tu form is letter-for-letter the third-person present indicative — so that half is DERIVED against `app_pt_BR.arb`, which the first test pins as uniformly `você` to keep the reference honest. Write `Tente novamente`, not `Tenta novamente`. The spoken `tts*` and `guided*` cues are held to the same register as the screens (§ 782 reversed § 760's `tu` choice there once the `guided*` block was measured as already `você`). `app_en.arb` is the template (carries the `@key` metadata); the rest are value-only.
- **Generated code is committed** under `lib/l10n/gen/` (config in `l10n.yaml`, `output-dir: lib/l10n/gen`). After editing any ARB, run `flutter gen-l10n` and **mirror the regenerated files to the iOS twin** — they're byte-identical (gen-l10n output is package-name independent).
- **Adding a string:** add the key to **all seven** ARBs (real translations, not English placeholders — `test/l10n_parity_test.dart` enforces non-empty + key parity + faithful `{placeholders}`), regenerate, then `AppLocalizations.of(context).<key>` at the call site. ARB keys are camelCase derived from web's dotted keys (`nav.dashboard` → `navDashboard`).
- **Locale selection:** per-device, **not** DB-synced — `Preferences.locale` (`_kLocale`, canonical tag; null = follow device) drives the global `localeNotifier` → `MaterialApp.locale`. Picker is in Settings → Preferences, and it **derives its options from `supportedLocales`** — never list them, that is decisions § 740. Pure negotiation lives in `lib/l10n/locale_support.dart` (Dart twin of web's `locale.ts`); `main.dart`'s `localeListResolutionCallback` routes both the device list and an explicit `MaterialApp.locale` through it, so Flutter's own `basicLocaleListResolution` never runs and the order of `supportedLocales` is not load-bearing.
- **Adding a locale** means adding the ARB, regenerating, and adding it to `supportedLocales` + `localeLabels` + `_exact` + `_baseToLocale` in `locale_support.dart`, `localeTags` in `test/l10n_parity_test.dart`, `android/app/src/main/res/xml/locales_config.xml`, and `CFBundleLocalizations` in the iOS twin's `Info.plist`. `test/architecture_guards_test.dart § locale reach` reads `lib/l10n/` as the source of truth and fails on any of them being missed — a catalogue that ships in the binary and resolves for nobody is the defect it exists to stop.
- **Test harnesses** that pump a screen using `AppLocalizations` must set `localizationsDelegates: AppLocalizations.localizationsDelegates` + `supportedLocales: AppLocalizations.supportedLocales` on the test `MaterialApp`, or `AppLocalizations.of(context)` throws.
- **Dates:** locale-aware `intl` `DateFormat` lives in `lib/l10n/date_format.dart` (pure helpers — `formatDateMed`/`formatDateShort`/`formatMonthName`/`formatDow`/`formatDowNarrow`/`formatMonthAbbr`/`formatDateTime`/`formatTime`/`formatDowDateShort`, each taking a BCP-47 tag). Every helper uses CLDR skeletons (`yMMMd`, `MMMd`, `MMMEd`, …), so field order is locale-appropriate — month-first for `en` (US), day-first for de/fr/es/pt, year-first for ja. **Every helper normalizes a UTC instant to local time before formatting** (`_local(dt)` = `dt.isUtc ? dt.toLocal() : dt`): stored timestamps (`runs.started_at`, comment/review `created_at`, event starts) arrive as UTC `DateTime`s from `DateTime.parse` of a `Z`-suffixed string, and `DateFormat` renders raw wall-clock fields with no zone conversion — so formatting them directly showed the UTC calendar day, which rolled a day for viewers behind/ahead of UTC (the "manual run saved as tomorrow" bug). Pass synthetic calendar values (`DateTime(2026,1,5)` for DOW labels, `DateTime(2000, month)` for month names) as local `DateTime(...)` (`isUtc == false`) — they pass through untouched. **Don't re-add `.toLocal()` at call sites; the helper owns it.** `main.dart` calls `initializeDateFormatting()` once at startup (tests do it in `setUp`). Get the tag from `localeToTag(Localizations.localeOf(context))` where a `BuildContext` exists, else `activeLocaleTag` (context-free accessor in `locale_support.dart`, kept in sync from `main.dart` via `registerActiveLocaleTag` on every `localeNotifier` change — mirrors `registerActivePreferences`). The old hand-rolled month/day arrays are gone; `recurrence.dart`'s `weekdayLabel` stays English (TS↔Dart parity pair, not a display formatter).
- **TTS is locale-aware** (Epic C3, done). `audio_cues.dart` resolves the gen-l10n catalogue for the active locale via `lookupAppLocalizations(localeFromTag(activeLocaleTag))` (context-free) and re-applies the engine language per announcement via `setLanguage(ttsLanguageTag(activeLocaleTag))` (`en`→`en-US`, `de`→`de-DE`, `pt-BR`→`pt-BR`, unknown→`en-US`; best-effort, a failure never stops the cue). Spoken split / pace / speed / off-route / workout-step / pace-drift phrases live behind `tts*` ARB keys; `guided_runs.dart`'s scripts (titles + cue text) live behind `guidedRun*`/`guided*` keys and the library is now `guidedRunLibrary(AppLocalizations)` (was a `const`). The pure utterance helpers take an optional `localeTag` defaulting to `activeLocaleTag`, so `audio_cues` unit tests keep asserting the verbatim English output.
- **String extraction complete** (2026-06-03): every user-facing screen/widget now routes through `AppLocalizations`. A final wider sweep (stricter than the `Text('[A-Z]` heuristic) closed the real remainder: the `settings_screen` landing tiles, `period_summary` (`Week of`/`All time`/share text — pure helpers via context-free `lookupAppLocalizations`), the `verified_badge` tooltip, and dashboard/run-detail best-effort distance names (`bestEffortDistanceLabel` in `run_stats.dart`). Intentionally left English (not gaps): `devices_screen.overrideKeyRegistry` `label`/`hint` (fallbacks behind the `labelFor`/`hintFor` l10n switch), `workout_review_section.fromMap` labels (display uses `localizedLabel(l10n)`), `$e`-in-banner exception text, the `"DELETE"` deletion challenge token, and proper nouns. RTL (`EdgeInsetsDirectional`) is the only remaining mobile i18n work — deferred, no RTL locale ships yet.

## What's real vs stubbed

Nearly everything under Phase 1 "Android" in `roadmap.md` is implemented. Specifically:

**Live and working:**
- All of the `lib/screens/` files in the list below are wired to real data.
- Background GPS recording with foreground service, auto-pause, lap markers, wakelock.
- Offline-first: runs save to `LocalRunStore` → sync on connectivity change / app foreground / WorkManager periodic background sync → reconcile via `last_modified_at` timestamps.
- Strava ZIP import (GPX/TCX/FIT) and Health Connect import. Batch cloud push via `saveRunsBatch`.
- Disk-backed tile cache.
- Personal bests, weekly goals, edit title/notes, share as GPX, delete.
- Runs filter by activity type (run/walk/cycle/hike filter chips).
- Configurable split interval for voice cues (Settings > Split interval).
- Advanced GPS mode (Settings > Advanced GPS) for higher accuracy under tree cover.

**Stubbed or deferred:**
- Strava live OAuth (the ZIP import path is shipped). The OAuth surface is a Settings → Connect Strava button that's still scaffolded behind the same `apps/web` flow that ADR §41 covers.

## Dart analyzer policy — treat `info` as noise

`dart analyze` on this package reports ~2100 issues. **Every remaining entry is `info`-level** — the package is clean of `warning`/`error` as of this pass. The noise buckets (top categories from `dart analyze | grep -oE ' - [a-z_]+$' | sort | uniq -c | sort -rn`):

- `always_use_package_imports` (~220) and `avoid_relative_lib_imports` (~140) — these two interact with [decisions.md § 39](../../docs/architecture/decisions.md#39-mobile_android-and-mobile_ios-share-a-byte-for-byte-dart-codebase): tests use relative imports so the same file resolves on both targets. Not being fixed.
- `deprecated_member_use` (41) — `withOpacity` → `withValues` (9) plus assorted others. Deferred until we do a theme/deps pass. The `share_plus` half is **closed**: `share_sheet.dart` calls `SharePlus.instance.share(ShareParams(...))` and the deprecated `Share` statics are gone from the tree ([decisions.md § 714](../../docs/architecture/decisions.md)).
- `unnecessary_underscores` / `use_null_aware_elements` / `prefer_single_quotes` / `use_build_context_synchronously` — small stragglers.

**Do not waste a turn on these.** Only act on `info` if your change touched that specific file. **Do act on any new `warning`/`error`** — the bar is "zero warnings", so a fresh one is a regression your change introduced. The CI "Test Flutter packages" job runs `melos exec -- dart analyze` and **its exit code is enforced** — `dart analyze` exits non-zero on any `warning`/`error` (info-level is not fatal), so a single fresh `warning` anywhere in the melos-analyzed packages (incl. `test/`) reds the job. This bit us once (run 28033171233): three `unused_element_parameter` warnings on never-exercised test-fake params + one `unnecessary_cast` sat red on `main` for days because an earlier note here wrongly claimed the exit code was ignored. It is not — fix the warning at the root.
