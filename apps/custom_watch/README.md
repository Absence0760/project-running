## Power discipline

Per [`performance_path.md`](../../docs/custom_watch/performance_path.md), battery life is decided by **hardware** (Sharp MIP vs AMOLED ~3–4×, Ambiq vs nRF52 MCU ~25×, snapshot GNSS ~2–3×) — all tier-2 chip swaps — and the nRF52840 **dev kit can't measure ultra-watch power at all** (~30 mA idle from the onboard debugger). So tier-1's job is not a measured number; it's getting the **firmware architecture** right so the wins land at tier-2: DMA/interrupt-driven I/O, a tickless async runtime, aggressive sleep where every wake is justifiable, partial display updates, and a clean always-on/screen-on split. What that translates to in this workspace:

**Done:**
- **Partial display updates** — the `sharp_mip` driver tracks dirty lines and sends only changed ones (+ the VCOM-only frame when idle); a static screen costs near-nothing.
- **DMA/async, tickless** — every task is Embassy async over EasyDMA (no busy-polling), so the executor sleeps until a real event. **GPS UART reads run on a `BufferedUarte` ring** (`gps.rs`, `RX_RING_LEN`) — the CPU wakes once per half-buffer instead of per byte, and the next transfer is pre-armed in hardware so a CPU halt cannot lose bytes (decisions.md § 698), the doc's DMA-not-polling lever (sim-verified: fixes flow end-to-end and distance accrues).
- **Animations gated** — the ~1 Hz face animations freeze outside an ~8 s post-interaction window (`ANIM_WINDOW_S`), so an unattended wrist stops the per-second decorative redraw.
- **No gratuitous wakers** — the 2 Hz liveness LED is behind the default-OFF `dev-blink` feature (the sim/flash helpers opt it back in); a plain `cargo build` carries no free-running blinker.
- **BLE long connection interval** — the `ble` build requests a ~1 s interval on connect (`set_conn_params`), vs the 7.5 ms HID default (~100× idle-radio power). Compile-verified only.
- **Hardware EXTCOMIN VCOM** — EXTMODE held high + a free-running ~3.8 Hz PWM on EXTCOMIN (`ui::vcom_task`) drive the panel's bias inversion in hardware, so the display driver (`SharpMip::new_external_vcom`) never toggles the software VCOM bit and never sends a VCOM-maintenance frame: a clean framebuffer now flushes **zero SPI**. This removes the display's standing reason for the CPU to wake every second. Sim-verified to boot + init the PWM + still render the dashboard; the EXTMODE/EXTCOMIN wiring itself is bench-gated (some breakouts strap EXTMODE — confirm on the real panel).
- **Idle CPU-sleep** — building on hardware VCOM: the screen task is **event-driven** (it waits on the state Watches and re-renders only on a change, with a short tick only while animating or watching a fresh fix go stale, else a 30 s heartbeat); the idle-face title row is **static** (no ticking uptime); and the record task **drops its 1 Hz tick while idle/finished** and publishes a snapshot only when it changed. So a resting recorder wakes nothing downstream, and with no sensor events the CPU sleeps seconds apart instead of every second. Sim-verified: recording still drives the dashboard through events — the elapsed hero advances and distance accrues with no per-second timer.
- **GPS fix de-rate while idle** — the `gps` task now watches `state::RECORD` and, while **no run is active**, forwards at most one fix per `IDLE_FIX_MIN_INTERVAL_S` (held one second under the face's `STALE_AFTER_S` freshness budget) instead of every ~1 s fix. A moving idle position used to wake the UI, record, and phone consumers every second for a view nobody is recording; a run (Recording/Paused) lifts the throttle and gets every fix. This is the *software* half of GPS duty-cycling — it cuts the downstream wakes, not the UART stream itself. Sim-verified both ways: the idle (no-autostart) build publishes fixes ~4 s apart with the position still advancing (face stays fresh, never falsely "searching"), while the recording build gets full-rate fixes and distance accrues normally.
- **HR duty-cycling** (2026-07-18) — the MAX86177 samples continuously in Performance but 15 s per 60 s / 120 s window in Balanced / Expedition (`watch_core::hr_duty`, windows phase-locked to uptime-period boundaries; the constants are derivations, not measurements — the DK can't measure power, and the saving is deliberately NOT folded into `gnss_mode`'s battery projections until a PPK2 exists). Between windows the part goes into `shutdown()`; window-open `wake()` flushes the FIFO so pre-shutdown counts can't replay, and the detector resets. Honest bounded staleness everywhere the reading flows (`hr_duty::shown_bpm`): the face blanks to `--` after one full period (Performance keeps the ordinary 5 s budget — which also fixed a latent freeze-forever on a wedged bus), zone-time banking stops at the same budget, and track-point `bpm` stamps go empty rather than stale. A sensor that won't wake degrades to "no HR" for that window (L4). **Sim-verified 2026-07-19** against the new Renode MAX86177 model: six clean 15 s-on / 60 s-period Balanced cycles, the part really shut down and its FIFO frozen between them, flushed on every wake, the detector re-converging to the same BPM inside ~3 s, and the reading honestly held (not re-sampled) across an off-window — see `sim/verification-2026-07-19/`. The *power* saving itself stays a derivation, bench-gated like every other figure here.
- **Selectable GNSS recording modes** (2026-07-10) — the de-rate above, generalised into the mode surface every ultra watch ships: `watch_core::gnss_mode` defines **Performance / Balanced / Expedition** (every ~1 s fix / one per 15 s / one per 60 s — the UltraTrac / UltraMax class), each with a *projected* battery-hours figure (~110/~180/~220 h; a derivation in the module docs, not a measurement — the DK can't measure power). **BTN3 cycles the mode on the idle face** (`MODE PERF ~110H` row; mid-run BTN3 stays on pages via the host-tested `btn3_action`, so a run's mode is frozen), the gps task forwards fixes at the mode's cadence while recording, the recorder's jump gate scales to the interval (`MAX_SPEED_MPS * dt` past 1 s — a fixed 100 m ceiling would reject every legitimate ~240 m Expedition leg; the 1 Hz filter is unchanged), and the face's staleness budget stretches to the cadence (`face::stale_after_s`) so a 40 s-old Expedition fix reads `SATS`, not `STALE` — run-view GPS rows carry the mode tag. Sim-verified with `bin/watch-sim.sh --no-autostart` (boot idle, cycle the mode, BTN1 to start): forwarded-fix cadence measured ~1 s / ~15 s / ~60 s per mode with distance accruing in all three. Still only the *software* half — the tier-2 receiver power-down below is where the mode's real battery win lands.

- **GNSS power-down between fixes** (2026-07-19) — the deeper half of the recording modes above, closing the last architecturally-owed power lever: while a run is **Recording** in Balanced / Expedition, the gps task follows each published fix with **UBX-RXM-PMREQ** on UARTE0's TX (u-blox backup mode, bounded duration — the tier-1 software path; no load switch) and wakes the receiver with the 0xFF RX-activity byte a 5 s reacquire margin before the next fix is owed; the PMREQ duration is the self-wake backstop for a lost wake byte (never 0 — an unbounded sleep). The schedule is the pure host-tested `watch_core::gnss_power`, keyed to the last *published* fix rather than `hr_duty`'s uptime phase-lock (the publication throttle is publish-relative, so a boundary-locked wake could drift into its own reacquire margin and stay there, never sleeping again); the UBX encoder (`ublox_nmea::ubx`) is host-pinned to spec-derived byte vectors. Constants are derivations, not measurements — the DK can't measure power — and the mode's projected battery figures are untouched (they already assume this lever). Performance / idle / Paused keep the receiver on (the idle de-rate stays); a run-state change mid-window wakes it early; a failed PMREQ write leaves it on (L4 — status-quo draw, never a lost fix). Honest under a receiver that never sleeps: every fix the sim's PMREQ-ignoring feed delivers inside a window is one the publication throttle already drops (host-pinned), so sim and hardware publish identical sequences, and mid-window staleness reads through the existing `face::stale_after_s` budget. Sim-verified in Balanced (`--no-autostart`, BTN3 → BTN1): PMREQ after each published fix, wake byte on schedule, publications steady at ~15 s, and a confirmed BTN2 stop mid-window wakes the receiver immediately. The module's *actual* power state is bench-gated until the dev kit lands.

## Local testing

The watch's developer inner loop is `bin/watch-flash.sh` from the repo root (or `cargo run --release` from this directory): build the firmware, flash it to a connected Nordic nRF52840 DK, stream `defmt` logs back to your terminal until Ctrl-C. Host-side unit tests run via `bin/watch-test.sh` or `cargo test` and don't need a board. Run `bin/watch-doctor.sh` once per machine to verify toolchain + board detection. No board at all? `bin/watch-sim.sh` boots the same release ELF on an emulated nRF52840 DK (Renode) with decoded defmt logs streaming and a canned NMEA fixture feeding the GPS UART — the whole boot + blink + task-scheduling path runs today, pre-parts ([decisions.md § 208](../../docs/architecture/decisions.md#208-firmware-simulation-runs-the-unmodified-elf-on-renode-with-a-custom-defmt-rtt-drain)). See [`local_testing.md`](local_testing.md) for the full setup walkthrough, the host-vs-on-target-vs-sim testing split, and the common-error reference.

The barometer is wired too — the `baro` task drives the **BMP581** (`drivers/bmp581/`, 5 host tests) over TWISPI1 through the same async probe guard, feeding `watch_core::elevation` (barometric altitude + cumulative-vert accumulator) and publishing a snapshot to `state::ELEVATION`. That snapshot is now surfaced end-to-end: the idle faces prefer the barometric altitude for their ALT rows; the diagnostics view (behind BTN4, decisions §291) carries the cumulative-vert line (`VERT +gain -loss`) while no fix supplies a clock and the seconds clock once one does, while the home face tells the time with its 32x48 numeral clock hero (generated by `drivers/sharp_mip/scripts/gen_bignum.py` from Source Code Pro Bold — the `gen_font.py` pipeline at hero size), minute-resolution and extrapolated from the last fix's clock + uptime so an idle watch owes the panel zero per-second redraws — local time once a settings push carries the phone's timezone offset, UTC-labelled until then (decisions §293) — and the phone-link status frame carries an additive optional `"elev":{alt_m,gain_m,loss_m}` object (schema still `"v":1`, `null` when the baro is absent) that the mobile dev Sim Watch screen decodes and displays. **Run sync (firmware half) is now wired.** The record task captures the GPS *track*, not just totals: on start it opens a `run_store::RunWriter` over a slot-sized RAM staging buffer, `push_point`s each fix the recorder accepts as a new anchor (the added host-tested `Recorder::last_fix_stored` signal, so stored points mirror the acceptance filter exactly) stamped with the latest HR (`state::HR`) + barometric altitude (`state::ELEVATION`), and on stop finalizes the blob with the snapshot totals and commits it to internal flash. `app/src/run_flash.rs` is the flash driver — a `FlashSink` (`run_store::ByteSink`) over embassy-nrf's NVMC plus a `RunStore` (commit / manifest / read_chunk) over the host-tested `watch_core::flash_store` slot layout: **4 slots × one 4 KiB erase page, reserved at the top of flash in both `memory.x` and `memory-ble.x`** (FLASH shrunk by 16 KiB; the region addressed by absolute offset `0xFC000`). It is **best-effort / L4** — it probes for the NVMC controller once at boot and no-ops every op if it's absent, and any flash error only `warn!`s, so recording is never blocked on flash. The **per-run point cap is 253** (`HEADER + 253·POINT + FOOTER ≤ 4096`): a few minutes at ~1 accepted fix/s. A full ultra needs the tier-2 external QSPI flash; the internal-flash store is a bench-prototype foundation, not shipping capacity. On the **`ble`** build the same Threkir GATT service now carries `run_manifest` (read + notify: `ManifestHeader` + one `ManifestEntry` per finished run) and `run_chunk` (write + notify: the phone writes a `ChunkRequest {run_seq, offset, len}`, the watch notifies back that slice of the blob clamped to the notify MTU + blob end) — the protocol of [firmware.md § Sync protocol](../../docs/custom_watch/firmware.md), live link preserved. Like step 6 this **compiles + links but has never run on hardware**; additionally, with the SoftDevice enabled the NVMC backend must be swapped for `nrf_softdevice::Flash` (SoftDevice-coordinated flash) before real use — see the caveat in `app/src/run_flash.rs`. Reboot-persistence of the slot directory is now **wired (2026-07-10)**: `RunStore::new` scans every slot's flash bytes at boot via the host-tested `flash_store::recover_slot`, rebuilding the directory from the finished blobs already on flash so a run recorded in a prior power cycle is re-advertised instead of being lost until its slot is overwritten. Because the blob doesn't store its own length, the footer is located by scanning point-aligned offsets for the footer magic **plus** a CRC32 that verifies everything up to that candidate footer's own CRC field — the CRC is what makes a stray footer-magic inside track data safe, and since run-store **v3** (2026-07-25, decisions §321) the colliding window includes the decoy's would-be totals, so the scan is harder to fool than it was (10 new host tests, incl. the decoy-magic case + erased/truncated/newer-version rejection). `SlotDir::next_run_seq` resumes numbering above the highest recovered seq so a fresh run can't reuse a recovered id, and the record task seeds its counter from it. The core scan + directory rebuild is host-tested; the `app/` flash-read side (`recover_dir`) is best-effort / L4 and, like the rest of the driver, compile-verified only until the dev kit lands. **The phone half is now built too** (decisions §211): `apps/mobile_android/lib/sim_watch_sync.dart` is a Dart mirror of `run_store` — it pulls the manifest, reassembles chunks, `verify_blob`s each run (pinned to the SAME golden vector as the Rust `run_store` test, so the two can't drift; **v3** widened that check to cover the footer's totals, so a blob is trusted whole or refused whole and the phone can no longer ingest a run whose summary bit-rotted, decisions §321), reshapes it into the payload the existing `WatchIngestQueue` / `runFromWatchPayload` → `api.saveRun` path already uploads, and delivers it via `WatchSyncClient` behind an injectable transport seam (production impl over the sanctioned `flutter_reactive_ble`). A dev-gated "Sync runs" action on the Sim Watch screen drives it; the pull→decode→verify→deliver path is unit-tested without a radio. What remains is purely on-hardware: exercising the real SoftDevice + NVMC-vs-`nrf_softdevice::Flash` path, and bench-confirming the boot-time slot recovery reads back real committed blobs — both pending the dev kit. Those items, and the rest of what this step has to demonstrate on silicon, are enumerated as pass/fail criteria in the step-7 section of [`quality_standards.md`](../../docs/custom_watch/quality_standards.md#tier-1-bench-verification-checklist) — work that checklist rather than re-deriving "what's left" from this paragraph. **Two recorded flash defects gate a clean bench run of this step**: an in-progress checkpoint is advertised as a finished run (`FLAG_FINISHED` is enforced by nothing), and `checkpoint()` erases its slot before rewriting it — see the 2026-07-25 entry in the chronology below.

**Font `+` glyph fix + per-session sim pointer (2026-07-19).** The font bug two sim passes logged independently is closed, and the audit that came with it found a second glyph nobody had noticed. `scripts/gen_font.py` rasterised the glyph strip at 8x16 with no coverage information, so a stroke thinner than a device pixel vanished: `'+'` lost its vertical stem and packed byte-identical to `'-'` (the **Pacer** page's whole purpose is a signed `+0:42` / `-1:05` delta, and the idle face's `VERT +gain -loss` row lost its sign the same way), and `'|'` lost its stem too and packed **all-zero** — invisible, byte-identical to a space. The generator now re-rasterises colliding glyphs at 2x and averages back down, and fails loudly if a collision survives. It repairs only the **degenerate member** of a collision — candidates ranked by how much detail the 1x pass cost them, worst first, stopping the moment the group is pairwise distinct — because a collision has one guilty party and re-rasterising the innocent half is churn: at this cell size the 2x pass renders a hairline as two rows, so repairing `'-'` alongside `'+'` left the hyphen visibly heavier than the `'='` and `'_'` bars it sits beside. The repaired set is therefore exactly `'+'` and `'|'`; every other glyph, `'-'` included, stays bit-identical to the 1x pass. That loud-failure guard originally excused space on both sides — which is precisely why an all-zero `'|'` sailed through it — so space now participates: it is never the glyph re-rasterised, but anything else that packs blank collides with it and gets repaired. A new `drivers/sharp_mip/tests/font.rs` pins the invariants (the driver's `tests/driver.rs` stays about framebuffer semantics and wire encoding): `'+'` differs from `'-'` and carries a crossbar *plus* a stem that crosses it; `'|'` is a full-height stroke; `'='`, `'_'` **and `'-'`** are byte-for-byte what they were, so a repair can never quietly reshape a glyph that rasterised correctly; **no two printable chars share a bitmap, space included**; and `'+'` reads as a cross at 1x / 2x measured on the rendered framebuffer (`draw_text`, `draw_text_2x` pixel-replicate the one 8x16 glyph, so a correct glyph scales exactly; the 3x case was dropped 2026-07-22 with `draw_text_3x` itself, decisions §292). **Settings frame v3 — the CRC32 the format was missing (2026-07-25, decisions § 319).** The defect the property suite found above is fixed. `SET1` takes a third version byte and appends a four-byte little-endian **CRC32 trailer** over everything before it, reusing `run_store::crc32` (one checksum implementation in the firmware, the way `flash_store`'s config and bond records already share it) — the Dart encoder likewise reuses the `crc32` the run-store decoder already has. **Run-store v3 — the footer totals come under the CRC (2026-07-25, decisions § 321).** A follow-up recorded during the PR #620 review: the run blob's CRC32 covered only the `header | records` prefix, leaving the footer's `distance_m` / `moving_s` / `elapsed_s` outside the window — and the Dart mirror's suite had that written down as the *frozen wire spec*, with a test asserting a flip there **must** still verify. One rotted bit in those twelve bytes therefore produced a blob that passed `verify_blob`, passed `recover_slot`, and synced as an ordinary run with silently wrong numbers, which is worse than a rejected run because nothing tells the runner. **v3** takes the CRC over `blob[..len - 4]` — everything but the four bytes the checksum occupies. No field moved and no length changed; only the hashed window widened. Both emitting paths go through one `stamped_footer` helper (a second hand-rolled copy is how two CRC domains drift apart), and `recover_slot`'s footer scan widens with them, so a decoy `END1` in track data must now collide over its own would-be totals too. **Pre-v3 blobs are deliberately undecodable** (`MIN_FORMAT_VERSION` = 3): dispatching the CRC window on the version byte would have preserved the unprotected-totals hole forever for anything claiming to be old, and with no deployed devices there is nothing to migrate — an old blob on a bench board is rejected by version, its slot reads free, and the next run reuses it. - **`CRS1` v3 — the course frame gets a mandatory CRC32** ([§ 335](../../docs/architecture/decisions.md)). Through v2 a single flipped byte in the point array decoded as a frame of exactly the right length, a legal point count, known flags, and a perfectly valid course — displaced by up to a continent (one bit of a `lat_e7` high byte moves the first point 6.8°, pinned by test). - **The page-grid press-cost table re-derived at 33 pages.** The term the earlier reproduction attempt was missing: the grid is **additive** — § 288 never removed the bidirectional walk, so a page costs `min(walk, 1 + grid moves)` and the grid's worst *cell* is not the worst *page*. **Sleep-station mode — the 38th page (2026-07-30, [§ 373](../../docs/architecture/decisions.md)).** The roadmap's "how long can I sleep and still make the next cut-off" wedge, and it needed almost no new arithmetic: `cutoff_eta::next_cutoff_eta` already returns *(limit − elapsed) − (time still needed)* as its margin, which IS the nap budget before a reserve, so `watch_core::sleep_station` calls it once with a different pace and subtracts. **The nap timer deleted itself.** The race clock runs through a pause, so a budget recomputed each tick falls one second per second while the runner sleeps — the countdown is the budget, and the "elapsed clock that honestly keeps running" the row asked for is the race clock already kept. **Climb detection + the crest ahead — the 37th page (2026-07-29, [§ 359](../../docs/architecture/decisions.md)).** The parity backlog's ClimbPro row, and this batch's one item with **no web helper to port**. `watch_core::climb` splits into the two questions a runner on a hill actually asks: `ClimbDetector` segments the climb they are **in** from the recorder's own distance + altitude stream and needs no course, while `crest_ahead` answers how much is **left** from the pushed course profile and exists exactly when a course does — the live half never fabricates the second answer, because the watch cannot see the hill and a `--` remaining would read as a crest at zero metres. Both edges are **hysteretic and deliberately blunt**: a climb opens only past 20 m of gain above the last low point at ≥ 2 % grade and closes only once 10 m has been lost below its high point, because a page that re-zeroes on every roller is worse than no page (a runner pacing a 400 m ascent would watch their banked gain reset three times on the way up). That drop threshold is what makes the high point the **crest**, and the same rule runs the profile search so a shelf in a staircase climb is not reported as the top. Grades come from a climb's endpoints, never the last two samples — a 1 m baro twitch across a 5 m step reads as a 20 % grade. Integration cost was near zero: the detector rides the **same altitude sample `feed_gap` already takes** (so a hill cannot register on the GAP page and not this one) and `start` resets it (a run beginning at a lower trailhead than the last one ended would otherwise open a phantom ascent on its first fix); the crest half needed **no new wire at all**, since §334's distance-even `CRS1` v2 profile and the nav task's along-course position were already on-device — so it is derived per snapshot and shrinks with every fix, measured from the runner rather than their grid sample. **Backyard-ultra mode — the 38th page, and the first differentiator wedge on the wrist (2026-07-30, [§ 372](../../docs/architecture/decisions.md)).** The last-person-standing format sends one loop off every hour **on the hour** and scores on **loop count**; nothing a Garmin or a COROS ships models it, which is why the roadmap tracks it as a wedge rather than parity. `watch_core::backyard` (24 host tests, no web twin to port) derives the countdown from the runner's **local hour boundary** — the receiver's UTC clock shifted by the pushed timezone, extrapolated on uptime, the same shaping the Daylight page uses — and never from a lap or a run start: a runner who leaves 30 s late on loop 7 has a 59:30 loop, and an elapsed anchor would be minutes wrong by loop 20. Arming is a sixth settings-menu row in a spare `CFG1` flag bit, idle-only (re-pointing the auto-lap means a run is wholly in the mode or wholly out); `SCR1` metric byte 35 carries the countdown to the phone's composer, mirrored to the iOS twin. **What it refuses:** to declare a runner in or out. **Auto-lap became a chosen trigger (2026-07-30, [§ 374](../../docs/architecture/decisions.md)).** The recorder's auto-lap had been the constant `AUTO_LAP_DISTANCE_M` since 2026-07-09 — the same kilometre for every runner. `watch_core::auto_lap` makes it a **closed eight-rung catalogue** (`Off`, 1/5 km, 1/5 mi, 5/10/30 min) armed by `Recorder::set_auto_lap`, still defaulting to the kilometre it always had. Closed rather than an arbitrary metre count for a reason specific to this device: the flash lap store holds 64 records, so a 1 km trigger already overflows it on a 100 km run, the coarse rungs are what keep an ultra's splits inside it, `Off` is what lets a runner spend those records on splits they pick by hand, and an open field would let a 50 m trigger exhaust the budget inside 3.2 km. The closed set also costs one wire byte and three flash bits, which is what made both rails cheap. **The auto-pause interaction is the load-bearing call**: paused time counts toward nothing on either axis — distance structurally (it only accrues on a fix the acceptance filter takes as movement) and time by choice, because the budget is **moving** time, the axis the fuel arms already bank on (§ 214), not the elapsed clock. An elapsed-clock auto-lap turns a 40-minute sleep-station stop into eight zero-distance laps at the 5-minute rung, and on a 64-record budget those empty laps *displace real ones*; that deliberately differs from § 332's time **alert**, which banks on elapsed on purpose, because an alert costs a banner and a lap evicts a record. Pinned rather than argued — a test runs both an armed distance rung and an armed time rung through an hour of sub-threshold GPS jitter plus 3600 ticks and asserts the lap counter never moves. **Two rails carry the choice.** `SET1` **v7** is the bump v6's `KNOWN_FLAGS2 == u8::MAX` const-assert existed to force: both presence bytes were saturated, so the field rides a third one exactly as `flags2` rode v2; `decode` accepts v1–v7 side by side and the frozen v6 golden vector is pinned as still decoding, its absent trigger leaving whatever the watch holds standing rather than resetting a race's splits. Flash keeps it in `CFG1`'s flags byte behind a set-marker plus three discriminant bits — the §351/§353 drill a third time, no config-record version bump, bit 7 now the last one free — and the `record` task re-applies it at boot, because a battery pull at hour 60 of a 100-miler would otherwise put the rest of the race silently back on 1 km laps. The Lap page **names the armed trigger** beside the last split (`LAST 4:58    1KM`, or `OFF`), since a setting that changes what a page counts, on a page with no way to see it, reads as a broken lap counter. Deliberately **not** a § 351 settings-menu row: that menu is budgeted at five items so the farthest is two cursor steps and any change stays inside the published ≤ 4-press bound, and a rung a runner picks once before a race — with a keyboard, on the phone, where they also pick km or miles — is not worth trading that bound for. **Storm detection: the 41st page, and the reduction that makes it honest (2026-07-31, [§ 376](../../docs/architecture/decisions.md)).** The parity backlog's "Weather / storm alerts" row had read *baro-driven storm detection is cheap* since it was written, and the word cheap was hiding the entire problem: **a falling barometer means weather, and it also means climbing** — a front moves station pressure a few hPa over hours, 500 m of ascent moves it ~57 hPa in forty minutes. Trending raw station pressure would have announced a storm on every col of a mountain ultra. `watch_core::storm` trends the **sea-level reduction** instead (`elevation::sea_level_pa`, the exact inverse of `altitude_m`, sharing its constants): climbing moves the pressure and the altitude together so the reduced value does not move, a front moves the pressure alone so it does. **The reference altitude has to be independent of the pressure**, or the reduction returns the reference it was derived against with the weather divided out — a host test pins exactly that — so it is the **GPS** altitude, narrowed through the same `plausible_gps` window the vert filter uses, and pointedly **not** the complementary filter's corrected altitude, whose whole job is to remove weather drift and which would therefore suppress the signal (`HPF(baro) + LPF(gps)` leaves `HPF(weather)` as the error term; in Expedition mode that crossover sits near a hundred minutes and would swallow most of a three-hour trend). Noise is what that trade costs: ±15 m of receiver altitude is ~1.8 hPa of reduction error, paid for by five-minute buckets behind a three-corroborated-readings floor and a least-squares slope over the whole window rather than a difference of its endpoints. **The refusals are the half that matters** — no corroborated GPS altitude inside two minutes reads `NO ALT REFERENCE` (not a trend off the last good one, and never off raw station pressure), under a third of the window banked reads `TREND BUILDING`, and both still show the absolute reduced pressure so a working barometer never presents as a broken one. `BARO` seats beside `SUN` (the sky's clock and the sky's mood) and closes with `TENDENCY NOT FORECAST`, in the register `WATCH CANNOT WAKE YOU` established. The alert is off by default, once per front, between pace and fuel in the **never-dropped** class — a missed gel is re-offered a cadence later, a missed front is not — with no cooldown beside it because the signal is already hysteretic, and only a *measured* recovery re-arms it so a canyon cannot turn one front into two banners. `SET1` bumps to **v8**: `flags3` had six free bits and nothing about the layout required it, but a version has to name exactly one field set for an unknown presence bit to mean anything, so the bump is the discipline rather than the layout. Page 41 moves **no published press-cost ceiling** (symmetric worst still 7, forward-only still 10; the averages 4.25 → 4.2927 and 5.55 → 5.6585). Host sweep **2365 → 2407**; all three feature sets green on `clippy -D warnings`. **Sim-verified** for what the new `storm` scenario names — it ramps the BMP581 model's *sea-level reference* while its altitude stays put and asserts the baro task's own tendency line through the refusal, a still atmosphere reading `Steady` inside 0.5 hPa, `Storm` past the armed threshold, one banner, and the page rendering — and it was **verified to fail as well as pass**: mutating the tracker to take the baro-derived altitude leaves the still atmosphere at a suspiciously exact `+0.00 hPa` on the ISA reference and the front never arrives. **What no simulator here can settle** is the climb-versus-front separation itself (the harness cannot ramp the fixture's GPS altitude independently of the barometer), so that stays host-tested; the 3 h window and the 4 hPa threshold are **chosen, not measured** and join the derived register; a runner-tunable threshold was deliberately not exposed. § 82 unchanged: nothing here has run on silicon.

**The config page ping-pongs, because one erase held every setting the runner had (2026-08-02).** § 451 declined ping-pong for the `RCF1` record and named why the page needed it anyway: a brown-out inside the 85 ms erase in front of `rewrite_config_page` lost the GNSS mode, the BLE bond, the marked waypoints, the ICE card, the composed screens, the armed timer and the race config **at once**, because one page held all seven and every rewrite blanked it whole. There are now **two** 4 KiB config pages (`memory.x` / `memory-ble.x` carve out 8 KiB; the run-store base at `0xFC000` and every slot offset are byte-identical, the pages sit at `0xFA000`/`0xFB000`). A rewrite takes the page that is **not** live and writes a `PGN1` generation seal into its **last word, after every record** — so an interruption anywhere in the erase or the writes behind it leaves an unsealed page that `live_config_page` skips whole, and the runner keeps the settings they had. The per-record CRCs already cover a torn record; what the seal adds is "all of them landed", which is the only thing a page of independent records cannot say about itself. **The selector asks which generation is the other's successor, not which is greater** — a `>` on a wrapping counter reads the `u32::MAX → 0` roll backwards and would hand a race the settings from before it; a successor test is an equality on a wrapping difference and needs no epoch or half-space convention (§ 451's own reason for comparing bytes for equality, applied to the counter). A pair where neither succeeds the other is a state this writer cannot produce; it resolves to page 0 rather than to "no config", because answering *none* would send the next write to page 0 at generation 0 and leave the same undecidable pair forever — the store would silently stop persisting. `plan_factory_erase` grew to cover **both** pages: the superseded one still holds a full previous copy of every record, the bond's long-term key included, and its own host test walks every record offset on every page. Host sweep **2269 → 2280**, plus three new property tests — the interleaving one drives arbitrary rewrites and torn erases against both pages as raw bytes and demands the read always be the newest config that actually completed and has not been erased since, and it **finds the wrap on its own**: mutating the selector to `>` fails it with the minimal input `start_generation = u32::MAX`. **Sim-verified only for the alternation.** The `idle` scenario walks the GNSS ladder and reads the driver's own seal line back, asserting each rewrite lands on the other page at the next generation (`p0@g0 -> p1@g1`); mutating the planner to keep the live page fails it naming the erase. That the mechanism WORKS is not sim-verifiable at all — Renode's flash is plain memory behind an SVD-derived NVMC model that swallows `ERASEPAGE`, so a torn erase cannot be staged there. A real torn write is a **bench** item (`quality_standards.md` step 7): pull power inside a settings write and confirm the previous page reads back. All nine scenarios green. § 82 unchanged.

**Every refused push says so, on the wrist and to the phone (2026-08-03, [§ 464](../../docs/architecture/decisions.md), issue #664).** All five phone→watch pushes are latest-value, so a refusal leaves the PREVIOUS value armed — and only `course` had ever said so. `workout`, `roadbook`, `screens` and a settings queue with no room reached a `warn!` down a debug cable no runner carries, so a phone re-pushing a corrected roadbook mid-race that failed CRC left the runner racing the old cut-offs while the phone said "sent". Every outcome now funnels through one `state::note_push` seam — the radio task's five characteristics *and* the sim's UARTE1 settings path — stamping a `ble_sync::PushOutcome { seq, kind, accepted }` the recorder mirrors and the alert engine edge-detects into `! SET / CRS / WKT / SCR / RBK FAIL`, § 400's `! CRS FAIL` generalised rather than copy-pasted four times (an accepted push stays silent). The phone gets the same verdict off a **ninth characteristic, `push_status` (`..e9`, read-only)**: `writeCharacteristicWithResponse` is answered by the SoftDevice before this task's handler decides anything, so its "sent" was a transport fact and never an application one. `WatchSyncClient` samples the sequence before its writes and polls it after, throwing `WatchPushRejected` on a refusal and leaving silence *unconfirmed* rather than failed. Host-tested both sides + build-verified on the `ble` feature set; the radio half can never be sim-verified (no SoftDevice under Renode, § 210), and only the sim's UART settings refusal runs today.

**A dead guest is named as one, and a fault can speak before it halts (2026-08-11, [§ 582](../../docs/architecture/decisions.md), issue #754).** The `storm` scenario went red on a PR touching no firmware and reported `expected the tracker's first measured tendency … no decoded log line matched`, which reads as a storm-classifier regression. It was not one: the executor had **stopped** at t≈19 s — the log ends mid-run, Renode goes silent for the remaining 287 s, and `dev-blink`'s LED stops with everything else — and the harness spent its whole 300 s budget blaming whichever assertion held the wait. `LogTail` now measures how long the decoded stream has gone without growing and reports a **WEDGED GUEST** instead, naming the last line (which carries the firmware timestamp the hang has to be read against). The measure is on the **wall** clock, deliberately the opposite of `GNSS_SILENCE_S` and `dropout`'s void reasoning: a guest that stops executing stops stamping lines, so its virtual clock freezes with it and can never notice its own death. The threshold is measured, not chosen — the widest gap between consecutive decoded lines across all nine scenarios is **1.01 s** (the baro task's 1 Hz tick, holding through `idle` at 138 s and `dropout` at 120 s), so `GUEST_WEDGED_S = 90` is ~90x that, with a second check at the deadline (`LINE_CADENCE_S = 5`) for waits too short to reach it. Six host tests drive it against a synthetic stream and a fake clock — including the half that matters most, that a **live** stream failing a claim still reports a real assertion failure — and they run in `build-firmware`, so a harness regression fails in ~90 s rather than behind a 14 min emulation. Both sim jobs now stage the **firmware ELF** into the artifact directory (#754's symbols had to be resolved against a locally rebuilt binary and hoped to match), and `HardFault` reports its stacked `pc`/`lr`/`psr` before halting rather than spinning in cortex-m-rt's silent default — it halts because a reset boots a clean watch and erases the evidence. **That handler would not have caught #754**: Renode returns 0 for reads outside any modelled peripheral and keeps going, so the corruption there never raises a fault. It is for the bench. All three feature sets green on `clippy -D warnings`; the `screens` and `storm` scenarios re-run green under the changed harness. No firmware behaviour moved and § 82 is unchanged — **#754 itself remains open and unfixed**, since the corrupting write is still unidentified.

**The `Watch` panic is made to name itself (2026-08-11, [§ 583](../../docs/architecture/decisions.md), issue #713).** `RefCell already mutably borrowed` is raised inside `embassy_sync::watch`'s generic code, and all 37 `Watch`es in `state.rs` monomorphise through that one line — so it names a source location and never which `Watch`, nor whether the flag held a legitimate count or something that was never one. Those are the two live readings (logic bug vs #754's corruption) and they need different evidence. Twelve local repro attempts came back clean against a CI rate near 1 in 30, so the firmware is made to explain itself on the next natural occurrence instead. `panic_probe` is **replaced** (a `#[panic_handler]` is singular): the message still contains "panicked" — the substring `ci_smoke.py` scans for — the halt is still a halt, and `state::dump_watches` adds three words per `Watch` with interrupts masked first. **The first attempt destroyed its own evidence**: dumping every byte overran defmt-rtt's ring, 5 of 38 lines survived, and the casualty was the `panicked` line itself — which would have turned a panic into a scenario failing on an unrelated assertion, the misattribution § 582 exists to stop. Hence three words, and the message emitted **last**, since under an overwriting ring the last line is the one that survives (bad version: 5 lines, no `panicked`; current: 37 and one). Which three words is an honest hedge — the flag is `Cell<isize>` beside an align-8 `WatchState`, so first-word and last-two-words cover both layouts; a quiescent dump reads `0x00000000` first for all 37, consistent with flag-at-offset-0 but not proof. `sim/test_watch_dump.py` fails if a `Watch` is declared and not listed, verified to fail as well as pass. All three feature sets green on `clippy -D warnings`; smoke scenario green, its "no firmware panic" assertion included. **#713 remains open** — this diagnoses, it does not fix.

**The sim's RTC counted time the guest had not started it for (2026-08-18, [§ 666](../../docs/architecture/decisions.md), issue #788).** The `pages` scenario went red on every CI run, wedged before the firmware's first log line with `PC = 0x1a000`. Disassembling the CI job's own uploaded ELF at that address settles what the symbol could not (`embassy_nrf::init` inlines into the main task's `poll`, so `FindSymbolAt` names the task): `ldr r2, [r1]` / `cmp r2, #0` / `bne` with `r1 = 0x40011504`, RTC1's COUNTER — embassy-nrf's `RtcDriver::init` spin, `tasks_clear; tasks_start; while counter != 0 {}`. That ELF **reproduces the wedge on arm64 macOS**, so the failure was never a property of the CI host; it is a property of the binary. Instrumenting the model measured why: `TASKS_START` lands at virtual time `0.001000000 s`, the COUNTER read one instruction later at `0.001065330 s`. Renode grants the CPU a quantum and folds the executed slice into the clock source only when the CPU reports, so the RTC — enabled part-way through that slice — is credited with the whole 65.33 us of it, two 32768 Hz ticks. The spin then does not recover on the next read: it waits for the 24-bit counter to wrap, 2^24 / 32768 = **512 s**, past every budget in the job. Whether the slice happens to be under one 30.5 us tick depends on how many instructions a build spends before RTC init, which is why one ELF booted everywhere and the next wedged everywhere. `sim/NRF52840_RTC_Overflow.cs` now syncs the CPU's executed-but-unreported time into the clock source before START / STOP / CLEAR / TRIGOVRFLW touch the timers (`machine.SystemBus.TryGetCurrentCPU` + `cpu.SyncTime()`, the same idiom Renode's own `MAX32650_RTC` uses), so the counter starts at the instant the guest starts it. **The firmware was not changed**: that spin is upstream embassy-nrf's and it is correct against silicon — the model was wrong. Verified on the exact CI ELF: 3/3 `pages` runs pass at CI's `--budget 300`, and reverting only this file makes the same command wedge again at the same `PC = 0x1a000` with the same symbol. Every scenario re-run green.

**The battery gauge was reading a regulator, not the cell (2026-08-19, [§ 691](../../docs/architecture/decisions.md), issue #789).** § 294 sampled `saadc::VddInput` unconditionally, and § 316 recorded the consequence as "the gauge blanks across 4.2→3.6 V". It was worse than that. The nRF52840 has two supply paths: fed on VDD it runs in normal mode and the rail **is** the cell, but fed on VDDH it runs in high-voltage mode and VDD becomes the output of an internal regulator fixed by `UICR.REGOUT0` — so the SAADC read the same ~3.0 V at *every* state of charge, the plausibility band refused it, and the gauge was absent at all charge levels. High-voltage mode is not an exotic case here: it is exactly what SW9's Li-Po position selects, which is the configuration [`parts.md`](../../docs/custom_watch/parts.md) note 0 says the § 82 DoD run needs. The fix reuses a read the firmware already takes — `supply::report` reads `POWER.MAINREGSTATUS` at boot to warn about the 1.8 V logic level, and now returns the `watch_core::battery_sense::SupplySense` that read implies. Normal mode keeps `VddInput` at the driver's default gain 1/6 (3600 mV full scale); high-voltage mode takes `VddhDiv5Input` at **gain 1/2**, which is 1200 mV at the converter and therefore 6000 mV of VDDH — above VDDH's own 5.8 V absolute maximum, so this input cannot saturate anywhere the SoC is allowed to run, which is precisely the property whose absence was the bug (and it is four times the resolution of the default gain against a cell-sized rail). **Selecting rather than hard-swapping is the point**: an unconditional swap would make the DK's default USB/VDD position read a confident wrong number in place of the honest absent state it has today. The scale rides with the channel as one `SupplySense` value the task is handed, so a channel and a scale that disagree are not constructible. The plausibility band (3200..=4350 mV) and the discharge curve needed no change — 4200 mV already maps to 100 % — and the band's **upper** bound becomes reachable for the first time, refusing a ~5 V USB-fed VDDH rather than reading it as a cell. **Host-tested + build-verified** (+7 tests: a charger-fresh cell reads 100 %, the DK's regulated rail stays absent on either sense, VDDH's operating and absolute maxima cannot rail, the codes either side of both band edges, monotonicity over every code from empty cutoff to full charge; `watch_core` 2349 lib tests; default + `ble` + sim builds and all three clippy gates green). The Renode `smoke` scenario is green and its POWER model happens to report high-voltage mode, so the sim does exercise the new branch and the task still parks cleanly on it — but the SAADC has no model, so **nothing here is sim-verified about the reading itself, and the on-silicon figure is a bench item** ([`quality_standards.md`](../../docs/custom_watch/quality_standards.md), issue #597).

**The GPS link got DMA depth, and the simulator got the UARTE event provider it never had (2026-08-19, [§ 698](../../docs/architecture/decisions.md), issue #789).** `gps.rs` re-armed one 32-byte EasyDMA read, which fills in 8.3 ms at 38400 and then leaves the receiver disarmed until a task runs again — against a ~85 ms NVMC page-erase CPU halt that cannot be divided (§ 419), i.e. up to 326 bytes of NMEA per checkpoint, an L4 flash write degrading L1 distance. `BufferedUarte`'s ENDRX -> STARTRX PPI chain keeps the next transfer armed in hardware, so the halt costs nothing. The ring is **2048 bytes, derived**: the guaranteed headroom is `half_len`, so 1024 B = 267 ms at this baud against one 85 ms erase, where the 512 bytes § 420/§ 421 specified buys 66.7 ms and covers none — right at 9600, wrong by 4x after § 622. Peripherals (TIMER2 + PPI 2/3 + PPI group 0) are claimed in the board crate beside UARTE1's TIMER1 + PPI 0/1, all outside the S140's TIMER0 / PPI 17-31 / group 4-5 reservations; the board crate's header now states the budget in one place. **§ 421's SHORTS timer turned out to be necessary and not sufficient, and only running it showed that**: Renode's PPI casts the peripheral owning an event address to `INRFEventProvider`, v1.16.1's `NRF52840_UART` does not implement it, and so *every* PPI channel sourced from a UARTE event was refused at configuration time — including the one whose count **is** the ring's write index. The same error sits in a run of unmodified `main` for UARTE1, so § 420's hardware idle chain has never fired under the sim either and the software gap timeout was carrying the settings pipe alone. `sim/NRF52840_UARTE_Events.cs` is the v1.16.1 model plus upstream's own event-provider delta, plus one fix: v1.16.1 never disarms the receiver at RXD.MAXCNT, so once the guest clears ENDRX the RX pointer walks past the driver's buffer without limit. That corruption is what killed the first attempt, and it presented as `RefCell already borrowed` inside `embassy_sync::watch` — **issue #713's signature, reproduced deterministically for the first time**, which makes it a mechanism candidate for #713 rather than a diagnosis of it. Evidence: host suite unchanged and green, all three feature sets build clippy-clean, **all nine Renode scenarios pass** (`smoke` / `dropout` / `workout` are the three that drive this path hardest). Bench-verified: nothing — see the step-7 residual-stall item in [`quality_standards.md`](../../docs/custom_watch/quality_standards.md), whose pass criterion is unchanged and whose expectation moves from "up to 326 bytes lost" to zero.

**Two wire formats moved, and a missing parity arm turned up under a filing that named the wrong symbol (2026-09-03, [§§ 1026-1030](../../docs/architecture/decisions.md), issue #789).** `TRK1` v5 stores a track point's altitude in **whole metres**: the decimetre `i16` capped at 3276.7 m while `elevation::plausible_alt` admits to 9000 m, so 69 % of a Silverton-Handies-Silverton profile stored no elevation and — because the gain rule carries the last reading across a dropout — the summit push netted to zero vert. Same two bytes, same layout, same CRC window, so `MIN_FORMAT_VERSION` stays 3 and the unit resolves per header version through `run_store::ele_metres`; the phone's ceiling moved with it, which is the half nothing could see, since this format flows watch->phone and each suite pinned only its own end. `RBK1` v2 carries a per-checkpoint `target_elapsed_s` + verdict (both-or-neither, `MIN_ROADBOOK_FORMAT_VERSION` 1 so an un-updated phone still loads a schedule) and the Roadbook glance renders a signed glyph per row plus the next target's time — the number behind the glyph, because a verdict a runner cannot check is not a feature. `isTrackRenderable`'s 5 m gate is now named on the web and Dart rails too, so the three-rail registry can hold it. And the port sweep's `plan_replan`-is-missing-`easeOffNextWeek` filing was half wrong in a useful direction: the rules were inlined and present, while `plan_adaptive_replan`'s "faithful" P2 gate had silently omitted web's **deload override** — the one arm where the runner is at genuine risk. `segments` gained the batched effort walk (the per-slice loop re-sorted a 512-element array 64 times for an answer that does not depend on the slice) and a recorded exclusion for the catalogue matcher no frame delivers. Host-tested + build-verified across all three feature sets; no bench claim moved.


## Layout

Actual workspace shape (Cargo workspace, all paths relative to `apps/custom_watch/`):

```
Cargo.toml              workspace root
rust-toolchain.toml     pins a recent stable Rust + thumbv7em-none-eabihf target
.cargo/config.toml      runner = probe-rs, default target, defmt log level
app/
  Cargo.toml
  src/
    main.rs             #[embassy_executor::main] entry, spawns tasks
    state.rs            the embassy-sync Watches / Channels the tasks publish through
    run_flash.rs        internal-flash run store + config-page driver (README step 7)
    supply.rs           boot-time supply-mode report (decisions.md § 626)
    tasks/
      gps.rs            GNSS NMEA parser task
      hr.rs             MAX30101 sampling + peak-detect task
      baro.rs           BMP581 sample task (per decisions.md § 90)
      battery.rs        SAADC battery-voltage task (VDD or VDDH/5 per supply mode, probe-and-park)
      nav.rs            per-fix course projection + off-course latch
      ui.rs             screen update + liveness-LED task
      button.rs         edge detection + debounce, feeding the § 350 press grammar
      phone.rs          UARTE1 phone link: status frames out, SET1 frames in
      ble.rs            GATT server + sync task
      record.rs         recording state machine (port of Dart run_recorder)
core/                  watch_core: hardware-free app logic (face, record, gauge, statusbar, bar_chart, ...)
render/                watch_render: host-testable face-widget drawing over the sharp_mip framebuffer
drivers/
  sharp_mip/            Sharp Memory LCD driver crate
  ublox_nmea/           u-blox NMEA parser crate (no_std)
  max30101/             MAX30101 register-level driver — TIER 1's optical HR (decisions.md § 623)
  max86177/             MAX86177 register-level driver — the PRODUCTION AFE, kept as a head start;
                        its register map is NDA-modelled and no silicon has answered it
  bmp581/               Bosch BMP581 barometer driver crate
boards/
  nrf52840_dk/          board-support crate: pinmux, peripheral assignments
sim/                   Renode machine script + peripheral models (TWIM, MAX30101, BMP581, Sharp MIP, RTC)
                       + NMEA fixtures + the ci_smoke.py scenarios
```

This is intentionally close to the per-task / per-driver split that the Zephyr-flavoured proposal in [`docs/custom_watch/firmware.md`](../../docs/custom_watch/firmware.md) uses — so the firmware architecture stays portable across the language choice. If we ever revert to C/Zephyr per the §80 fallback, the task boundaries map directly onto Zephyr threads + work queues.
