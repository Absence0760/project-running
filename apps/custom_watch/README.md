## Power discipline

Per [`performance_path.md`](../../docs/custom_watch/performance_path.md), battery life is decided by **hardware** (Sharp MIP vs AMOLED ~3–4×, Ambiq vs nRF52 MCU ~25×, snapshot GNSS ~2–3×) — all tier-2 chip swaps — and the nRF52840 **dev kit can't measure ultra-watch power at all** (~30 mA idle from the onboard debugger). So tier-1's job is not a measured number; it's getting the **firmware architecture** right so the wins land at tier-2: DMA/interrupt-driven I/O, a tickless async runtime, aggressive sleep where every wake is justifiable, partial display updates, and a clean always-on/screen-on split. What that translates to in this workspace:

**Done:**
- **Partial display updates** — the `sharp_mip` driver tracks dirty lines and sends only changed ones (+ the VCOM-only frame when idle); a static screen costs near-nothing.
- **DMA/async, tickless** — every task is Embassy async over EasyDMA (no busy-polling), so the executor sleeps until a real event. **GPS UART reads are burst-buffered** (`gps.rs`, `RX_BURST`) — one CPU wake per ~32 bytes instead of per byte, the doc's DMA-not-polling lever (sim-verified: 53 fixes / 51 s, distance accrues).
- **Animations gated** — the ~1 Hz face animations freeze outside an ~8 s post-interaction window (`ANIM_WINDOW_S`), so an unattended wrist stops the per-second decorative redraw.
- **No gratuitous wakers** — the 2 Hz liveness LED is behind the default-OFF `dev-blink` feature (the sim/flash helpers opt it back in); a plain `cargo build` carries no free-running blinker.
- **BLE long connection interval** — the `ble` build requests a ~1 s interval on connect (`set_conn_params`), vs the 7.5 ms HID default (~100× idle-radio power). Compile-verified only.
- **Hardware EXTCOMIN VCOM** — EXTMODE held high + a free-running ~3.8 Hz PWM on EXTCOMIN (`ui::vcom_task`) drive the panel's bias inversion in hardware, so the display driver (`SharpMip::new_external_vcom`) never toggles the software VCOM bit and never sends a VCOM-maintenance frame: a clean framebuffer now flushes **zero SPI**. This removes the display's standing reason for the CPU to wake every second. Sim-verified to boot + init the PWM + still render the dashboard; the EXTMODE/EXTCOMIN wiring itself is bench-gated (some breakouts strap EXTMODE — confirm on the real panel).
- **Idle CPU-sleep** — building on hardware VCOM: the screen task is **event-driven** (it waits on the state Watches and re-renders only on a change, with a short tick only while animating or watching a fresh fix go stale, else a 30 s heartbeat); the idle-face title row is **static** (no ticking uptime); and the record task **drops its 1 Hz tick while idle/finished** and publishes a snapshot only when it changed. So a resting recorder wakes nothing downstream, and with no sensor events the CPU sleeps seconds apart instead of every second. Sim-verified: recording still drives the dashboard through events — the elapsed hero advances and distance accrues with no per-second timer.
- **GPS fix de-rate while idle** — the `gps` task now watches `state::RECORD` and, while **no run is active**, forwards at most one fix per `IDLE_FIX_MIN_INTERVAL_S` (held one second under the face's `STALE_AFTER_S` freshness budget) instead of every ~1 s fix. A moving idle position used to wake the UI, record, and phone consumers every second for a view nobody is recording; a run (Recording/Paused) lifts the throttle and gets every fix. This is the *software* half of GPS duty-cycling — it cuts the downstream wakes, not the UART stream itself. Sim-verified both ways: the idle (no-autostart) build publishes fixes ~4 s apart with the position still advancing (face stays fresh, never falsely "searching"), while the recording build gets full-rate fixes and distance accrues normally.
- **Selectable GNSS recording modes** (2026-07-10) — the de-rate above, generalised into the mode surface every ultra watch ships: `watch_core::gnss_mode` defines **Performance / Balanced / Expedition** (every ~1 s fix / one per 15 s / one per 60 s — the UltraTrac / UltraMax class), each with a *projected* battery-hours figure (~110/~180/~220 h; a derivation in the module docs, not a measurement — the DK can't measure power). **BTN3 cycles the mode on the idle face** (`MODE PERF ~110H` row; mid-run BTN3 stays on pages via the host-tested `btn3_action`, so a run's mode is frozen), the gps task forwards fixes at the mode's cadence while recording, the recorder's jump gate scales to the interval (`MAX_SPEED_MPS * dt` past 1 s — a fixed 100 m ceiling would reject every legitimate ~240 m Expedition leg; the 1 Hz filter is unchanged), and the face's staleness budget stretches to the cadence (`face::stale_after_s`) so a 40 s-old Expedition fix reads `SATS`, not `STALE` — run-view GPS rows carry the mode tag. Sim-verified with `bin/watch-sim.sh --no-autostart` (boot idle, cycle the mode, BTN1 to start): forwarded-fix cadence measured ~1 s / ~15 s / ~60 s per mode with distance accruing in all three. Still only the *software* half — the tier-2 receiver power-down below is where the mode's real battery win lands.

**Architecturally owed (tier-1 wins, but hardware-gated or behaviour-changing — not yet built):**
- **GNSS power-down between fixes** — the fix de-rate / recording modes above throttle *publication*; the module's UART still streams and the CPU still wakes per burst to drain it. The deeper win powers the GNSS down (u-blox power-save / backup mode, or a load switch) between the selected mode's fixes and wakes it on demand — a behaviour/mode change plus module power/wake wiring that the Renode sim can't model, and the tier-2 snapshot-GNSS lever. The `gnss_mode` surface is the user-facing half this plugs into; its projected battery figures assume this lever lands. Same shape as HR duty-cycling below.
- **HR duty-cycling** — sample HR a few seconds per minute rather than 100 Hz continuously (the LED current dominates HR power); a mode/fidelity trade to make deliberately.
- **Always-on / screen-on split for tier-2** — the sensor tasks are already isolated per subsystem, the boundary a coprocessor (Apollo510B network core / BHI260) slots into at tier-2.

## Local testing

The watch's developer inner loop is `bin/watch-flash.sh` from the repo root (or `cargo run --release` from this directory): build the firmware, flash it to a connected Nordic nRF52840 DK, stream `defmt` logs back to your terminal until Ctrl-C. Host-side unit tests run via `bin/watch-test.sh` or `cargo test` and don't need a board. Run `bin/watch-doctor.sh` once per machine to verify toolchain + board detection. No board at all? `bin/watch-sim.sh` boots the same release ELF on an emulated nRF52840 DK (Renode) with decoded defmt logs streaming and a canned NMEA fixture feeding the GPS UART — the whole boot + blink + task-scheduling path runs today, pre-parts ([decisions.md § 208](../../docs/architecture/decisions.md#208-firmware-simulation-runs-the-unmodified-elf-on-renode-with-a-custom-defmt-rtt-drain)). See [`local_testing.md`](local_testing.md) for the full setup walkthrough, the host-vs-on-target-vs-sim testing split, and the common-error reference.

On real hardware BTN1 is the only start path; the old "auto-start on the first fix" stand-in lives behind the **default-OFF `sim-autostart` Cargo feature** so the sim records without needing a button. Manual lap is sim-verified through that path (2026-07-09): `runMacro $btn4` lands `button: Lap -> Lap` → `record: command Lap`, and cycling BTN3 to the Lap page renders it on the emulated panel. The hardware build keeps the low-power SENSE path untouched. The barometer is wired too — the `baro` task drives the **BMP581** (`drivers/bmp581/`, 5 host tests) over TWISPI1 through the same async probe guard, feeding `watch_core::elevation` (barometric altitude + cumulative-vert accumulator) and publishing a snapshot to `state::ELEVATION`. That snapshot is now surfaced end-to-end: the status face prefers the barometric altitude for its ALT row and adds a cumulative-vert line (`VERT +gain -loss`), and the phone-link status frame carries an additive optional `"elev":{alt_m,gain_m,loss_m}` object (schema still `"v":1`, `null` when the baro is absent) that the mobile dev Sim Watch screen decodes and displays. **Run sync (firmware half) is now wired.** The record task captures the GPS *track*, not just totals: on start it opens a `run_store::RunWriter` over a slot-sized RAM staging buffer, `push_point`s each fix the recorder accepts as a new anchor (the added host-tested `Recorder::last_fix_stored` signal, so stored points mirror the acceptance filter exactly) stamped with the latest HR (`state::HR`) + barometric altitude (`state::ELEVATION`), and on stop finalizes the blob with the snapshot totals and commits it to internal flash. `app/src/run_flash.rs` is the flash driver — a `FlashSink` (`run_store::ByteSink`) over embassy-nrf's NVMC plus a `RunStore` (commit / manifest / read_chunk) over the host-tested `watch_core::flash_store` slot layout: **4 slots × one 4 KiB erase page, reserved at the top of flash in both `memory.x` and `memory-ble.x`** (FLASH shrunk by 16 KiB; the region addressed by absolute offset `0xFC000`). It is **best-effort / L4** — it probes for the NVMC controller once at boot and no-ops every op if it's absent, and any flash error only `warn!`s, so recording is never blocked on flash. The **per-run point cap is 253** (`HEADER + 253·POINT + FOOTER ≤ 4096`): a few minutes at ~1 accepted fix/s. A full ultra needs the tier-2 external QSPI flash; the internal-flash store is a bench-prototype foundation, not shipping capacity. The default (sim) build boots + records unchanged (verified: distance accrues over 30 s, no panic/hang; Renode does model NVMC). With the `sim-buttons` feature the sim can now also **stop** a run (`runMacro $btn2`) — verified to drive the recorder to `Finished`, which runs the `commit` path (a clean end-to-end flash-write capture is still owed). On the **`ble`** build the same Threkir GATT service now carries `run_manifest` (read + notify: `ManifestHeader` + one `ManifestEntry` per finished run) and `run_chunk` (write + notify: the phone writes a `ChunkRequest {run_seq, offset, len}`, the watch notifies back that slice of the blob clamped to the notify MTU + blob end) — the protocol of [firmware.md § Sync protocol](../../docs/custom_watch/firmware.md), live link preserved. Like step 6 this **compiles + links but has never run on hardware**; additionally, with the SoftDevice enabled the NVMC backend must be swapped for `nrf_softdevice::Flash` (SoftDevice-coordinated flash) before real use — see the caveat in `app/src/run_flash.rs`. Reboot-persistence of the slot directory is now **wired (2026-07-10)**: `RunStore::new` scans every slot's flash bytes at boot via the host-tested `flash_store::recover_slot`, rebuilding the directory from the finished blobs already on flash so a run recorded in a prior power cycle is re-advertised instead of being lost until its slot is overwritten. Because the blob doesn't store its own length, the footer is located by scanning point-aligned offsets for the footer magic **plus** a CRC32 that verifies the header+points prefix — the CRC is what makes a stray footer-magic inside track data safe (10 new host tests, incl. the decoy-magic case + erased/truncated/newer-version rejection). `SlotDir::next_run_seq` resumes numbering above the highest recovered seq so a fresh run can't reuse a recovered id, and the record task seeds its counter from it. The core scan + directory rebuild is host-tested; the `app/` flash-read side (`recover_dir`) is best-effort / L4 and, like the rest of the driver, compile-verified only until the dev kit lands. **The phone half is now built too** (decisions §211): `apps/mobile_android/lib/sim_watch_sync.dart` is a Dart mirror of `run_store` — it pulls the manifest, reassembles chunks, `verify_blob`s each run (pinned to the SAME golden vector as the Rust `run_store` test, so the two can't drift), reshapes it into the payload the existing `WatchIngestQueue` / `runFromWatchPayload` → `api.saveRun` path already uploads, and delivers it via `WatchSyncClient` behind an injectable transport seam (production impl over the sanctioned `flutter_reactive_ble`). A dev-gated "Sync runs" action on the Sim Watch screen drives it; the pull→decode→verify→deliver path is unit-tested without a radio. What remains is purely on-hardware: exercising the real SoftDevice + NVMC-vs-`nrf_softdevice::Flash` path, and bench-confirming the boot-time slot recovery reads back real committed blobs — both pending the dev kit.
8. **Fabricate the tier-1 enclosure** — once the integrated unit records a run, 3D-print a chassis that holds the breakout boards + LiPo together and takes a Velcro strap, so it can be worn for a test jog. **FDM (any hobby printer / Shapeways / JLCPCB 3D) is the intended method here, ~$0–50 per print** — see [`parts.md`](../../docs/custom_watch/parts.md) (optional-tools table) and the tier-1 deliverables in [`prototyping.md`](../../docs/custom_watch/prototyping.md#tier-1--bench-prototype-5002k-36-months). This is a *functional chassis to hold breakouts*, **not** case CAD / industrial design / a sealed enclosure — those are tier-2+ and stay gated on the §71 triggers (see [`CLAUDE.md`](CLAUDE.md)). A printed case is not water-resistant and will not pass IPX7 (that needs injection-moulded tooling + a gasket, a tier-2/3 line item).

## Layout

Actual workspace shape (Cargo workspace, all paths relative to `apps/custom_watch/`):

```
Cargo.toml              workspace root
rust-toolchain.toml     pins a recent stable Rust + thumbv7em-none-eabihf target
.cargo/config.toml      runner = probe-rs, default target, defmt log level
app/
  Cargo.toml
  src/
    main.rs             #[embassy_executor::main] entry, spawns tasks
    tasks/
      gps.rs            GNSS NMEA parser task
      hr.rs             MAX86177 polling + naive peak-detect task
      baro.rs           BMP581 sample task (per decisions.md § 90)
      ui.rs             screen update + button-handler task
      ble.rs            GATT server + sync task
      record.rs         recording state machine (port of Dart run_recorder)
core/                  watch_core: hardware-free app logic (face, record, gauge, statusbar, bar_chart, ...)
render/                watch_render: host-testable face-widget drawing over the sharp_mip framebuffer
drivers/
  sharp_mip/            Sharp Memory LCD driver crate
  ublox_nmea/           u-blox NMEA parser crate (no_std)
  max86177/             MAX86177 register-level driver + bindgen wrapper for the HR algorithm
boards/
  nrf52840_dk/          board-support crate: pinmux, peripheral assignments
```

This is intentionally close to the per-task / per-driver split that the Zephyr-flavoured proposal in [`docs/custom_watch/firmware.md`](../../docs/custom_watch/firmware.md) uses — so the firmware architecture stays portable across the language choice. If we ever revert to C/Zephyr per the §80 fallback, the task boundaries map directly onto Zephyr threads + work queues.
