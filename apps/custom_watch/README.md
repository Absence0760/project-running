## Power discipline

Per [`performance_path.md`](../../docs/custom_watch/performance_path.md), battery life is decided by **hardware** (Sharp MIP vs AMOLED ~3–4×, Ambiq vs nRF52 MCU ~25×, snapshot GNSS ~2–3×) — all tier-2 chip swaps — and the nRF52840 **dev kit can't measure ultra-watch power at all** (~30 mA idle from the onboard debugger). So tier-1's job is not a measured number; it's getting the **firmware architecture** right so the wins land at tier-2: DMA/interrupt-driven I/O, a tickless async runtime, aggressive sleep where every wake is justifiable, partial display updates, and a clean always-on/screen-on split. What that translates to in this workspace:

**Done:**
- **Partial display updates** — the `sharp_mip` driver tracks dirty lines and sends only changed ones (+ the VCOM-only frame when idle); a static screen costs near-nothing.
- **DMA/async, tickless** — every task is Embassy async over EasyDMA (no busy-polling), so the executor sleeps until a real event. **GPS UART reads are burst-buffered** (`gps.rs`, `RX_BURST`) — one CPU wake per ~32 bytes instead of per byte, the doc's DMA-not-polling lever (sim-verified: 53 fixes / 51 s, distance accrues).
- **Animations gated** — the ~1 Hz face animations freeze outside an ~8 s post-interaction window (`ANIM_WINDOW_S`), so an unattended wrist stops the per-second decorative redraw.
- **No gratuitous wakers** — the 2 Hz liveness LED is behind the default-OFF `dev-blink` feature (the sim/flash helpers opt it back in); a plain `cargo build` carries no free-running blinker.
- **BLE long connection interval** — the `ble` build requests a ~1 s interval on connect (`set_conn_params`), vs the 7.5 ms HID default (~100× idle-radio power). Compile-verified only.
- **Hardware EXTCOMIN VCOM** — EXTMODE held high + a free-running ~3.8 Hz PWM on EXTCOMIN (`ui::vcom_task`) drive the panel's bias inversion in hardware, so the display driver (`SharpMip::new_external_vcom`) never toggles the software VCOM bit and never sends a VCOM-maintenance frame: a clean framebuffer now flushes **zero SPI**. This removes the display's standing reason for the CPU to wake every second. Sim-verified to boot + init the PWM + still render the dashboard; the EXTMODE/EXTCOMIN wiring itself is bench-gated (some breakouts strap EXTMODE — confirm on the real panel).
- **Idle CPU-sleep** — building on hardware VCOM: the screen task is **event-driven** (it waits on the state Watches and re-renders only on a change, with a short tick only while animating or watching a fresh fix go stale, else a 30 s heartbeat); the idle-face title row is **static** (no ticking uptime); and the record task **drops its 1 Hz tick while idle/finished** and publishes a snapshot only when it changed. So a resting recorder wakes nothing downstream, and with no sensor events the CPU sleeps seconds apart instead of every second. Sim-verified: recording still drives the dashboard through events — the elapsed hero advances and distance accrues with no per-second timer.
- **GPS fix de-rate while idle** — the `gps` task now watches `state::RECORD` and, while **no run is active**, forwards at most one fix per `IDLE_FIX_MIN_INTERVAL_S` (held one second under the face's `STALE_AFTER_S` freshness budget) instead of every ~1 s fix. A moving idle position used to wake the UI, record, and phone consumers every second for a view nobody is recording; a run (Recording/Paused) lifts the throttle and gets every fix. This is the *software* half of GPS duty-cycling — it cuts the downstream wakes, not the UART stream itself. Sim-verified both ways: the idle (no-autostart) build publishes fixes ~4 s apart with the position still advancing (face stays fresh, never falsely "searching"), while the recording build gets full-rate fixes and distance accrues normally.
- **HR duty-cycling** (2026-07-18) — the MAX86177 samples continuously in Performance but 15 s per 60 s / 120 s window in Balanced / Expedition (`watch_core::hr_duty`, windows phase-locked to uptime-period boundaries; the constants are derivations, not measurements — the DK can't measure power, and the saving is deliberately NOT folded into `gnss_mode`'s battery projections until a PPK2 exists). Between windows the part goes into `shutdown()`; window-open `wake()` flushes the FIFO so pre-shutdown counts can't replay, and the detector resets. Honest bounded staleness everywhere the reading flows (`hr_duty::shown_bpm`): the face blanks to `--` after one full period (Performance keeps the ordinary 5 s budget — which also fixed a latent freeze-forever on a wedged bus), zone-time banking stops at the same budget, and track-point `bpm` stamps go empty rather than stale. A sensor that won't wake degrades to "no HR" for that window (L4). **Sim-verified 2026-07-19** against the new Renode MAX86177 model: six clean 15 s-on / 60 s-period Balanced cycles, the part really shut down and its FIFO frozen between them, flushed on every wake, the detector re-converging to the same BPM inside ~3 s, and the reading honestly held (not re-sampled) across an off-window — see `sim/verification-2026-07-19/`. The *power* saving itself stays a derivation, bench-gated like every other figure here.
- **Selectable GNSS recording modes** (2026-07-10) — the de-rate above, generalised into the mode surface every ultra watch ships: `watch_core::gnss_mode` defines **Performance / Balanced / Expedition** (every ~1 s fix / one per 15 s / one per 60 s — the UltraTrac / UltraMax class), each with a *projected* battery-hours figure (~110/~180/~220 h; a derivation in the module docs, not a measurement — the DK can't measure power). **BTN3 cycles the mode on the idle face** (`MODE PERF ~110H` row; mid-run BTN3 stays on pages via the host-tested `btn3_action`, so a run's mode is frozen), the gps task forwards fixes at the mode's cadence while recording, the recorder's jump gate scales to the interval (`MAX_SPEED_MPS * dt` past 1 s — a fixed 100 m ceiling would reject every legitimate ~240 m Expedition leg; the 1 Hz filter is unchanged), and the face's staleness budget stretches to the cadence (`face::stale_after_s`) so a 40 s-old Expedition fix reads `SATS`, not `STALE` — run-view GPS rows carry the mode tag. Sim-verified with `bin/watch-sim.sh --no-autostart` (boot idle, cycle the mode, BTN1 to start): forwarded-fix cadence measured ~1 s / ~15 s / ~60 s per mode with distance accruing in all three. Still only the *software* half — the tier-2 receiver power-down below is where the mode's real battery win lands.

- **GNSS power-down between fixes** (2026-07-19) — the deeper half of the recording modes above, closing the last architecturally-owed power lever: while a run is **Recording** in Balanced / Expedition, the gps task follows each published fix with **UBX-RXM-PMREQ** on UARTE0's TX (u-blox backup mode, bounded duration — the tier-1 software path; no load switch) and wakes the receiver with the 0xFF RX-activity byte a 5 s reacquire margin before the next fix is owed; the PMREQ duration is the self-wake backstop for a lost wake byte (never 0 — an unbounded sleep). The schedule is the pure host-tested `watch_core::gnss_power`, keyed to the last *published* fix rather than `hr_duty`'s uptime phase-lock (the publication throttle is publish-relative, so a boundary-locked wake could drift into its own reacquire margin and stay there, never sleeping again); the UBX encoder (`ublox_nmea::ubx`) is host-pinned to spec-derived byte vectors. Constants are derivations, not measurements — the DK can't measure power — and the mode's projected battery figures are untouched (they already assume this lever). Performance / idle / Paused keep the receiver on (the idle de-rate stays); a run-state change mid-window wakes it early; a failed PMREQ write leaves it on (L4 — status-quo draw, never a lost fix). Honest under a receiver that never sleeps: every fix the sim's PMREQ-ignoring feed delivers inside a window is one the publication throttle already drops (host-pinned), so sim and hardware publish identical sequences, and mid-window staleness reads through the existing `face::stale_after_s` budget. Sim-verified in Balanced (`--no-autostart`, BTN3 → BTN1): PMREQ after each published fix, wake byte on schedule, publications steady at ~15 s, and a confirmed BTN2 stop mid-window wakes the receiver immediately. The module's *actual* power state is bench-gated until the dev kit lands.

- **Always-on / screen-on split for tier-2** — the sensor tasks are already isolated per subsystem, the boundary a coprocessor (Apollo510B network core / BHI260) slots into at tier-2.

## Local testing

The watch's developer inner loop is `bin/watch-flash.sh` from the repo root (or `cargo run --release` from this directory): build the firmware, flash it to a connected Nordic nRF52840 DK, stream `defmt` logs back to your terminal until Ctrl-C. Host-side unit tests run via `bin/watch-test.sh` or `cargo test` and don't need a board. Run `bin/watch-doctor.sh` once per machine to verify toolchain + board detection. No board at all? `bin/watch-sim.sh` boots the same release ELF on an emulated nRF52840 DK (Renode) with decoded defmt logs streaming and a canned NMEA fixture feeding the GPS UART — the whole boot + blink + task-scheduling path runs today, pre-parts ([decisions.md § 208](../../docs/architecture/decisions.md#208-firmware-simulation-runs-the-unmodified-elf-on-renode-with-a-custom-defmt-rtt-drain)). The recorder also banks **HR zones + in-zone time** (2026-07-09): `watch_core::hr_zones` mirrors the main app's default five-zone %-of-max ladder (web `training/hr_zones.ts` canonical — 60/70/80/90/100 % upper bounds, inclusive boundaries, the legacy 190 bpm fallback; max HR is a plausibility-guarded `set_max_hr` hook for a future settings sync), and per-zone time accrues exactly where moving time does — manual pause, auto-pause, and a missing/dropped pulse (`set_hr`, fed by the record task from `state::HR`) bank nothing. The `Snapshot` carries the ladder + accumulators, run-view HR rows show the live zone (`152 BPM Z3`), and the fifth Zones glance page renders the breakdown (sim-verified 2026-07-19 with a **live** BPM now that the sim has a MAX86177 model: `72 BPM`, `ZONE 1`, `Z1 0:18` banked with Z2-Z5 at `0:00`; the honest no-HR zero state is still what an absent/off-wrist sensor shows). The recorder also carries an **even-pace virtual partner** (2026-07-10): `watch_core::pacer` defines a partner running a goal (distance + time) at perfectly even pace on the **elapsed** clock — a race clock doesn't stop at an aid station, so ahead/behind answers "will I cross the line by the goal time", the Garmin Virtual Partner semantics — and `Pacer::status` reduces the live totals into metres ahead/behind, the same delta as seconds at goal pace, a projected finish at the whole-run average, and an ahead / on-pace / behind verdict inside the app's shared ±5 % dead-band (the web `challenge_progress.ts` `ON_PACE_BAND` ratio rule, so the watch can't grade "on pace" differently than the app's challenge hint). It is **best-effort / L4** — it probes for the NVMC controller once at boot and no-ops every op if it's absent, and any flash error only `warn!`s, so recording is never blocked on flash. The **per-run point cap is 253** (`HEADER + 253·POINT + FOOTER ≤ 4096`): a few minutes at ~1 accepted fix/s. A full ultra needs the tier-2 external QSPI flash; the internal-flash store is a bench-prototype foundation, not shipping capacity. On the **`ble`** build the same Threkir GATT service now carries `run_manifest` (read + notify: `ManifestHeader` + one `ManifestEntry` per finished run) and `run_chunk` (write + notify: the phone writes a `ChunkRequest {run_seq, offset, len}`, the watch notifies back that slice of the blob clamped to the notify MTU + blob end) — the protocol of [firmware.md § Sync protocol](../../docs/custom_watch/firmware.md), live link preserved. Like step 6 this **compiles + links but has never run on hardware**; additionally, with the SoftDevice enabled the NVMC backend must be swapped for `nrf_softdevice::Flash` (SoftDevice-coordinated flash) before real use — see the caveat in `app/src/run_flash.rs`. Reboot-persistence of the slot directory is now **wired (2026-07-10)**: `RunStore::new` scans every slot's flash bytes at boot via the host-tested `flash_store::recover_slot`, rebuilding the directory from the finished blobs already on flash so a run recorded in a prior power cycle is re-advertised instead of being lost until its slot is overwritten. Because the blob doesn't store its own length, the footer is located by scanning point-aligned offsets for the footer magic **plus** a CRC32 that verifies everything up to that candidate footer's own CRC field — the CRC is what makes a stray footer-magic inside track data safe, and since run-store **v3** (2026-07-25, decisions §321) the colliding window includes the decoy's would-be totals, so the scan is harder to fool than it was (10 new host tests, incl. the decoy-magic case + erased/truncated/newer-version rejection). `SlotDir::next_run_seq` resumes numbering above the highest recovered seq so a fresh run can't reuse a recovered id, and the record task seeds its counter from it. The core scan + directory rebuild is host-tested; the `app/` flash-read side (`recover_dir`) is best-effort / L4 and, like the rest of the driver, compile-verified only until the dev kit lands. **The phone half is now built too** (decisions §211): `apps/mobile_android/lib/sim_watch_sync.dart` is a Dart mirror of `run_store` — it pulls the manifest, reassembles chunks, `verify_blob`s each run (pinned to the SAME golden vector as the Rust `run_store` test, so the two can't drift; **v3** widened that check to cover the footer's totals, so a blob is trusted whole or refused whole and the phone can no longer ingest a run whose summary bit-rotted, decisions §321), reshapes it into the payload the existing `WatchIngestQueue` / `runFromWatchPayload` → `api.saveRun` path already uploads, and delivers it via `WatchSyncClient` behind an injectable transport seam (production impl over the sanctioned `flutter_reactive_ble`). A dev-gated "Sync runs" action on the Sim Watch screen drives it; the pull→decode→verify→deliver path is unit-tested without a radio. What remains is purely on-hardware: exercising the real SoftDevice + NVMC-vs-`nrf_softdevice::Flash` path, and bench-confirming the boot-time slot recovery reads back real committed blobs — both pending the dev kit. Those items, and the rest of what this step has to demonstrate on silicon, are enumerated as pass/fail criteria in the step-7 section of [`quality_standards.md`](../../docs/custom_watch/quality_standards.md#tier-1-bench-verification-checklist) — work that checklist rather than re-deriving "what's left" from this paragraph. **Two recorded flash defects gate a clean bench run of this step**: an in-progress checkpoint is advertised as a finished run (`FLAG_FINISHED` is enforced by nothing), and `checkpoint()` erases its slot before rewriting it — see the 2026-07-25 entry in the chronology below.
8. **Fabricate the tier-1 enclosure** — once the integrated unit records a run, 3D-print a chassis that holds the breakout boards + LiPo together and takes a Velcro strap, so it can be worn for a test jog. **FDM (any hobby printer / Shapeways / JLCPCB 3D) is the intended method here, ~$0–50 per print** — see [`parts.md`](../../docs/custom_watch/parts.md) (optional-tools table) and the tier-1 deliverables in [`prototyping.md`](../../docs/custom_watch/prototyping.md#tier-1--bench-prototype-5002k-36-months). **Font `+` glyph fix + per-session sim pointer (2026-07-19).** The font bug two sim passes logged independently is closed, and the audit that came with it found a second glyph nobody had noticed. `scripts/gen_font.py` rasterised the glyph strip at 8x16 with no coverage information, so a stroke thinner than a device pixel vanished: `'+'` lost its vertical stem and packed byte-identical to `'-'` (the **Pacer** page's whole purpose is a signed `+0:42` / `-1:05` delta, and the idle face's `VERT +gain -loss` row lost its sign the same way), and `'|'` lost its stem too and packed **all-zero** — invisible, byte-identical to a space. The generator now re-rasterises colliding glyphs at 2x and averages back down, and fails loudly if a collision survives. It repairs only the **degenerate member** of a collision — candidates ranked by how much detail the 1x pass cost them, worst first, stopping the moment the group is pairwise distinct — because a collision has one guilty party and re-rasterising the innocent half is churn: at this cell size the 2x pass renders a hairline as two rows, so repairing `'-'` alongside `'+'` left the hyphen visibly heavier than the `'='` and `'_'` bars it sits beside. The repaired set is therefore exactly `'+'` and `'|'`; every other glyph, `'-'` included, stays bit-identical to the 1x pass. That loud-failure guard originally excused space on both sides — which is precisely why an all-zero `'|'` sailed through it — so space now participates: it is never the glyph re-rasterised, but anything else that packs blank collides with it and gets repaired. A new `drivers/sharp_mip/tests/font.rs` pins the invariants (the driver's `tests/driver.rs` stays about framebuffer semantics and wire encoding): `'+'` differs from `'-'` and carries a crossbar *plus* a stem that crosses it; `'|'` is a full-height stroke; `'='`, `'_'` **and `'-'`** are byte-for-byte what they were, so a repair can never quietly reshape a glyph that rasterised correctly; **no two printable chars share a bitmap, space included**; and `'+'` reads as a cross at 1x / 2x measured on the rendered framebuffer (`draw_text`, `draw_text_2x` pixel-replicate the one 8x16 glyph, so a correct glyph scales exactly; the 3x case was dropped 2026-07-22 with `draw_text_3x` itself, decisions §292). **Settings frame v3 — the CRC32 the format was missing (2026-07-25, decisions § 319).** The defect the property suite found above is fixed. `SET1` takes a third version byte and appends a four-byte little-endian **CRC32 trailer** over everything before it, reusing `run_store::crc32` (one checksum implementation in the firmware, the way `flash_store`'s config and bond records already share it) — the Dart encoder likewise reuses the `crc32` the run-store decoder already has. A mismatch rejects the frame outright, no partial apply, the same fail-closed rule as an unknown flag bit or a short buffer. Compatibility follows §293's v1→v2 precedent: `decode` still accepts v1 (no `flags2`) and v2 (no CRC) so an old phone's push keeps working, neither legacy golden moved, and neither was retro-fitted with a checksum it never carried; the encoder is **v3-only**, so every new push is checked. A fully populated frame grows 45 → 49 bytes and `MAX_SETTINGS_LEN` carries it into the GATT characteristic and the sim-link buffer. The `#[ignore]`d property is **un-ignored and passing** — deleting it was never on the table, it was the defect's only executable record. Alongside it, a host test builds the QNH→pages corruption and re-seals it under its own correct CRC to show the length check genuinely cannot catch it, then shows the same flip carrying the *sender's* CRC rejected; and the raw-frame generator seals v3 frames with their real checksum at any length, so the CRC never shadows the exact-length check underneath. `watch_core` 1379 host tests; default + `ble` + sim builds, `cargo fmt --check`, and the clippy gate green on all three feature sets; Dart goldens moved in lockstep across both byte-identical twins. **Host-tested + build-verified only** (§ 314) — the radio leg (a corrupted push refused on-device, a 49-byte GATT write surviving a real MTU) is a bench-checklist item, and BLE can never be sim-verified.

**Run-store v3 — the footer totals come under the CRC (2026-07-25, decisions § 321).** A follow-up recorded during the PR #620 review: the run blob's CRC32 covered only the `header | records` prefix, leaving the footer's `distance_m` / `moving_s` / `elapsed_s` outside the window — and the Dart mirror's suite had that written down as the *frozen wire spec*, with a test asserting a flip there **must** still verify. One rotted bit in those twelve bytes therefore produced a blob that passed `verify_blob`, passed `recover_slot`, and synced as an ordinary run with silently wrong numbers, which is worse than a rejected run because nothing tells the runner. **v3** takes the CRC over `blob[..len - 4]` — everything but the four bytes the checksum occupies. No field moved and no length changed; only the hashed window widened. Both emitting paths go through one `stamped_footer` helper (a second hand-rolled copy is how two CRC domains drift apart), and `recover_slot`'s footer scan widens with them, so a decoy `END1` in track data must now collide over its own would-be totals too. **Pre-v3 blobs are deliberately undecodable** (`MIN_FORMAT_VERSION` = 3): dispatching the CRC window on the version byte would have preserved the unprotected-totals hole forever for anything claiming to be old, and with no deployed devices there is nothing to migrate — an old blob on a bench board is rejected by version, its slot reads free, and the next run reuses it. Both goldens moved on purpose (version byte `02` → `03`, new trailing CRC), the v1/v2 vectors stay as *rejection* fixtures on both sides, the Dart "totals are uncovered" test is inverted into an exhaustive every-byte sweep, and the property suite's corruption case strengthens to "no flip anywhere survives" plus one aimed at the twelve summary bytes. **Host-tested + build-verified only** (§ 314): `watch_core` **1377** lib tests plus the property suites green, all three feature sets clean under `clippy -D warnings`, `cargo fmt --check` clean, Dart twins byte-identical. Not sim-verified, not bench-verified.

**Second app-logic hardening batch — six parallel worktrees (2026-07-25, decisions §§ 324-330).** The extraction pass above left eleven modules in `watch_core` and a handful of decisions still inside async task bodies. A six-task parallel pass closed them, and four of the six found real defects rather than merely adding coverage.

- **Two free-running sensor wakers, closed** (§ 328). `embassy_sync::Watch::send` wakes every receiver whether or not the value moved, and both the barometer and the GSV/GSA side channel published on every sample — a standing per-second reason for the CPU to wake and the face to fully re-render, against § Power discipline above. Equality dedup could not fix either: a `Reading` is three `f32`s off a real sensor, and `ublox_nmea` emits one `Gsv` per GSV *sentence* rather than per group, so a multi-constellation receiver lands 3-6 genuinely-different counts a second. Both are now gated on the coarsest quantum still lossless for every consumer — the drawn bar count for the merged `state::SIGNAL`, and `elevation::PUBLISH_STEP_M` = 0.1 m for the barometer, deliberately *not* the face's whole-metre rendering quantum, because the recorder feeds the same altitude to the GAP estimator's ~5 m grade segments. A manual QNH snap bypasses the gate entirely so the ALT row can never contradict its own banner.
- **The Nav course polyline was never clipped to its panel** (§ 327). Moving the last three inline pixel jobs out of the `ui` task into `watch_render` widgets found it on the first test written: `Framebuffer` clips at the *display* edge, but the Nav panel is a band inside it and the polyline paints after the text rows, so a realistic four-point ultra course on the auto-zoom window put 16 pixels of breadcrumb on the NAV title row. Now Cohen-Sutherland-clipped to the panel rect with the interpolation in `i64` — release builds wrap on overflow, and a wrapped multiply puts a garbage line *back inside* the panel on the one page a lost runner is reading. A whole-course fit renders byte-identically, pinned.
- **Two partial settings pushes coalesced and the first was lost** (§ 329, § 330). `state::SETTINGS` was a single-slot `Watch` polled opportunistically — but the `SET1` frame's whole premise is the partial push, so a phone sending max HR then a page mask lost the max HR outright: decoded, CRC-checked (§ 319), correctly routed (§ 324), and still never applied. It is now a depth-4 `Channel` (§ 320's sibling), both publishers `try_send` + `warn!` on full, and the record loop drains in arrival order — then § 330 closed the other half by making a pushed frame its own wake source, since indoors with no fix and no button press the drain's wait was unbounded. The arm is `ready_to_receive`, not `receive`, so the drain stays the sole consumer and the FIFO order holds; idle wake rate is unchanged, and a burst costs one wake rather than one per frame.
- **The settings fan-out is now exhaustive by construction** (§ 324). `record.rs`'s nine routing arms moved to `watch_core::settings_apply` as a plan of typed effects: no `..` rest pattern (a new field is a compile error), capacity derived from the variant chain, and the load-bearing test counting the plan against the frame's own presence bitfields. No routing defect existed — stated plainly rather than dressed up.
- **The HR AGC cadence** joined the host-tested drain surface (§ 325), where the extraction found the task's comment naming the wrong mechanism for its post-wake hold: `PeakDetector`'s DC estimates read `Some` again one sample after a reset, so the counter reset is the *only* thing holding a freshly-woken part off a gain step. Plus a latent (unreachable-today) ordering defect in when the period is consumed.
- **Two untested tables and one untested accumulator got guards.** `phone.rs`'s hand-rolled settings-frame byte accumulator — whose buffer just grew 45 → 49 for the v3 CRC — is now `watch_core::settings_frame`; it turned out correct, so the tests pin the boundaries against the *next* growth. And `drivers/sharp_mip/tests/icons.rs` gives the 16x16 icon table the sweep the font and bignum tables already had, with `gen_icons.py` emitting `Icon::ALL` so the enumeration cannot silently narrow (§ 326). No collision existed.

**Verification.** Host tests **1702 → 1799** (0 ignored); `app/src` **4,561 → 4,492** lines. All three feature sets build and pass `clippy -D warnings`; `cargo fmt --check` clean. **Host-tested + build-verified only** (§ 314) — Renode is not installed on the authoring machine and no parts exist, so nothing here is sim- or bench-verified. Three specific limits are worth naming: the sim has no BMP581 (the baro task parks, so § 328's elevation gate is unreachable under Renode), every sim NMEA fixture is single-constellation GPS-only (so is the GSV repeat the signal gate exists to absorb), and the 0.1 m step's noise-floor justification is a datasheet-class derivation now registered as such in [`quality_standards.md`](../../docs/custom_watch/quality_standards.md).

**`cutoff_eta` caught up to web issue #607 (2026-07-26).** The [`cutoff_eta`] port predated the canonical helper's two additions, so the watch's Cut-off page could say "BEHIND" without ever saying what pace would still make it. `CutoffEta` now carries `required_pace_s_per_km` — the flat pace over the remaining distance that arrives exactly at the limit — and an explicit `limit_passed` flag, faithfully mirroring `apps/web/src/lib/runs/live_cutoff_eta.ts` and its Dart twin. The required pace is deliberately computed **even when the fix is stale**: unlike the ETA it does not depend on recent pace, so withholding it would hide a number the runner can still act on. `limit_passed` exists because the pace is `None` for two unrelated reasons — the limit has passed, or the cut-off is under 50 m out — and a "you cannot make it" surface must never fire from the second. The glance page gains one row (`NEED 6:00 /KM`, `NEED --` when there is no meaningful pace), via the existing `write_pace` idiom. Six mirror tests, one per new web case (host tests **1799 → 1805**). One-way faithful port per [decisions § 24](../../docs/architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive) — not part of the enforced web↔mobile lockstep. **Host-tested + build-verified only** ([§ 314](../../docs/architecture/decisions.md)): all three feature sets build, `clippy -D warnings` + `cargo fmt --check` clean; not sim-verified, not bench-verified.

## Layout

Actual workspace shape (Cargo workspace, all paths relative to `apps/custom_watch/`):

```
Cargo.toml              workspace root
rust-toolchain.toml     pins a recent stable Rust + thumbv7em-none-eabihf target
.cargo/config.toml      runner = probe-rs, default target, defmt log level
app/
  Cargo.toml
  src/
    main.rs             #[embassy_executor::main] entry, spawns tasks
    tasks/
      gps.rs            GNSS NMEA parser task
      hr.rs             MAX86177 polling + naive peak-detect task
      baro.rs           BMP581 sample task (per decisions.md § 90)
      battery.rs        SAADC battery-voltage task (VDD channel, probe-and-park)
      ui.rs             screen update + button-handler task
      ble.rs            GATT server + sync task
      record.rs         recording state machine (port of Dart run_recorder)
core/                  watch_core: hardware-free app logic (face, record, gauge, statusbar, bar_chart, ...)
render/                watch_render: host-testable face-widget drawing over the sharp_mip framebuffer
drivers/
  sharp_mip/            Sharp Memory LCD driver crate
  ublox_nmea/           u-blox NMEA parser crate (no_std)
  max86177/             MAX86177 register-level driver + bindgen wrapper for the HR algorithm
boards/
  nrf52840_dk/          board-support crate: pinmux, peripheral assignments
```

This is intentionally close to the per-task / per-driver split that the Zephyr-flavoured proposal in [`docs/custom_watch/firmware.md`](../../docs/custom_watch/firmware.md) uses — so the firmware architecture stays portable across the language choice. If we ever revert to C/Zephyr per the §80 fallback, the task boundaries map directly onto Zephyr threads + work queues.
