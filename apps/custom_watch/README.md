# custom_watch — tier-1 bench-prototype workspace

Rust + Embassy firmware for the ultra-marathon watch research effort. This is *only* the active workspace + per-step build status; the broader research (strategy, BOM, cost tiers, firmware architecture, performance path, parts list) lives under [`docs/custom_watch/`](../../docs/custom_watch/README.md). See also [`CLAUDE.md`](CLAUDE.md) in this directory for the scope rules.

## Local testing

The watch's developer inner loop is `bin/watch-flash.sh` from the repo root (or `cargo run --release` from this directory): build the firmware, flash it to a connected Nordic nRF52840 DK, stream `defmt` logs back to your terminal until Ctrl-C. Host-side unit tests run via `bin/watch-test.sh` or `cargo test` and don't need a board. Run `bin/watch-doctor.sh` once per machine to verify toolchain + board detection. No board at all? `bin/watch-sim.sh` boots the same release ELF on an emulated nRF52840 DK (Renode) with decoded defmt logs streaming and a canned NMEA fixture feeding the GPS UART — the whole boot + blink + task-scheduling path runs today, pre-parts ([decisions.md § 208](../../docs/architecture/decisions.md#208-firmware-simulation-runs-the-unmodified-elf-on-renode-with-a-custom-defmt-rtt-drain)). See [`local_testing.md`](local_testing.md) for the full setup walkthrough, the host-vs-on-target-vs-sim testing split, and the common-error reference.

## Next steps

1. **Order parts** — see [`docs/custom_watch/parts.md`](../../docs/custom_watch/parts.md). Total ~$300 for the MCU + sensor breakouts + battery + breadboard, plus ~$200–$900 in bench tools depending on which soldering iron / multimeter / logic analyzer tier you pick.
2. **Scaffold the Cargo workspace** — **DONE (2026-05-28).** `Cargo.toml`, `rust-toolchain.toml`, `.cargo/config.toml` with probe-rs runner, `app/` crate with Embassy executor + blink-LED stub task, stub modules for each subsystem, driver crates (`sharp_mip`, `ublox_nmea`, `max86177`) as `no_std` stubs, board crate (`nrf52840_dk`) with DK pin assignments, VS Code launch + tasks for in-IDE debug. `nrf-softdevice` is **not** in deps yet — it adds at step 6 with BLE and requires bumping `memory.x` to leave room for the SoftDevice. First flash pending parts arrival.
3. **GNSS bring-up** — **CODE DONE, SIM-VERIFIED (2026-07-08); bench verification pending parts.** `ublox_nmea` streaming parser (RMC/GGA, checksummed, 10 host tests) + the `gps` task reading UARTE0, publishing merged fixes through `watch_core::fix` into an embassy-sync `Watch`. The Renode sim feeds `sim/nmea/bench_jog.nmea` and fixes flow end-to-end.
4. **Display bring-up** — **CODE DONE, SIM-VERIFIED (2026-07-08); bench verification pending parts.** `sharp_mip` driver (framebuffer + dirty-line tracking + generated 8x16 font + a generated 16x16 icon table + the Sharp line-update wire protocol, 13 host tests) on SPIM3, and the `ui` screen task rendering the `watch_core::face` rows at 1 Hz. The face has two layouts (`watch_core::face`, host-tested): an **idle status face** (uptime clock, GPS status, last-known position, speed, altitude, HR, vert — the bench / acquisition view) and, once a run is under way, a **run dashboard** — a 2x-scale elapsed-time **hero** across the top two rows (pixel-doubled from the 8x16 font by `Framebuffer::draw_text_2x`, drawn from `face::hero_line`, with the blinking state tag tucked top-right), then distance, average + current pace, HR, altitude, and cumulative vert, each metric row carrying a 16x16 gutter icon (footsteps / heart / mountain / vert-arrows / satellite) with the values stacked in one glanceable column and raw lat/lon dropped. The icons are authored as editable SVG under `drivers/sharp_mip/icons/`, rasterised to the committed 1-bit `src/icons.rs` table by `scripts/gen_icons.py` (Inkscape → ImageMagick → packed Rust, same discipline as `gen_font.py`), and blitted by `Framebuffer::draw_icon`. Three ~1 Hz animations ride the existing per-second render tick as pure functions of `uptime_s` (so frame choice stays host-tested, not a hidden timer): the **REC** tag blinks while recording, the HR heart pulses (big/small frames) while a pulse is detected, and the GPS satellite cycles growing search arcs (`sat_search0/1` → `satellite`) until a fresh fix locks. The run view is **paged** (`watch_core::page::Page`, host-tested): **BTN3** cycles Dashboard → Distance-glance → Pace-glance, where the glance pages put one metric up large as the 2x hero with the rest as 1x context; `face::page_rows` / `page_icons` / `page_hero` render whichever page is current, and the idle status face ignores the page. Page selection is **compile-verified only** — the Renode sim has no buttons, so BTN3 is a bench-hardware path. `bin/watch-sim.sh --gui` shows the live panel via the `sim/SharpMipDisplay.cs` Renode model.
5. **Optical HR bring-up** — **CODE DONE incl. app wiring, SIM-VERIFIED (2026-07-08); bench verification pending parts.** `max86177` register driver (soft-reset → single-LED PPG channel → FIFO drain over blocking I²C) + a float-free integer PPG→BPM peak detector (DC-baseline removal, envelope-threshold beat detection with a refractory gate, inter-beat-interval smoothing, validity flag; 10 host tests). The `hr` task now drives it over TWISPI0, runs the detector, and publishes to `state::HR`, which the status face renders as an HR row. Because the driver is blocking, the task first does an async, timeout-bounded presence probe so an absent sensor (the sim, an unwired bench) parks instead of stalling the executor — sim-confirmed. The licensed Maxim HR algorithm comes later via `bindgen` against Maxim's C library, post-tier-1.
6. **BLE GATT bring-up** — **CODE DONE behind the `ble` feature (2026-07-08); UNVERIFIED — needs the dev kit, cannot be sim-tested.** The `ble` task enables the Nordic **S140 SoftDevice** via `nrf-softdevice` (git-pinned rev `47d6121c`; compiles + links against this Embassy 0.10 stack), advertises a custom 128-bit GATT service ("Threkir"), and on connection `notify`s one `watch_core::link` status frame per second — the SAME bytes the UART transport emits, so the phone-side decoder is transport-agnostic. Because the SoftDevice is proprietary firmware the Renode sim can't run, this path is compile-and-link-verified only; RAM origin, interrupt priorities, and connection params all need bench confirmation. It's **feature-gated and mutually exclusive with the default build**: `cargo build --release --no-default-features --features ble` (the SoftDevice owns `critical-section`, so the default `single-core-cs` feature is dropped; `build.rs` swaps in `memory-ble.x` to link above the SoftDevice). The default / sim build is byte-for-byte unchanged and still carries the link over UARTE1. Flashing needs the S140 hex programmed once alongside the app — see [`local_testing.md`](local_testing.md) and [decisions.md § 210](../../docs/architecture/decisions.md). ANT+ (S340) and secure pairing/bonding are later work.
7. **Integration** — wire steps 3–6 into a single recording state machine that ports the existing Dart `run_recorder` algorithm to async Rust. **RECORDER + BUTTON CONTROL + ELEVATION + FLASH RUN STORE + BLE SYNC (firmware half) WIRED; recording SIM-VERIFIED (2026-07-08); BLE sync compile-only / UNVERIFIED.** `watch_core::record` holds the host-tested `Recorder` (Idle → Recording → Paused → Finished) — haversine distance, elapsed/moving time, pace, `run_recorder`'s point-acceptance filter (min-move 3 m, max-jump 100 m, max-speed 10 m/s) and its derived moving-time auto-pause (0.5 m/s gate); 7 host tests. The `record` task drives it from `state::FIX` **and the `state::RECORD_CMD` command channel** (selecting over tick / fix / command) and publishes a snapshot to `state::RECORD`, which the face renders as a recording line; the sim run shows distance accruing and auto-pause holding moving time. **Button control is wired**: the `button` task debounces the DK's buttons and feeds commands — **BTN1** = start/pause/resume toggle, **BTN2** = stop — with the press→command decision in the host-tested `watch_core::button` (4 host tests). On real hardware BTN1 is the only start path; the old "auto-start on the first fix" stand-in now lives behind the **default-OFF `sim-autostart` Cargo feature**, which `bin/watch-sim.sh` builds with so the button-less Renode sim still records. The barometer is wired too — the `baro` task drives the **BMP581** (`drivers/bmp581/`, 5 host tests) over TWISPI1 through the same async probe guard, feeding `watch_core::elevation` (barometric altitude + cumulative-vert accumulator) and publishing a snapshot to `state::ELEVATION`. That snapshot is now surfaced end-to-end: the status face prefers the barometric altitude for its ALT row and adds a cumulative-vert line (`VERT +gain -loss`), and the phone-link status frame carries an additive optional `"elev":{alt_m,gain_m,loss_m}` object (schema still `"v":1`, `null` when the baro is absent) that the mobile dev Sim Watch screen decodes and displays. **Run sync (firmware half) is now wired.** The record task captures the GPS *track*, not just totals: on start it opens a `run_store::RunWriter` over a slot-sized RAM staging buffer, `push_point`s each fix the recorder accepts as a new anchor (the added host-tested `Recorder::last_fix_stored` signal, so stored points mirror the acceptance filter exactly) stamped with the latest HR (`state::HR`) + barometric altitude (`state::ELEVATION`), and on stop finalizes the blob with the snapshot totals and commits it to internal flash. `app/src/run_flash.rs` is the flash driver — a `FlashSink` (`run_store::ByteSink`) over embassy-nrf's NVMC plus a `RunStore` (commit / manifest / read_chunk) over the host-tested `watch_core::flash_store` slot layout: **4 slots × one 4 KiB erase page, reserved at the top of flash in both `memory.x` and `memory-ble.x`** (FLASH shrunk by 16 KiB; the region addressed by absolute offset `0xFC000`). It is **best-effort / L4** — it probes for the NVMC controller once at boot and no-ops every op if it's absent, and any flash error only `warn!`s, so recording is never blocked on flash. The **per-run point cap is 253** (`HEADER + 253·POINT + FOOTER ≤ 4096`): a few minutes at ~1 accepted fix/s. A full ultra needs the tier-2 external QSPI flash; the internal-flash store is a bench-prototype foundation, not shipping capacity. The default (sim) build boots + records unchanged (verified: distance accrues over 30 s, no panic/hang; Renode does model NVMC, and the sim has no stop path so `commit` stays untouched there). On the **`ble`** build the same Threkir GATT service now carries `run_manifest` (read + notify: `ManifestHeader` + one `ManifestEntry` per finished run) and `run_chunk` (write + notify: the phone writes a `ChunkRequest {run_seq, offset, len}`, the watch notifies back that slice of the blob clamped to the notify MTU + blob end) — the protocol of [firmware.md § Sync protocol](../../docs/custom_watch/firmware.md), live link preserved. Like step 6 this **compiles + links but has never run on hardware**; additionally, with the SoftDevice enabled the NVMC backend must be swapped for `nrf_softdevice::Flash` (SoftDevice-coordinated flash) before real use — see the caveat in `app/src/run_flash.rs`. Reboot-persistence of the slot directory (scanning flash headers on boot) is a documented not-yet — blobs survive in flash but the in-RAM index that advertises them is rebuilt per power cycle. **The phone half is now built too** (decisions §211): `apps/mobile_android/lib/sim_watch_sync.dart` is a Dart mirror of `run_store` — it pulls the manifest, reassembles chunks, `verify_blob`s each run (pinned to the SAME golden vector as the Rust `run_store` test, so the two can't drift), reshapes it into the payload the existing `WatchIngestQueue` / `runFromWatchPayload` → `api.saveRun` path already uploads, and delivers it via `WatchSyncClient` behind an injectable transport seam (production impl over the sanctioned `flutter_reactive_ble`). A dev-gated "Sync runs" action on the Sim Watch screen drives it; the pull→decode→verify→deliver path is unit-tested without a radio. What remains is purely on-hardware: exercising the real SoftDevice + NVMC-vs-`nrf_softdevice::Flash` path, and slot-directory reboot-persistence — both pending the dev kit.
8. **Fabricate the tier-1 enclosure** — once the integrated unit records a run, 3D-print a chassis that holds the breakout boards + LiPo together and takes a Velcro strap, so it can be worn for a test jog. **FDM (any hobby printer / Shapeways / JLCPCB 3D) is the intended method here, ~$0–50 per print** — see [`parts.md`](../../docs/custom_watch/parts.md) (optional-tools table) and the tier-1 deliverables in [`prototyping.md`](../../docs/custom_watch/prototyping.md#tier-1--bench-prototype-5002k-36-months). This is a *functional chassis to hold breakouts*, **not** case CAD / industrial design / a sealed enclosure — those are tier-2+ and stay gated on the §71 triggers (see [`CLAUDE.md`](CLAUDE.md)). A printed case is not water-resistant and will not pass IPX7 (that needs injection-moulded tooling + a gasket, a tier-2/3 line item).

Each step is roughly 2–4 weeks of evenings depending on prior firmware experience.

## Layout

Actual workspace shape (Cargo workspace, all paths relative to `apps/custom_watch/`):

```
Cargo.toml              workspace root
rust-toolchain.toml     pins a recent stable Rust + thumbv7em-none-eabihf target
.cargo/config.toml      runner = probe-rs, default target, defmt log level
app/
  Cargo.toml
  src/
    main.rs             #[embassy_executor::main] entry, spawns tasks
    tasks/
      gps.rs            GNSS NMEA parser task
      hr.rs             MAX86177 polling + naive peak-detect task
      baro.rs           BMP581 sample task (per decisions.md § 90)
      ui.rs             screen update + button-handler task
      ble.rs            GATT server + sync task
      record.rs         recording state machine (port of Dart run_recorder)
drivers/
  sharp_mip/            Sharp Memory LCD driver crate
  ublox_nmea/           u-blox NMEA parser crate (no_std)
  max86177/             MAX86177 register-level driver + bindgen wrapper for the HR algorithm
boards/
  nrf52840_dk/          board-support crate: pinmux, peripheral assignments
```

This is intentionally close to the per-task / per-driver split that the Zephyr-flavoured proposal in [`docs/custom_watch/firmware.md`](../../docs/custom_watch/firmware.md) uses — so the firmware architecture stays portable across the language choice. If we ever revert to C/Zephyr per the §80 fallback, the task boundaries map directly onto Zephyr threads + work queues.
