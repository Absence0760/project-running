# Run app — orientation for AI sessions

You're in a cross-platform running app monorepo: Flutter (Android + iOS), native Swift (Apple Watch), native Kotlin + Compose-for-Wear (Wear OS), SvelteKit (web), and Supabase (Postgres + Auth + Storage + Edge Functions). Full product context lives in [docs/](docs/) — this file is the index plus the non-obvious things that cost time to rediscover.

## Audit commands

Project-curated slash commands for security / privacy / invariant audits live under `.claude/commands/audit/`. Invoke as `/audit/<name>` (e.g. `/audit/rls`, `/audit/privacy-zones`). `/audit/all` runs the full sweep in parallel. Each is read-only on the codebase — they report findings, they don't fix without confirmation. **Findings are persisted to `reviews/`** (gitignored working notes — `reviews/audit-<name>.md` for audits, `reviews/persona-<name>.md` for persona hunts; lifecycle in [`reviews/README.md`](reviews/README.md)), not just chat. See [`.claude/commands/audit/README.md`](.claude/commands/audit/README.md) for the index + when to run each.

## /safe-edit — coder ↔ reviewer loop for non-trivial changes

For security-sensitive, schema, or recording-stack changes — anything where a second pass of "did the diff actually honour the project's invariants" is worth ~2-3x the token cost — use `/safe-edit <task>`. It implements the change, then runs the `code-reviewer` agent against the working diff (cross-checking decisions ADRs, layering contract, twin invariant, paywall gates, fail-closed defaults, comment / abstraction discipline), applies any concrete findings, re-reviews once, and hands off to the user for the commit decision. Hard cap at 2 review cycles. Don't use it on typos, doc tweaks, or any < ~10-line diff that touches no invariant — just edit those directly.

## /check — review + test-gap + doc-hygiene before declaring done

Every non-trivial dev change goes through **review → unit tests → e2e tests** before it's done. The `/check` slash command runs the three relevant agents in parallel against the working diff and reports gaps:

- `code-reviewer` — does the change honour project invariants? (same agent `/safe-edit` uses)
- `test-gap-checker` — did the diff add unit tests + e2e tests where the rule says it should? Web e2e = Playwright (`apps/web/tests-e2e/`). Backend e2e = pgtap (`apps/backend/supabase/tests/`) or Deno tests next to the Edge Function. Mobile / watch have **no e2e equivalent** by design — see `docs/testing/testing.md § What's not covered`.
- `doc-hygiene-checker` — same as the Docs hygiene rule below.

Cheaper than `/safe-edit` (single pass, no review-and-fix loop), advisory only — the user decides which findings to apply. Use it before every commit on a non-trivial change. Skip on typos / comment edits / dep bumps.

The full rule + per-source-type test surface is in [`docs/architecture/conventions.md` § Test hygiene](docs/architecture/conventions.md#test-hygiene--review-then-unit-then-e2e).

## /improve-round — ship one improvement to an area, then self-audit

`/improve-round [area]` is the repeatable "do another round" loop: pick (or take) one area of the app, ship a genuinely useful, bounded improvement **web-first** in path-scoped per-piece commits (tests + twin parity + i18n + docs each in their own commit), then run the `code-reviewer` agent against the commit range and fix every finding — **verifying any numeric claim by computing it** before applying — until clean, capped at two review cycles. Unlike `/check` (advisory, working-diff, no fixes) and `/safe-edit` (one task, coder↔reviewer loop), this one *chooses the work*, commits as it goes, and closes the audit loop itself. Omit the arg to let it survey for a high-value target (a missing signal, a feature interconnection that doesn't exist yet, or a shipped-but-inconsistent surface) and propose it before building. Definition in [`.claude/commands/improve-round.md`](.claude/commands/improve-round.md).

## /ux-hunt — hunt UI/UX anti-patterns, fix them web + mobile

`/ux-hunt [area]` is the repeatable "do some rounds of hunting + fixing" loop: fan out two read-only hunter agents (web + mobile) against a UI/UX anti-pattern checklist (destructive-action-without-confirm, swallowed/indistinguishable failures, double-submit, missing loading/empty/error states, a11y labels, hardcoded English, overflow), triage the findings — pulling out the ones present on **both** platforms — then fix each as a matched web↔mobile pair: web confirms via `ConfirmDialog`, mobile via the `AlertDialog` idiom; surface swallowed failures (fixing the data-layer swallow at its source when there's a single caller); add the i18n keys to all six web locales + all mobile ARBs; mirror Dart to the iOS twin; and pin every fix with a test (Playwright web / Flutter widget mobile) in the same path-scoped commit — **including updating the existing tests that assumed an immediate delete**. Bakes in the mobile-test gotchas (store I/O needs `tester.runAsync`, `showTopBanner` leaves a pending timer, `pumpAndSettle` hangs on cursor/`LiveRunMap` animations, duplicate button labels need dialog-scoped finders). Unlike `/polish-ui` (redesigns one surface) and `/improve-round` (ships one self-scoped feature improvement), this one *finds a class of issues* and fixes them cross-platform. Omit the arg to sweep both platforms broadly. Definition in [`.claude/commands/ux-hunt.md`](.claude/commands/ux-hunt.md).

## Always recommend the long-term solution

When there's a choice between a quick patch and the durable fix, **lead with the durable one** — the root cause, the reusable abstraction, the consistent pattern, the proper schema change — not the band-aid. This applies to every recommendation: a one-off conversion vs. a shared component, papering over a failing test vs. fixing the bug it caught, a local workaround vs. closing the underlying gap, copy-paste vs. extracting the shared helper.

- **Recommend the long-term solution even when it's more work.** Don't pre-emptively pitch the cheap option to save effort or tokens. State the durable fix as the recommendation.
- **When you do mention a quicker path, present the long-term one first and name the trade-off** so the user is choosing with eyes open — never silently ship the shortcut.
- **A short-term fix is only acceptable when the user explicitly chooses it** after seeing the long-term option, or when the durable fix is genuinely out of scope for an urgent hotfix (say so, and note the follow-up).
- This reinforces the existing discipline rules: fix the root cause (don't inflate timeouts / retries / skips to hide a bug), don't defer on low-priority grounds, and close flagged gaps in the same turn rather than leaving a TODO. The default is **do it right**, not **do it again later**.

## Compliance sign-offs gate prod, not code

A legal / CISO / counsel sign-off (privacy-boundary changes, Art 9 health-data consent, Stripe Connect payouts, GDPR retention, anything tagged "gated on owner+CISO+counsel" in the docs) is a **pre-production deploy gate, not a reason to leave the code unwritten.** Write the feature, land it behind whatever flag/config the design calls for, and record the sign-off as a deploy-time checklist item — do **not** stub it out, half-build it, or park it in followups as "blocked on legal."

- **Build the whole code path now**, including the privacy/consent/payout logic, tests, and docs. The reviewer (counsel/CISO) reviews *shipped code on `main`*, which is easier to evaluate than a description of intent.
- **Keep the prod gate explicit and fail-closed**: the gating flag/secret defaults to off/unset so the feature can't reach real users until the sign-off lands (e.g. Stripe live keys unset, a feature flag default-off, `BYPASS_PAYWALL` dev-only). The gate lives in config, not in missing code.
- **Record the sign-off as a pre-deploy checklist item**, not a `- [ ]` "blocked on legal" follow-up. The followups entry, if any, tracks the *deploy/credential* step, not the code.
- This does **not** override genuine external blockers: a missing third-party credential/account (Garmin OAuth approval, a Firebase project, a RunSignUp key) or on-device/hardware/real-fixture validation still gates *going live* — but write all the code that doesn't depend on the secret, behind the same fail-closed gate. See [decisions.md § 150](docs/architecture/decisions.md).

## Branches & PRs

- `main` is the working branch locally, but `origin/main` is protected: every change reaches it through a PR that must pass the single required **CI gate** status check. No human approval is required (a green CI is the merge gate, review is a quality practice not a gate), but a PR is mandatory and enforced even for admins — no direct pushes. Force-pushes and branch deletion are blocked; history is linear and conversation resolution is required.
- **PR titles are lint-gated — get this right or the `lint title` check fails the PR on open.** The title itself must be conventional-commit format `type(scope): subject` (scope optional), enforced by [.github/workflows/pr-title-lint.yml](.github/workflows/pr-title-lint.yml). The **type must be one of** `feat fix chore docs refactor test perf ci build revert` — note there is **no `style`** in that list (fine as a commit type, not as a PR-title type — retitle a formatting-only PR to `chore:` or `refactor:`). The **most common failure**: putting the *scope* where the *type* goes — e.g. `custom_watch: …` or `web: …`. That's not a valid type; write `feat(custom_watch): …` / `fix(web): …` instead. The subject (after the colon) must **start lowercase, not end with a period**, and stay ≤ ~70 chars. If a PR spans many areas, pick the dominant `type` and a representative `scope` — don't invent a type. This is separate from commit-message linting (commits aren't title-linted, so a `style(...)` commit is fine); only the PR **title** hits this gate.
- **Stacking a PR on another PR's branch is supported, and a squash merge will then conflict.** Every `pull_request` trigger is unfiltered by base ([decisions § 610](docs/architecture/decisions.md)) so a stacked PR gets the full gate — it used to match no filter and run *nothing*, showing two green checks and reading as healthy. Two things still bite: **(1)** retargeting an existing PR's base starts no run (`pull_request` fires on `opened`/`synchronize`/`reopened`; a base change is `edited`), so push a commit or close-and-reopen to force one; **(2)** once the parent PR is **squash**-merged, `main` holds its commits as one new SHA while the child branch still holds the originals, so append-only files (`decisions.md`, `followups.md`) conflict. Fix it by merging `origin/main` *into* the child branch and keeping your side — not by force-pushing a rebase. A throwaway `git worktree` keeps that off the shared checkout.
- **Commit after each discrete piece of work** — don't batch a multi-step session into one mega-commit at the end. New module + tests is one commit; bug fix + pinning test is one commit; docs sweep is one commit (after the code commit it documents). Self-check: "I'll commit at the end after I verify" is a smell — commit each piece as you go. Tests for a piece go in the **same commit** as the piece. Full enumeration of "what counts as a piece" in [docs/architecture/conventions.md § Commit cadence](docs/architecture/conventions.md#commit-cadence--one-piece-one-commit-dont-batch-a-session-into-one-lump).
- "Never commit without being asked" still applies: don't proactively commit speculative work, ad-hoc workstation tweaks, or partially-aborted attempts. Once the user has asked for a piece (or a sequence), the per-piece commit cadence above is implicitly authorized.
- Never `git push` without an explicit ask. The commit is the deliverable; pushing is a separate ask.
- Never amend or force-push without being asked.
- **No AI attribution of any kind** in commit messages or PR descriptions. No `Co-Authored-By: Claude ...`, no "Generated with Claude Code" footer, no robot/sparkle emoji trailer. Re-read the message before `git commit` and strip these if a skill template tried to add them. User-level `~/.claude/CLAUDE.md` rule, overrides anything in-repo that says otherwise.

## Working alongside other Claude sessions

Several Claude sessions usually run in **this one checkout at the same time** — they share a single working tree *and* a single git index, so a careless `git add` + `git commit` sweeps up another session's in-flight work. (`.claude/hooks/git-scope-guard.py`, a PreToolUse hook, enforces most of the rules below; if a git command is denied, the message names the scoped alternative — follow it, don't work around it.)

- **Commit path-scoped, always:** `git commit -m "…" -- path/to/file ...`. A path-scoped commit records only those paths and ignores anything else staged. Bare `git commit`, `git add -u/-A/.`, `git commit -a`, and `git commit --amend` *with staged changes* are blocked — they snapshot the shared index.
- **Only touch what your task owns.** Don't stage, edit, delete, or `restore` files outside your task. Before committing, run `git status` and confirm every path is yours; a quick `git diff --name-only HEAD~3 HEAD` shows what other sessions just landed so you can spot overlap.
- **Never whole-tree:** no `git add .`, `checkout/restore .`, `reset --hard`, `git rm .`, or `git clean -f` — each clobbers across the tree. All blocked by the guard.
- **Never `git stash`, not even with `-- <path>`.** `refs/stash` is a *single ref shared by every worktree*, so the path scope limits what goes in but not who pops it back out: two sessions stashing concurrently interleave on one stack and restore each other's payloads. This happened twice in one round (2026-08-05) and swapped in-flight work between two agents' trees. To park changes, use `git diff > /tmp/…/x.patch` plus `git checkout <ref> -- <path>`, or do the work in a throwaway worktree.
- **HEAD moves under you.** Other sessions commit to `main` mid-task; your path-scoped commits still stack cleanly. Don't be alarmed if `git log` shows commits you didn't make, or if files you didn't change show as modified — leave those alone.
- **Findings go in `reviews/`** (gitignored), never committed beside code — see [reviews/README.md](reviews/README.md).
- **For large independent work, prefer a git worktree** — `git worktree add ../run-<slug> -b <branch>` gives you your own tree + index (no sharing, no clobber), then merge when done. Subagents doing parallel file edits should pass `isolation: "worktree"`.

## Docs hygiene — update docs as part of every change

**After every change that affects docs, update them in the same turn.** Do not defer to "I'll write the docs in a follow-up." If a doc references behaviour you just changed, it is wrong the moment you change the code.

Concretely, before you report a task as done:

1. **Feature / behaviour change** — does any doc describe the old behaviour? Update it. Candidates: `roadmap.md`, `features.md`, `parity.md` (flip cells for every platform the change affects), `architecture.md`, the matching `apps/<app>/local_testing.md`, and the per-app CLAUDE.md.
2. **Schema change** — regenerate both type files (`npm run gen:types` + `dart run scripts/gen_dart_models.dart`). Update `api_database.md` if a column, index, or RLS policy moved. See [schema_codegen.md](docs/architecture/schema_codegen.md).
3. **New convention or house rule** — add it to `docs/architecture/conventions.md`.
4. **Non-obvious decision or trade-off** — append an entry to `docs/architecture/decisions.md`. One paragraph. Don't rewrite history entries.
5. **Process / tooling change** — update `monorepo.md` (common tasks) and this file (if it's something a future session will hit as a gotcha).
6. **Roadmap checkbox** — tick it in `roadmap.md` the moment the work merges, not weeks later.

If you're unsure whether a doc change is warranted, err on the side of editing — a one-line update is better than drift. If the user tells you to skip doc updates for speed, respect that, but note the skipped update in your end-of-turn summary.

## Gotchas (things that cost me time to rediscover)

### Tools and workspace

- **Supabase lives under `apps/backend/supabase/`**, not at the repo root. If you ever see a top-level `supabase/` directory appear, it's the CLI's local state cache (`.branches`, `.temp`); don't write migrations there. Always `cd apps/backend` before `supabase <cmd>` (or use `--workdir`).
- **`melos run <script>` is broken on Melos 7** — scripts in `melos.yaml` aren't picked up (Melos 7 moved script definitions into package `pubspec.yaml` files). Use `melos exec -- <cmd>` for ad-hoc workspace-wide commands. Example: `melos exec -- dart analyze`.
- **`dart analyze` exits 0 on `info`, 2 on `warning`, 3 on `error`** — so a single new `warning` anywhere fails the `Test Flutter packages` job while thousands of infos do not. `mobile_android` carries ~3000 info-level lints today (the bulk are `always_use_package_imports` + `avoid_relative_lib_imports` interacting with the byte-identical-twin convention, plus `deprecated_member_use` from `withOpacity` → `withValues`). All acknowledged tech debt. Treat `info` as noise; only act on `warning`/`error`. Because the bar is "zero warnings", a Flutter SDK bump that promotes a new diagnostic to `warning` fails CI on code nobody touched — which is why `FLUTTER_VERSION` in `ci.yml` is pinned (decisions.md § 595); bump it deliberately and fix the fallout in that commit.
- **Two package managers.** `apps/web` and `apps/backend` are npm workspaces (run `npm` commands from repo root or the app dir). Flutter packages are managed by Melos. Don't cross the streams.
- **`supabase gen types typescript --local` writes "Connecting to db 5432" to stdout**, not stderr. The `gen:types` script in `apps/backend/package.json` pipes through `grep -v '^Connecting to db'` to strip it. If you rewrite the script, keep the filter.
- **Seed user**: `runner@test.com` / `testtest`. Lives in `apps/backend/supabase/seed.sql`. Use it for any manual testing.
- **Local Supabase ports**: API 54321, DB 54322, Studio 54323, Mailpit 54324. The SvelteKit web dev server runs on **7777**, preview on 8888.

### Schema and row types

Fail-closed in three directions, and all three are the point of the helper: a STALE fix claims nothing (the last position being old is exactly when "they have not moved" is unknowable), a GAP inside the buffer discards everything before it (a runner who reconnects near where they dropped out was never observed standing there — the outage must not be counted as stillness), and a window shorter than `motionMinWindowMs` claims nothing (every runner alive stands still for twenty seconds at a road crossing). The `atLeast` flag says the stop reached the start of the vouched window, so the surface must say "at least N min" rather than state the figure flat. Web renders the chip on `/live/[id]`, mobile on `live_spectator_screen.dart`, both neutral rather than alarming — a runner stopped for six minutes is at an aid station. `atMs` is a Dart `int` epoch-ms against web's `number`, so the non-finite guard covers only the odometer on the Dart side; 18 mirror tests each), `auth_gates` (web `core/auth_gates.ts` ↔ mobile `auth_gates.dart`; `checkPasswordPair` + the `MIN_PASSWORD_LENGTH`/`minPasswordLength` floor — each a re-export of the canonical minimum (`PASSWORD_MIN_LENGTH` in `auth_rules.ts` / `kPasswordMinLength` in `auth_validation.dart`, 8, enforced server-side via config.toml's `minimum_password_length`) — the two-field check every password-MINTING surface runs: at least the floor, then exact equality, length reported first, **neither side trimmed** (whitespace is a real password character and is exactly the typo class this catches). A single-field sign-up bakes a typo into the account: GoTrue hashes it, the confirmation mail is clicked, and the account is then unreachable by its owner — visible to us only as a confirmed account whose `last_sign_in_at` stays null. Web has three minting surfaces (sign-up / reset / change-password), mobile only sign-up, so web's `checkSignUpGates` consent half is NOT twinned — mobile's sign-up screen is separate from sign-in, so those gates stay inline in `sign_up_screen.dart`'s `_checkGates`. Web's `{ok} | {ok, reason}` union is a nullable reason in Dart; 17 mirror tests each), `password_change` (web `core/password_change.ts` ↔ mobile `password_change.dart`; the change-password step-up — `checkPasswordPair` first (reused from `auth_gates`), then a non-empty current password, then a POSITIVE `verifyCurrentPassword` before `updatePassword`; a rejection, a thrown error, and a session with no email all fail closed identically (OWASP ASVS V2.1.14 / CWE-620, issue #381, decisions §278). Web models the failure as a `{ok, reason, detail?}` union, Dart as a small `PasswordChangeResult` class; the reason set is the lockstep. 7 mirror tests each), `streak_card` (web `runs/streak_card.ts` ↔ mobile `streak_card.dart`; `streakCardState` — which claim the dashboard streak card may make from which source: the `run_streaks_for_user` all-time row drives headline + sub-label when it has answered, and a null — loading, offline, signed out — suppresses the numeric best/"all-time best" claim entirely rather than presenting the windowed/resident figure as truth (decisions § 471/§ 475). Deliberately separate from `streaks` (the compute pair). The Dart-only `mergeAllTimeStreaks` is a documented mobile extra outside the pair: it pointwise-max-folds the RPC row with the local compute so a just-recorded unsynced run is never walked back — web needs no twin because its windowed fetch reads the same database the aggregate does. 7 mirror tests each), `route_simplify` (web `routes/route_simplify.ts` ↔ mobile `route_simplify.dart`; `simplifyTrack` (RDP) + `computeElevationGain` + the `ELEVATION_GAIN_MIN_DELTA_M` / `kElevationGainMinDeltaM` noise gate. Both doc comments had claimed lockstep for a long time while the two carried DIFFERENT algorithms and each suite pinned the opposite answer — see [decisions.md § 305](docs/architecture/decisions.md). Gain is always taken over the RAW track: RDP measures perpendicular distance in 2-D, so a straight road over a summit collapses to its endpoints and grading the simplified line reads the climb as zero. The scope of the pair is those two functions plus the constant, 13 mirror tests each — `summarizeRouteFromTrack` is web-only (mobile composes the two calls at the save-as-route call site) and `computeElevationLoss` is mobile-only (the run-detail stat shown beside gain, gated identically so the pair can't read as a bug), as is `simplifyToBudget` (priority DP to a fixed POINT COUNT rather than to a tolerance — the custom watch's 256-point `CRS1` course budget, decisions §370; web has no fixed-capacity course consumer to mirror it)), `geo` (web `routes/geo.ts` ↔ mobile `geo.dart`; `lonDeltaDeg` / `unwrapLonDeg` / `wrapLonDeg` — the longitude normalisation EVERY local planar frame on both platforms must take its east-west deltas through, ported from the firmware's `watch_core::geo` (decisions §463/§468). A plain longitude subtraction is wrong by a whole turn across 180°, so an uncorrected frame reads a point just past the line as ~40,000 km away and a bounding box as spanning 359.9°. Trigonometric formulae (haversine lengths, great-circle bearings) are periodic and immune — `privacy` is the named helper that needed no fix for exactly this reason, pinned by a test on both sides. Consumers today: `route_geometry`, `route_snap`, `route_simplify`, `track_projection` (incl. its `isTrackRenderable` 5 m span gate), `run_heatmap`, `route_loop` (both platforms), and the web-only `routing_quality` + `nearest_track_point` (decisions §473). Identity bit for bit inside a hemisphere — `unwrapLonDeg` is written as the longitude less whole turns, NOT the watch's `reference + delta`, so no rounding creeps into the common path; 6 mirror tests each), `undo_queue` (web `core/undo_queue.ts` ↔ mobile `undo_queue.dart`; the deferred-commit undo contract — `undoWindowSFromPref` (an absent / non-numeric / unrecognised `undo_window_s` falls back to 8 s and **never** to `0`) plus the queue itself: the mutation is HELD for the window rather than performed and later compensated, so undo cancels a timer and cannot fail; one slot (a second destruction commits the first and disarms its timer); `restore` puts back a list snapshot so ordering survives; a commit that later fails restores AND reports; `pause`/`resume` spend only the remaining time and keep the published `id` + `windowMs` stable. Web's `createUndoQueue(deps)` factory reads as a Dart `UndoQueue(UndoQueueDeps)` constructor — an idiomatic shape difference like `password_change`'s union-vs-class, not a divergence. The HOSTS are deliberately NOT twinned and cannot be: web's `UndoBar.svelte` widens `Modal.svelte`'s Tab ring, mobile's `widgets/undo_bar.dart` is a root `Overlay` entry that outlives a route pop and lands above a modal barrier's `BlockSemantics` — Flutter has no Tab ring and its snack bar is unreachable under a barrier (decisions § 523). 14 mirror tests each), `ai_disclosure` (web `core/ai_disclosure.ts` ↔ mobile `ai_disclosure.dart`; the versioned AI-processing consent ladder — `AI_DISCLOSURE_VERSION_COACH`/`_ROUTE_AI`/`_CURRENT_VERSION` + `AI_DISCLOSURE_ERROR` and the fail-closed `checkAiDisclosure` / `aiDisclosureFromProfileRow` grading (`missing` / `stale` / `unknown`, where a version above the build's ladder DENIES rather than counting as more-than-enough). The pair's scope is that client half only — web's `gateAiDisclosure` + `aiDisclosureDenialBody` are server-side and owe no Dart twin, and the constants must also stay in lockstep with the SQL `ai_disclosure_current_version()`, which both suites pin by parsing migration `20270511_001`. decisions § 571 + § 573; 16 tests web / 11 Dart — the count differs by design, web's extra cases cover `gateAiDisclosure`), `coach_load` (web `training/coach_load.ts` ↔ mobile `coach_load.dart`; `acwr` + `injuryRiskBand` + `loadTrend` — the acute:chronic-workload-ratio band edges the coach roster classifies through. The `coach_roster_summary` RPC returns RAW acute (7 d) and chronic (28 d-averaged-per-7 d) sums and every surface bands them here, so the thresholds cannot drift between the roster column, the athlete detail, and mobile), `nearby` (web `social/nearby.ts` ↔ mobile `nearby.dart`; `NEARBY_BUCKET_BOUNDS_M` / `NEARBY_BUCKET_COUNT` / `nearbyDistanceBucket` / `nearbyBucketUpperBoundM` — the coarse distance buckets opt-in "runners nearby" discovery reports instead of metres, so a caller cannot triangulate an opted-in runner. A THIRD copy of the boundaries lives in the SQL `CASE` behind `discoverable_runners_near` (migration `20270424000005`); all three must agree or the phone and the web disagree about how far away the same person is), `off_route_alert` (web `safety/off_route_alert.ts` ↔ mobile `off_route_alert.dart`; `OffRouteAlertDetector` + `OFF_ROUTE_ALERT_DISTANCE_M` + `OFF_ROUTE_ALERT_SUSTAIN_MS` + `offRouteEscalationEnabled` — the sustained-off-route escalation to a trusted contact, the moving-but-lost complement to the overdue net that only fires on telemetry silence. Deliberately a larger distance than the run screen's 40 m off-route *banner*: a nudge and a contact-ping are different claims. Mobile-only surface like `safety_nudge` — web carries the twinned decision logic), `profile_query` (web `social/profile_query.ts` ↔ mobile `packages/core_models/lib/src/profile_query.dart`; `extractProfileId` resolves a pasted bare uuid or `/u/<uuid>` URL straight to that runner. The Dart side is the one pair that does NOT live under `apps/mobile_android/lib/` — it sits in the shared `core_models` package that `api_client` consumes, so it needs no iOS-twin mirror and its mirror suite is `packages/core_models/test/profile_query_test.dart`), `env_flag` (web `core/env_flag.ts` ↔ mobile `env_flag.dart`; `isTruthyFlagValue` — the ONE accepted-affirmative set every fail-closed feature gate on either platform parses through: `1` / `true` / `yes` / `on`, trimmed and case-insensitive, everything else — unset, empty, `false`, a typo — off. The set being one contract across both platforms is the whole point of the pair: it was previously copied inline into four mobile gates and three more web ones beside the canonical, and the narrowest copy (`checkpoint_checkin_screen.dart`'s `_weighInGate`, `1`/`true` only) meant an operator who set `WEIGH_IN_GATE=yes` got the Art 9 weigh-in fields left off while the same string turned every other gate on (decisions § 709). The two flags whose parser lives INSIDE another parity pair — `off_route_alert`'s `offRouteEscalationEnabled` and `plan_adaptive_replan`'s `adaptiveFitnessGateEnabled` — keep their named function and delegate to this one, the same re-export shape `auth_gates` uses for the password floor, so the feature keeps owning its flag while the parse stays single-sourced. Both suites carry a source guard that no other module may spell the set out; the mobile suite additionally pins that every dotenv key read under `lib/` is bridged from a `--dart-define` in `main.dart`, because release builds never load `.env.development` and three sign-off-gated flags were therefore unflippable in production. 7 tests web / 11 Dart — the five parser cases are the mirrored half; the Dart suite's four per-gate delegation cases and its release-reachability case have no web analogue, and web's `*_flag.ts` routing guard has no Dart one because mobile's gates do not live in `*_flag` modules), plus the `track_projection.ts` ↔ `projectTrack` / `isTrackRenderable` helpers inside `track_preview.dart`. The `shared-library-syncer` agent (under `.claude/agents/`) detects divergence proactively after edits — invoke it whenever you touch one side of a pair. **That agent works from its own table, not from this list**, so a pair added here without a row there is a pair whose divergence is never detected (and the reverse reads as a single-platform helper); `scripts/check_parity_pair_registry.mjs` fails the PR when the two registries disagree in either direction, or when either points at a file that no longer exists. Adding a pair means editing both, in the same change. See decisions.md § 604.


Many of these pure helpers also carry a **third parity rail** in the research-tier watch firmware: a `no_std` Rust port under `apps/custom_watch/core/src/<name>.rs`, host-tested test-for-test against the web `.test.ts`. Because the watch is additive per [decisions.md § 24](docs/architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive), these are **one-way faithful ports, NOT part of the enforced web↔mobile lockstep** the `shared-library-syncer` checks — the watch [`README.md` § step 7](apps/custom_watch/README.md) tracks the full set.
