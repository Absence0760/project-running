# Run app — orientation for AI sessions

You're in a cross-platform running app monorepo: Flutter (Android + iOS), native Swift (Apple Watch), native Kotlin + Compose-for-Wear (Wear OS), SvelteKit (web), and Supabase (Postgres + Auth + Storage + Edge Functions). Full product context lives in [docs/](docs/) — this file is the index plus the non-obvious things that cost time to rediscover.

## Audit commands

Project-curated slash commands for security / privacy / invariant audits live under `.claude/commands/audit/`. Invoke as `/audit/<name>` (e.g. `/audit/rls`, `/audit/privacy-zones`). `/audit/all` runs the full sweep in parallel. Each is read-only on the codebase — they report findings, they don't fix without confirmation. **Findings are persisted to `reviews/`** (gitignored working notes — `reviews/audit-<name>.md` for audits, `reviews/persona-<name>.md` for persona hunts; lifecycle in [`reviews/README.md`](reviews/README.md)), not just chat. See [`.claude/commands/audit/README.md`](.claude/commands/audit/README.md) for the index + when to run each.

## /safe-edit — coder ↔ reviewer loop for non-trivial changes

For security-sensitive, schema, or recording-stack changes — anything where a second pass of "did the diff actually honour the project's invariants" is worth ~2-3x the token cost — use `/safe-edit <task>`. It implements the change, then runs the `code-reviewer` agent against the working diff (cross-checking decisions ADRs, layering contract, twin invariant, paywall gates, fail-closed defaults, comment / abstraction discipline), applies any concrete findings, re-reviews once, and hands off to the user for the commit decision. Hard cap at 2 review cycles. Don't use it on typos, doc tweaks, or any < ~10-line diff that touches no invariant — just edit those directly.

## /check — review + test-gap + doc-hygiene before declaring done

Every non-trivial dev change goes through **review → unit tests → e2e tests** before it's done. The `/check` slash command runs the three relevant agents in parallel against the working diff and reports gaps:

- `code-reviewer` — does the change honour project invariants? (same agent `/safe-edit` uses)
- `test-gap-checker` — did the diff add unit tests + e2e tests where the rule says it should? Web e2e = Playwright (`apps/web/tests-e2e/`). Backend e2e = pgtap (`apps/backend/supabase/tests/`) or Deno tests next to the Edge Function. Mobile / watch have **no e2e equivalent** by design — see `docs/testing/testing.md § What's not covered`.
- `doc-hygiene-checker` — same as the Docs hygiene rule below.

Cheaper than `/safe-edit` (single pass, no review-and-fix loop), advisory only — the user decides which findings to apply. Use it before every commit on a non-trivial change. Skip on typos / comment edits / dep bumps.

The full rule + per-source-type test surface is in [`docs/architecture/conventions.md` § Test hygiene](docs/architecture/conventions.md#test-hygiene--review-then-unit-then-e2e).

## /improve-round — ship one improvement to an area, then self-audit

`/improve-round [area]` is the repeatable "do another round" loop: pick (or take) one area of the app, ship a genuinely useful, bounded improvement **web-first** in path-scoped per-piece commits (tests + twin parity + i18n + docs each in their own commit), then run the `code-reviewer` agent against the commit range and fix every finding — **verifying any numeric claim by computing it** before applying — until clean, capped at two review cycles. Unlike `/check` (advisory, working-diff, no fixes) and `/safe-edit` (one task, coder↔reviewer loop), this one *chooses the work*, commits as it goes, and closes the audit loop itself. Omit the arg to let it survey for a high-value target (a missing signal, a feature interconnection that doesn't exist yet, or a shipped-but-inconsistent surface) and propose it before building. Definition in [`.claude/commands/improve-round.md`](.claude/commands/improve-round.md).

## /ux-hunt — hunt UI/UX anti-patterns, fix them web + mobile

`/ux-hunt [area]` is the repeatable "do some rounds of hunting + fixing" loop: fan out two read-only hunter agents (web + mobile) against a UI/UX anti-pattern checklist (destructive-action-without-confirm, swallowed/indistinguishable failures, double-submit, missing loading/empty/error states, a11y labels, hardcoded English, overflow), triage the findings — pulling out the ones present on **both** platforms — then fix each as a matched web↔mobile pair: web confirms via `ConfirmDialog`, mobile via the `AlertDialog` idiom; surface swallowed failures (fixing the data-layer swallow at its source when there's a single caller); add the i18n keys to every web locale + all mobile ARBs; mirror Dart to the iOS twin; and pin every fix with a test (Playwright web / Flutter widget mobile) in the same path-scoped commit — **including updating the existing tests that assumed an immediate delete**. Bakes in the mobile-test gotchas (store I/O needs `tester.runAsync` — and then `pumpUntil` from `apps/mobile_android/test/pump_until.dart` to wait for it, never a fixed `Future.delayed`, decisions §715; `showTopBanner` leaves a pending timer, `pumpAndSettle` hangs on cursor/`LiveRunMap` animations, duplicate button labels need dialog-scoped finders). Unlike `/polish-ui` (redesigns one surface) and `/improve-round` (ships one self-scoped feature improvement), this one *finds a class of issues* and fixes them cross-platform. Omit the arg to sweep both platforms broadly. Definition in [`.claude/commands/ux-hunt.md`](.claude/commands/ux-hunt.md).

## Always recommend the long-term solution

When there's a choice between a quick patch and the durable fix, **lead with the durable one** — the root cause, the reusable abstraction, the consistent pattern, the proper schema change — not the band-aid. This applies to every recommendation: a one-off conversion vs. a shared component, papering over a failing test vs. fixing the bug it caught, a local workaround vs. closing the underlying gap, copy-paste vs. extracting the shared helper.

- **Recommend the long-term solution even when it's more work.** Don't pre-emptively pitch the cheap option to save effort or tokens. State the durable fix as the recommendation.
- **When you do mention a quicker path, present the long-term one first and name the trade-off** so the user is choosing with eyes open — never silently ship the shortcut.
- **A short-term fix is only acceptable when the user explicitly chooses it** after seeing the long-term option, or when the durable fix is genuinely out of scope for an urgent hotfix (say so, and note the follow-up).
- This reinforces the existing discipline rules: fix the root cause (don't inflate timeouts / retries / skips to hide a bug), don't defer on low-priority grounds, and close flagged gaps in the same turn rather than leaving a TODO. The default is **do it right**, not **do it again later**.

## Compliance sign-offs gate prod, not code

A legal / CISO / counsel sign-off (privacy-boundary changes, Art 9 health-data consent, Stripe Connect payouts, GDPR retention, anything tagged "gated on owner+CISO+counsel" in the docs) is a **pre-production deploy gate, not a reason to leave the code unwritten.** Write the feature, land it behind whatever flag/config the design calls for, and record the sign-off as a deploy-time checklist item — do **not** stub it out, half-build it, or park it in followups as "blocked on legal."

- **Build the whole code path now**, including the privacy/consent/payout logic, tests, and docs. The reviewer (counsel/CISO) reviews *shipped code on `main`*, which is easier to evaluate than a description of intent.
- **Keep the prod gate explicit and fail-closed**: the gating flag/secret defaults to off/unset so the feature can't reach real users until the sign-off lands (e.g. Stripe live keys unset, a feature flag default-off, `BYPASS_PAYWALL` dev-only). The gate lives in config, not in missing code.
- **Record the sign-off as a pre-deploy checklist item**, not a `- [ ]` "blocked on legal" follow-up. The followups entry, if any, tracks the *deploy/credential* step, not the code.
- This does **not** override genuine external blockers: a missing third-party credential/account (Garmin OAuth approval, a Firebase project, a RunSignUp key) or on-device/hardware/real-fixture validation still gates *going live* — but write all the code that doesn't depend on the secret, behind the same fail-closed gate. See [decisions.md § 150](docs/architecture/decisions.md).

## Branches & PRs

- `main` is the working branch locally, but `origin/main` is protected: every change reaches it through a PR that must pass the single required **CI gate** status check. No human approval is required (a green CI is the merge gate, review is a quality practice not a gate), but a PR is mandatory and enforced even for admins — no direct pushes. Force-pushes and branch deletion are blocked; history is linear and conversation resolution is required.
- **PR titles are lint-gated — get this right or the `lint title` check fails the PR on open.** The title itself must be conventional-commit format `type(scope): subject` (scope optional), enforced by [.github/workflows/pr-title-lint.yml](.github/workflows/pr-title-lint.yml). The **type must be one of** `feat fix chore docs refactor test perf ci build revert` — note there is **no `style`** in that list (fine as a commit type, not as a PR-title type — retitle a formatting-only PR to `chore:` or `refactor:`). The **most common failure**: putting the *scope* where the *type* goes — e.g. `custom_watch: …` or `web: …`. That's not a valid type; write `feat(custom_watch): …` / `fix(web): …` instead. The subject (after the colon) must **start lowercase, not end with a period**, and stay ≤ ~70 chars. If a PR spans many areas, pick the dominant `type` and a representative `scope` — don't invent a type. This is separate from commit-message linting (commits aren't title-linted, so a `style(...)` commit is fine); only the PR **title** hits this gate.
- **Stacking a PR on another PR's branch is supported, and a squash merge will then conflict.** Every `pull_request` trigger is unfiltered by base ([decisions § 610](docs/architecture/decisions.md)) so a stacked PR gets the full gate — it used to match no filter and run *nothing*, showing two green checks and reading as healthy. Two things still bite: **(1)** retargeting an existing PR's base starts no run (`pull_request` fires on `opened`/`synchronize`/`reopened`; a base change is `edited`), so push a commit or close-and-reopen to force one; **(2)** once the parent PR is **squash**-merged, `main` holds its commits as one new SHA while the child branch still holds the originals, so append-only files (`decisions.md`, `followups.md`) conflict. Fix it by merging `origin/main` *into* the child branch and keeping your side — not by force-pushing a rebase. A throwaway `git worktree` keeps that off the shared checkout.
- **Commit after each discrete piece of work** — don't batch a multi-step session into one mega-commit at the end. New module + tests is one commit; bug fix + pinning test is one commit; docs sweep is one commit (after the code commit it documents). Self-check: "I'll commit at the end after I verify" is a smell — commit each piece as you go. Tests for a piece go in the **same commit** as the piece. Full enumeration of "what counts as a piece" in [docs/architecture/conventions.md § Commit cadence](docs/architecture/conventions.md#commit-cadence--one-piece-one-commit-dont-batch-a-session-into-one-lump).
- "Never commit without being asked" still applies: don't proactively commit speculative work, ad-hoc workstation tweaks, or partially-aborted attempts. Once the user has asked for a piece (or a sequence), the per-piece commit cadence above is implicitly authorized.
- Never `git push` without an explicit ask. The commit is the deliverable; pushing is a separate ask.
- Never amend or force-push without being asked.
- **No AI attribution of any kind** in commit messages or PR descriptions. No `Co-Authored-By: Claude ...`, no "Generated with Claude Code" footer, no robot/sparkle emoji trailer. Re-read the message before `git commit` and strip these if a skill template tried to add them. User-level `~/.claude/CLAUDE.md` rule, overrides anything in-repo that says otherwise.

## Working alongside other Claude sessions

Several Claude sessions usually run in **this one checkout at the same time** — they share a single working tree *and* a single git index, so a careless `git add` + `git commit` sweeps up another session's in-flight work. (`.claude/hooks/git-scope-guard.py`, a PreToolUse hook, enforces most of the rules below; if a git command is denied, the message names the scoped alternative — follow it, don't work around it.)

- **Commit path-scoped, always:** `git commit -m "…" -- path/to/file ...`. A path-scoped commit records only those paths and ignores anything else staged. Bare `git commit`, `git add -u/-A/.`, `git commit -a`, and `git commit --amend` *with staged changes* are blocked — they snapshot the shared index.
- **Only touch what your task owns.** Don't stage, edit, delete, or `restore` files outside your task. Before committing, run `git status` and confirm every path is yours; a quick `git diff --name-only HEAD~3 HEAD` shows what other sessions just landed so you can spot overlap.
- **Never whole-tree:** no `git add .`, `checkout/restore .`, `reset --hard`, `git rm .`, or `git clean -f` — each clobbers across the tree. All blocked by the guard.
- **Never `git stash`, not even with `-- <path>`.** `refs/stash` is a *single ref shared by every worktree*, so the path scope limits what goes in but not who pops it back out: two sessions stashing concurrently interleave on one stack and restore each other's payloads. This happened twice in one round (2026-08-05) and swapped in-flight work between two agents' trees. To park changes, use `git diff > /tmp/…/x.patch` plus `git checkout <ref> -- <path>`, or do the work in a throwaway worktree.
- **HEAD moves under you.** Other sessions commit to `main` mid-task; your path-scoped commits still stack cleanly. Don't be alarmed if `git log` shows commits you didn't make, or if files you didn't change show as modified — leave those alone.
- **Findings go in `reviews/`** (gitignored), never committed beside code — see [reviews/README.md](reviews/README.md).
- **For large independent work, prefer a git worktree** — `git worktree add ../run-<slug> -b <branch>` gives you your own tree + index (no sharing, no clobber), then merge when done. Subagents doing parallel file edits should pass `isolation: "worktree"`.

## Docs hygiene — update docs as part of every change

**After every change that affects docs, update them in the same turn.** Do not defer to "I'll write the docs in a follow-up." If a doc references behaviour you just changed, it is wrong the moment you change the code.

Concretely, before you report a task as done:

1. **Feature / behaviour change** — does any doc describe the old behaviour? Update it. Candidates: `roadmap.md`, `features.md`, `parity.md` (flip cells for every platform the change affects), `architecture.md`, the matching `apps/<app>/local_testing.md`, and the per-app CLAUDE.md.
2. **Schema change** — regenerate both type files (`npm run gen:types` + `dart run scripts/gen_dart_models.dart`). Update `api_database.md` if a column, index, or RLS policy moved. See [schema_codegen.md](docs/architecture/schema_codegen.md).
3. **New convention or house rule** — add it to `docs/architecture/conventions.md`.
4. **Non-obvious decision or trade-off** — append an entry to `docs/architecture/decisions.md`. One paragraph. Don't rewrite history entries.
5. **Process / tooling change** — update `monorepo.md` (common tasks) and this file (if it's something a future session will hit as a gotcha).
6. **Roadmap checkbox** — tick it in `roadmap.md` the moment the work merges, not weeks later.

If you're unsure whether a doc change is warranted, err on the side of editing — a one-line update is better than drift. If the user tells you to skip doc updates for speed, respect that, but note the skipped update in your end-of-turn summary.

## Gotchas (things that cost me time to rediscover)

### Tools and workspace

- **Supabase lives under `apps/backend/supabase/`**, not at the repo root. If you ever see a top-level `supabase/` directory appear, it's the CLI's local state cache (`.branches`, `.temp`); don't write migrations there. Always `cd apps/backend` before `supabase <cmd>` (or use `--workdir`).
- **`melos run <script>` is broken on Melos 7** — scripts in `melos.yaml` aren't picked up (Melos 7 moved script definitions into package `pubspec.yaml` files). Use `melos exec -- <cmd>` for ad-hoc workspace-wide commands. Example: `melos exec -- dart analyze`.
- **`dart analyze` exits 0 on `info`, 2 on `warning`, 3 on `error`** — so a single new `warning` anywhere fails the `Test Flutter packages` job while thousands of infos do not. `mobile_android` carries ~3000 info-level lints today (the bulk are `always_use_package_imports` + `avoid_relative_lib_imports` interacting with the byte-identical-twin convention, plus `deprecated_member_use` from `withOpacity` → `withValues`). All acknowledged tech debt. Treat `info` as noise; only act on `warning`/`error`. Because the bar is "zero warnings", a Flutter SDK bump that promotes a new diagnostic to `warning` fails CI on code nobody touched — which is why `FLUTTER_VERSION` in `ci.yml` is pinned (decisions.md § 595); bump it deliberately and fix the fallout in that commit.
- **The repo's own `.mjs` scripts are typechecked now** — `scripts/`, `apps/backend/scripts/`, `.github/` and `infra/` are in `tsconfig.scripts.json`, and `infra/modules/web-stack/functions/` in `tsconfig.cloudfront.json`, both `checkJs` + `strict` (decisions § 757). There is still no root `tsconfig.json` and adding one is not the fix: a new tree gets a root of its own, and `scripts/tsconfig_coverage.test.mjs` fails the PR the moment a compilable file outside `apps/web` belongs to none. Run them with `npm run check:script-types` / `check:cloudfront-types` / `check:tsconfig-coverage`; the `apps/web` half is four more roots with its own guard (§ 749 / § 752).
- **Adding a job or a guard to `ci.yml` now has two enforced obligations** (decisions § 764). A new job must be named in the `CI gate` aggregator's `needs:` list — the gate counts a job it never waited for as no result, so an omitted line makes that job's red invisible rather than merely unlabelled. And a job that runs a SECOND guard becomes a *bundled* job by that fact, at which point every one of its check steps must print its own `::error::` (the `if ! cmd; then echo "::error::…"; exit 1; fi` form); the set of bundled jobs is derived from the guards they run, not listed, so nothing has to be registered. `scripts/check_ci_diagnostics.mjs` in `workflow-lint` fails the PR on both. A third rule in the same job: a workflow may only `npx` / `pnpm exec` a binary some `package.json` declares, or CI downloads an unpinned copy at run time — that is what `tsx` did for the entire life of the web unit suite.
- **The web icon font is a SUBSET, so adding an icon is a codegen step.** Every web icon is a Material Symbols ligature (`<span class="material-symbols">close</span>`), and the shipped `.woff2` carries only the 324 the tree names — 69 KB, against 3870 KB for the full font that used to load `font-display: block` on the root layout (decisions § 780). The set is derived from the source by `scripts/gen_web_icon_font.mjs`, so a new icon fails the `build-web` job naming itself; fix it with `pnpm gen:icon-font` and commit the regenerated `.woff2` **and** its `.json` manifest. Do not import `material-symbols/*.css` — that restores the full font.
- **Two package managers.** `apps/web` and `apps/backend` are npm workspaces (run `npm` commands from repo root or the app dir). Flutter packages are managed by Melos. Don't cross the streams.
- **A dirty root `deno.lock` after an npm dep bump (or a `supabase db reset`) is its `workspace` section, not its integrity pins.** That section transcribes the npm workspace's `package.json` specs, nothing resolves against it, and it drifts on every web bump. Run `pnpm sync:deno-lock` — deno rewrites it (the ranges are canonicalized, so hand-editing doesn't stick), `remote`/`redirects` are left alone, and the `parity-types` CI job fails on drift. [decisions.md § 706](docs/architecture/decisions.md). Relocating the lock would not remove that section — deno records it for any npm workspace *above* the lock, measured in [§ 730](docs/architecture/decisions.md).
- **`ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` in every pnpm lane at once means a lockfile lost the root `overrides:` block**, not that your change broke anything — a dep-bump PR regenerating `pnpm-lock.yaml` has dropped it before, taking 17 checks down at dependency install. Those four overrides are CVE pins (`_overrides_rationale` in the root `package.json`). Fix with `pnpm install --lockfile-only` and commit both lockfiles; `pnpm check:pnpm-overrides` (in `parity-types`) also fails when a pin is declared but *resolved around*, which a frozen install cannot see. [decisions.md § 730](docs/architecture/decisions.md).
- **`supabase gen types typescript --local` writes "Connecting to db 5432" to stdout**, not stderr. The `gen:types` script in `apps/backend/package.json` pipes through `grep -v '^Connecting to db'` to strip it. If you rewrite the script, keep the filter.
- **Seed user**: `runner@test.com` / `testtest`. Lives in `apps/backend/supabase/seed.sql`. Use it for any manual testing.
- **Local Supabase ports**: API 54321, DB 54322, Studio 54323, Mailpit 54324. The SvelteKit web dev server runs on **7777**, preview on 8888.
- **A Playwright seed's calendar day is the BROWSER's, not the runner's.** `playwright.config.ts` pins every context to `timezoneId: 'UTC'` while the Node process building the seed sits in the workstation's zone, so `new Date(y, m, d, h, 0)` puts the row on the adjacent day whenever the two disagree — green sixteen hours a day in EDT, red the other eight, and always green on UTC CI. Build every day-relative timestamp through `apps/web/tests-e2e/fixtures/dates.ts`; `fixtures/dates.test.ts` scans the whole `tests-e2e` tree and fails on a local-zone date getter. [decisions.md § 728](docs/architecture/decisions.md).

### Schema and row types

- **Every migration requires two regenerations.** TypeScript: `npm run gen:types`. Dart: `dart run scripts/gen_dart_models.dart`. Both outputs are committed. CI runs `gen:types:check` in the `parity-types` job and will fail PRs that skip it. See [docs/architecture/schema_codegen.md](docs/architecture/schema_codegen.md).
- **The Dart generator only understands `create table`, `alter table ... add column`, `alter table ... drop column`.** Everything else (indexes, functions, RLS, storage buckets, `$$...$$` bodies) is ignored. If you need a new SQL form, grow the parser in `scripts/gen_dart_models.dart` — don't hand-edit `db_rows.dart`.
- **Narrow unions live client-side AND in CHECK constraints** — `RunSource`, `RouteSurface`, `IntegrationProvider`, `PreferredUnit`, `SubscriptionTier`, `ClubRole`, `ActivityType` are overlaid as TS unions in `apps/web/src/lib/types.ts` via `Omit & {...}` AND enforced by CHECK constraints (see `apps/backend/supabase/migrations/20260505_001_narrow_union_check_constraints.sql` for the first four, `20260429_001_subscription_paywall.sql` for `subscription_tier`, `20260428_001_role_permissions.sql` for `role`, `20261207_001_promote_activity_type_is_dnf.sql` for `activity_type`). The vocabulary and the CHECK must stay in lockstep — updating one without the other lets one client write a value the other rejects (postgres 23514 `check_violation`). **`types.ts` is one rail of many.** The `parity-types` CI job runs `apps/web/scripts/check_constraint_unions.mjs`, whose `PAIRS` array is keyed on the COLUMN and lists **every** client declaration that enumerates it — 68 live set-shaped CHECK columns, 173 rails across 72 files, **80 of them Dart** (decisions § 791 + § 818). Dart is not exempt and never was: the `core_models` leaves `activity_type.dart`'s `ActivityType` and `distance_unit.dart`'s `DistanceUnit`, `challenge_progress.dart`'s `ChallengeMetric`, `gym_progression.dart`'s `ProgressionScheme`, `route_markers.dart`'s `routeMarkerKinds`, `run_stats.dart`'s two PR-bracket maps and 22 more are read against their CHECK on every PR. A rail declares its `shape`: `union` (TS `type X = 'a' | 'b'`), `strings` (a const array), `keys` (an object-key map), `records` (a list of specs plus the `field` to read), `enum` (a Dart enum, read as snake_case) or `switch` (a Dart switch's `case 'a':` / `'a' =>` labels, addressed by the innermost ENCLOSING declaration and optionally class-qualified — `_MarkerEditorSheetState._kindLabel`). A `Record<Union, X>` icon/label map is deliberately NOT registered — `tsc` already makes it exhaustive — but the Dart analogue IS: a `switch` over a `String` can never be exhaustive, so 46 of them are rails (decisions § 818), 22 with a staleness-checked `allowMissing` for the value their `default:` branch was written for.
  **Coverage is enforced, so a new CHECK column fails until it is registered.** Adding a set-shaped `check (col in (…))` to a live column means adding a `PAIRS` entry in the same change: either naming every client rail, or an empty `clients` list plus a `note` saying no client enumerates it (11 of the 68 are that shape). Registering a column that `database.types.ts` no longer has fails too. A client value the column cannot hold — or a column value a client deliberately omits — is declared per rail as `allowExtra` / `allowMissing` with a reason, and the guard fails when such an exemption goes stale. Dart rails name `apps/mobile_android` only; the twin invariant ([decisions § 39](docs/architecture/decisions.md#39-mobile_android-and-mobile_ios-share-a-byte-for-byte-dart-codebase)) covers iOS and the guard's suite pins it. If you add a new value: update the migration, regenerate both type files, then update **every rail the guard names for that column** — it will tell you which.
- **`runs.track` is not a column.** The GPS trace lives as a gzipped JSON file in the `runs` Storage bucket at `{user_id}/{run_id}.json.gz`; the row stores `track_url`. Never try to read `row.track` — it's `row.track_url` + a lazy download via `fetchTrack()`. See [docs/architecture/decisions.md](docs/architecture/decisions.md) for why.
- **`Run.metadata` is a `jsonb` bag** with no schema. It currently holds `activity_type`, `steps`, `event` (parkrun), `position` (parkrun), `age_grade`, and — client-only — a synthesised `track_url` key stuck there by `_runFromRow` for convenience. If you add a new metadata key, write a roadmap note; there is no type-level protection on these.

### Styling and conventions

- **No emojis anywhere** unless explicitly requested. Not in code, not in docs, not in commit messages, not in responses.
- **Default to zero comments.** Only write a comment if it explains a non-obvious *why* (hidden constraint, subtle invariant, workaround for a known bug). Never `// used by X`, never task-tracking references, never explain *what* well-named code already says.
- **Don't summarise what you just did** at the end of every response when the user can read the diff — keep end-of-turn text to 1–2 sentences (what changed, what's next).
- **No preemptive abstractions.** Three similar lines is better than a premature helper. If a `bug fix` PR contains a refactor, split it.
- **No backwards-compat shims**, no `// removed X` comments, no renamed-to-underscore-prefix unused variables. If something's unused, delete it.
- **Layered resilience is a product contract.** Basics always work. Design every new feature so a failure at a higher layer (L4 auxiliary effect, L3 route overlay, L2 map, etc.) cannot break a lower one (L1 GPS/pedometer distance, L0 clock). CloudFront's Lambda OAC sigv4-signs every origin request but cannot hash a body it streams, and an OAC-signed Function URL refuses an unsigned payload, so a client that hashes differently gets a 403 before invocation rather than a wrong answer), `race_match` (web `integrations/race_match.ts` ↔ mobile `race_match.dart`; the pure auto-match scoring behind the offer to import an official race result after a run is saved -- same calendar day, start within `raceMatchRadiusM` of the listing, distance inside the race's band, offered at or above `raceMatchThreshold`. INFORM-tier on both platforms: nothing writes without confirmation, so the two must agree about WHICH runs are offered or the same run is a race on one client and not on the other), `workout_labels` (web `training/workout_labels.ts` ↔ mobile `training_labels.dart`; the presentation-layer labels for the training enums, kept out of `training.ts` / `training.dart` so that pair stays locale-free. What is in lockstep is the COVERAGE -- every `WorkoutKind` and every `PlanPhase` resolving to a label on both platforms, so a kind added to the union cannot render as a raw token on one client. The key IDENTIFIERS are not: web carries dotted `MessageKey`s resolved through `m()`, mobile the camelCase ARB names resolved through `AppLocalizations`, the same carve-out `badges` and `extended_nutrients` record. The Dart file is named for the enums it labels rather than for the web basename the registry keys on)), plus the `track_projection.ts` ↔ `projectTrack` / `isTrackRenderable` helpers inside `track_preview.dart`. The `shared-library-syncer` agent (under `.claude/agents/`) detects divergence proactively after edits — invoke it whenever you touch one side of a pair. **That agent works from its own table, not from this list**, so a pair added here without a row there is a pair whose divergence is never detected (and the reverse reads as a single-platform helper); `scripts/check_parity_pair_registry.mjs` fails the PR when the two registries disagree in either direction, or when either points at a file that no longer exists. Adding a pair means editing both, in the same change. See decisions.md § 604. `rate_limit_errors` is PARSE-ONLY since decisions § 744: both halves return the `{bucket, seconds}` the postgres P0001 carries and neither holds a sentence, because the activity is a clause whose verb inflects and the wait pluralises. The wording lives in the seven web catalogues and the seven ARBs, assembled by render glue — `i18n/rate_limit_message.ts` resolving through `m`, `rate_limit_message.dart` resolving through `AppLocalizations` — which is per-platform (the key identifiers differ by convention) and, like `badges`' label keys, is NOT part of the enforced lockstep. The bucket→sentence mapping therefore costs nothing to extend on one platform, which is what § 737 had priced as a lockstep edit when it left both direct-message buckets on the generic wording.

Many of these pure helpers also carry a **third parity rail** in the research-tier watch firmware: a `no_std` Rust port under `apps/custom_watch/core/src/<name>.rs`, host-tested test-for-test against the web `.test.ts`. Because the watch is additive per [decisions.md § 24](docs/architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive), these are **one-way faithful ports, NOT part of the enforced web↔mobile lockstep** the `shared-library-syncer` checks — the watch [`README.md` § step 7](apps/custom_watch/README.md) tracks the full set. Ported 2026-07-11: `age_grade`, `hydration`, `exercise_calories`, `training_paces` (the pace-zone surface of `training`, reusing the watch's ported Riegel), `fitness` (VO2max / VDOT / per-run TSS / recovery advice + the Fitness-card snapshot, with the web's ISO `started_at` + `nowMs` collapsed to an integer day index like `training_load`), then a second batch — `route_markers`, `checkpoint_projection` (reuses the watch's `roadbook::CutoffStatus` + `cutoff_eta::CUTOFF_TIGHT_S`), `route_description` (reuses `distance_bands`), `plan_progress`, `plan_adherence`, `current_week` (ISO dates collapsed to a day index), `nutrition_targets`, `challenge_progress` (reuses `pacer::ON_PACE_BAND`), `badges` (thresholds in lockstep with the SQL awarder; i18n label keys carried as identifiers, not strings), and `locale_defaults`, then a third batch (track / route / race / training) — `privacy` (`clipPointsToZones`), `segments` (segment effort + competition-rank + crown label), `track_projection`, `run_heatmap` (`buildHeatCells` + `heatBounds`; the MapLibre GeoJSON emitters are web-only), `relink_candidates` (dates collapsed to a day index), `live_freshness`, and `finisher_certificate` (the shaping half; the SVG/PNG builder is web-only). Ported 2026-07-26: `race_phases` (the 10-10-10 / negative-split / even phase plan; the closing factor is DERIVED so the distance-weighted mean factor is exactly 1.0 — surfaced on the watch's Pacer glance page) and `course_profile` (the watch-only distance-even resampler that turns a pushed course's per-point elevation into the drawn climb profile; no web twin — web renders the profile from the full polyline). The same batch caught the watch's `cutoff_eta` up to web issue #607 (`requiredPaceSecPerKm` + `limitPassed`) and closed a divergence it surfaced: the watch gated pace on a bare `p > 0.0`, accepting `+Infinity` where web gates on `Number.isFinite`. Ported 2026-07-28: `workout` — the mobile `run_recorder` `WorkoutRunner` state machine (a shipped-phone-engine port, not a web pair), executing `WKT1`-pushed pre-expanded steps with its own glance page + lap-press step-skip (decisions § 354; the Dart `watch_workout.dart` encoder + iOS twin pin the shared golden vectors), and `daylight` (the seasonal sunrise/sunset half of `safety_nudge` — Cooper's declination, the −0.833° horizon, the polar clamps — driving the watch's tz-gated Daylight countdown page, decisions §355). **The 2026-07-29 batch is watch-native, not ported at all** — three parity rows with no web twin to mirror: `waypoints` (an eight-slot newest-wins mark store + `WPT1` codec behind BTN5's hold, decisions §357), `ice` (the ICE / medical-ID card on `SET1` v6 + an `ICE1` flash record, rendered as a third idle face, decisions §358), and `climb` (live ascent segmentation plus the ClimbPro-style crest ahead read off the already-pushed course profile, decisions §359). Nothing in that batch belongs in the parity-pair list above: adding a web twin later would be a *new* web feature, not a sync obligation. **Watch-native again 2026-07-30, three at once:** `sleep_station` (decisions §373) — the nap budget a 200-mile racer can afford before the next cut-off, computed as `cutoff_eta`'s margin less a reserve and inheriting its refusal to project off a stale fix; `timers` (decisions §375) — a countdown + stopwatch as one instrument behind an idle BTN2 modal, whose ADR also records why an **alarm** and a **find-my-phone** were refused rather than built; and `backyard` (decisions §372) — the wall-clock-anchored corral bell, the loop count riding the recorder's lap, the learned loop length and the projected return margin. None of the three has a web twin, and none is owed. **Watch-native once more 2026-07-31:** `storm` (decisions §376) — baro-driven storm detection, which trends a GPS-compensated **sea-level reduction** rather than raw station pressure because on a mountain ultra a 500 m climb moves the barometer twenty times further than a front does, and which refuses outright (`NO ALT REFERENCE`) when no GPS altitude corroborates the sensor rather than reporting a climb as weather. No web twin and none owed — the phone has no barometer. Most of these cores are wired to a run-view glance page (41 as of 2026-07-31); the ones that are not are deliberately UI-less per § 24 — see `docs/custom_watch/roadmap.md § Feature parity backlog` before assuming a missing page is owed.
