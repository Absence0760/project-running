### Power instrumentation

Per [decisions.md § 83](../architecture/decisions.md#83-tier-1-power-measurement-uses-nordic-power-profiler-kit-ii-applied-per-subsystem): a Nordic Power Profiler Kit II (PPK2, ~$120) is part of the tier-1 bench-tools kit. Used **per-subsystem** (bare-MCU sleep, GPS active/sleep, HR AFE sample, display refresh) rather than whole-device — the DK's onboard J-Link + LEDs burn ~30 mA at idle and make whole-device readings useless as a baseline. The per-subsystem numbers project to tier-2 / tier-3 power (see [`performance_path.md`](performance_path.md)). DoD doesn't require hitting any specific number; these measurements inform tier-2 planning, they don't gate tier-1 completion.

The five rigs and their pass criterion ("a number exists, and it's within an order of magnitude of the datasheet figure — a >10× disagreement means the rig is wrong, not the datasheet") are itemised in [`quality_standards.md § Power instrumentation`](quality_standards.md#power-instrumentation-per--83), alongside the list of firmware figures that are **derivations, not measurements** and that these rigs exist to confirm or refute — most importantly the ~110/180/220 h GNSS-mode battery projections.

### Definition of Done

Per [decisions.md § 82](../architecture/decisions.md#82-tier-1-firmware-is-done-when-one-outdoor-run-syncs-end-to-end-to-supabase-from-the-bench-prototype): tier 1 is complete when **one real outdoor run produces a GPS+HR-tagged track that syncs to Supabase** from the bench prototype end-to-end.

That stays the only completion bar. The [`quality_standards.md`](quality_standards.md) bench checklist ([§ 314](../architecture/decisions.md)) is **not** an additional gate — it's how bench verification gets conducted and claimed, so an open or failed item is a recorded finding and a tier-2 input, never an un-completion. Its [what tier 1 does not have to hit](quality_standards.md#what-tier-1-does-not-have-to-hit) section names the tier-2 targets (≥ 24 hr GPS battery, 100 % outdoor fix reliability) that must not leak into tier 1.

## Feature parity backlog (Garmin + COROS table stakes)

Everything above sequences the *hardware* build-out. This section tracks the *software feature surface* — the on-watch capabilities an ultra runner relies on today from a Garmin Fenix / Enduro or COROS Vertix, and would notice missing the day they switch. [`vision.md`](vision.md) covers the hardware table stakes (battery, GNSS, MIP display, buttons, maps, baro, HR); [`competitive_landscape.md`](competitive_landscape.md) covers where we go *beyond* parity (map UX, AI coach, social, update cadence), now turned into trackable work in [§ Differentiation backlog](#differentiation-backlog--where-we-can-beat-them) below. This is the middle layer: the features we have to match just to not feel like a downgrade.

**Framing.** Parity here means "an ultra runner doesn't lose a feature they relied on." It explicitly does **not** mean matching Garmin's full daily-smartwatch surface — per [`vision.md`](vision.md) the device is "a tool for the run, not a tool for the rest of the day," so the daily / lifestyle features are deliberately deprioritised (last table).

**Big lever.** Most on-run-guidance and training-metric items already have a pure-logic helper in the main app (the TS↔Dart parity pairs enumerated in [`CLAUDE.md`](../../CLAUDE.md)). For those, watch parity is a *firmware port* of an already-tested algorithm — the third language-level parity surface per [`firmware.md`](firmware.md) — not a fresh design; noted `(port: <helper>)` below. Items with no helper are new firmware design work.

Nothing in this section is ticked, and **that is a verification statement, not a build statement** — a great deal of it is built. The rung that ticks a box is **bench-verified** ([`quality_standards.md`](quality_standards.md#bench-verified)), and no parts exist, so a fully built, host-tested, sim-verified feature still reads `[ ]` here. Read each line's annotation for what is actually built; the shipped tier-1 slice is summarised in the status snapshot above. Tier tags show where each item realistically lands: **T1** = bench-prototype recording core, **T2** = wearable-prototype guidance / nav, **T3** = production polish. Everything still owed at T2 is sized in [`tier2_scope.md`](tier2_scope.md).

**On the ported cores without a UI.** `watch_core` holds **98** modules against **37** built-in glance pages, so most modules back no page at all — and that is the design, not a gap. The rest are not a backlog of unfinished screens — the third parity rail is a *one-way faithful port* of the shipped web helper (see [`apps/custom_watch/README.md`](../../apps/custom_watch/README.md) and the `CLAUDE.md` parity-pair list), and a good number of them are deliberately UI-less per [§ 24](../architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive) because their domain is phone-side (`badges`, `challenge_progress`, `recap`'s share path, `nutrition_targets`, `hydration`, `age_grade`, `finisher_certificate`, `relink_candidates`, `run_heatmap`, `privacy`, `locale_defaults`) or because they are helpers other cores reuse (`route_geometry`, `route_markers`, `exercise_calories`, `track_projection`). Don't read "no page" as "owed a page" — check whether an on-wrist surface is wanted at all before wiring one.

### Recording & on-run guidance

- [ ] **Activity profiles** — at minimum Run / Trail Run / Ultra / Hike, each with its own data screens + defaults. **Implemented** (2026-07-28, [decisions § 353](../architecture/decisions.md)): `watch_core::profiles` defines the four profiles as **macros over existing knobs** — a curated §284 page mask (Run drops the pushed-course cluster, Hike the racing cluster, Trail/Ultra keep the full cycle; every preset keeps the Dashboard + the Back-to-start safety page) plus a GNSS mode (Performance / Balanced / Expedition / Expedition) — selected from a fourth §351 settings-menu row as a clamped directional ladder, applied through the same channels a phone push and the quick cycle ride (last-writer-wins, no third state system), persisted in CFG1 behind a new flags bit, and re-applied at boot. Deliberately no per-profile alert cadences (§24 — the desert case has its `SET1` wire). Host-tested + build-verified. **T2** keeps nothing.
- [ ] **Auto-lap / manual lap / auto-pause.** Auto-pause is already specced in [`run_recording.md`](../features/run_recording.md); direct firmware port. **Auto-pause is implemented** in the tier-1 recorder (`watch_core::record`, the 0.5 m/s moving-time gate, sim-verified 2026-07-08). **Auto-lap + manual lap are implemented too** (2026-07-09): a 1 km auto-lap boundary and a manual lap close through the same host-tested `close_lap` path (a manual lap resets the auto countdown), surfaced on a Lap run-view page — current lap time up large, lap number + last-lap split below. Laps **persist to flash** since run-store v2 (2026-07-21, #599, [§ 285](../architecture/decisions.md)): record byte 15 tags point-vs-lap, laps interleave with points in close order on a 64-lap budget, and a slot-full run decimates its points rather than truncating — laps are never dropped. Host-tested + sim-verified (the lap press → lap command → Lap page renders — the key was BTN4 when this landed and has been **BTN5** since [§ 350](../architecture/decisions.md) moved paging to the lower pair). **The auto-lap half became CONFIGURABLE on 2026-07-30** ([§ 374](../architecture/decisions.md)): `watch_core::auto_lap` is a closed eight-rung catalogue — off, 1/5 km, 1/5 mi, 5/10/30 min — armed by `Recorder::set_auto_lap`, carried to the watch on **`SET1` v7** (both presence bytes were saturated, so the field rode a third one and the version bump v6's assert existed to force; v1–v6 still decode, an absent trigger leaves the watch's own standing), persisted in `CFG1`'s flags byte behind a set-marker + three discriminant bits (no config-record version bump; bit 7 is the last one free), re-applied at boot, and **named on the Lap page** beside the last split so an OFF trigger reads as a choice, not a stuck counter. The catalogue is closed rather than an arbitrary metre count because the flash lap budget is 64 records: 1 km laps already overflow it on a 100 km run, and an open field would let 50 m exhaust it inside 3.2 km. **The time rungs bank on MOVING time, never the elapsed clock** — an elapsed-clock auto-lap turns a 40-minute sleep-station stop into eight empty laps that displace real ones, and the stationary-runner case is pinned by a test running both axes through an hour of sub-threshold jitter. Like every history-derived page the *rolling* estimate needs the multi-day run history a standalone watch doesn't hold, so the value is phone-pushed through the plausibility-guarded `Recorder::set_fitness` setter and the page reads an honest `NOT SYNCED` until it arrives; `race_predictor` (also ported + wired) projects the ladder on-device from the current run as a single effort. Host-tested + build-verified only — **not** sim- or bench-verified, so it stays unticked per [`quality_standards.md`](quality_standards.md). **T2.**
- [ ] **Training status / readiness / recovery time** — Garmin Training Readiness, COROS equivalent. **Partially implemented** (2026-07-11): `watch_core::readiness` (a TSB / sleep / RHR score with its dominant contributor) and `watch_core::goals` are ported and wired as `Readiness` + `Goals` glance pages, and `fitness::recovery_advice` returns a recovery enum. Like every history-derived surface the score itself is **phone-pushed** through a plausibility-guarded setter and reads an honest `NOT SYNCED` until it arrives — the watch holds no multi-day history, and the sleep / RHR inputs need daily-wear sensing tier 1 doesn't do. On-watch synthesis stays **T3.**
- [ ] **Running dynamics** — cadence (have), plus stride length, vertical oscillation, ground-contact time, running power. Some need extra sensor fusion or an accessory. **T3.**
- [ ] **Resting HR / HRV status.** **T2/T3.**
- [ ] **SpO2 / pulse-ox** (altitude acclimatisation — mountain ultras). Needs AFE support; check the HR-sensor choice in [`vision.md`](vision.md) req #8. **T3.**
- [ ] **Sleep / stress / "body-battery"-style energy** — explicitly low-priority; these are daily-wear metrics, not run metrics. **T3 or deferred.**

### Safety & live tracking

- [ ] **Live spectator tracking** — watch → phone → the existing live pipeline. Already specced as a firmware stretch in [`firmware.md`](firmware.md). `(reuses live_freshness)`. **The watch half of the transport exists**: `watch_core::link::status_frame` notifies one status frame per second over BLE (the same bytes the UART sim bridge emits), and `live_freshness` is ported. What's missing is the phone forwarding it into the live pipeline instead of into the dev Sim Watch screen, plus the reconnect / gap semantics a spectator sees. **T2.**
- [ ] **Cutoff / barrier ETA alerts** — "you're 8 min ahead of the next cutoff." `(port: live_cutoff_eta, roadbook)` — a genuine ultra differentiator, not just parity. **Implemented** (2026-07-10): `watch_core::cutoff_eta` is a parity port of web `runs/live_cutoff_eta.ts` `nextCutoffEta` (the `roadbook.ts` `CUTOFF_TIGHT_S` = 30 min span, the nearest-cutoff-ahead selection, the flat-pace projection), mirrored test-for-test. It rides the breadcrumb-course work this batch's sibling built: the `nav` task's along-course projection is fed into the (course-agnostic) recorder via `set_route_position`, and the recorder folds in the whole-run pace to project on / tight / behind at the next cutoff. The honesty rule is the port's: a stale route position (lost signal, aged past a few fix intervals) or an unknown pace **withholds** the projected time (`Unknown`) rather than fabricate an arrival off an old fix — the checkpoint distance is still shown. A tenth CutoffEta glance page (after RacePredictor) shows the margin as the hero (`+`/`-` split), the verdict, the distance to the cutoff, and the projected arrival clock, with honest `NO CUTOFFS` / `NO CUTOFF AHEAD` states. Cutoff legs arrive with the phone-pushed roadbook (the `CRS1` course push + `Recorder::set_roadbook` both landed); an unpushed watch honestly reads `NO CUTOFFS`, and the sim arms a canned schedule behind `sim-course`. See [decisions § 215](../architecture/decisions.md#215-tier-1-cut-off-eta-feeds-the-course-agnostic-recorder-a-route-position-the-race-predictor-projects-the-current-run-as-a-single-effort). **Caught up to web issue #607 on 2026-07-26**: the page now also carries `required_pace_s_per_km` — the flat pace that still makes the limit, computed **even when the fix is stale** because unlike the ETA it does not depend on recent pace — plus an explicit `limit_passed`, because the pace is absent for two unrelated reasons (limit passed, or under 50 m out) and a "you cannot make it" surface must never fire from the second. Host-tested + build-verified; Renode sim + bench verification pending. **T1** (landed at T1 with the course work — pure projection on top of the along-course distance).
- [ ] **Incident detection + emergency-contact alert** (fall / stop detection → notify). Needs an accelerometer + the phone bridge. **T3.**
- [ ] **Satellite SOS.** Garmin's inReach integration is the backcountry safety killer feature — **and a COROS gap** ([`competitive_landscape.md`](competitive_landscape.md)) — so it is parity-with-Garmin *and* a wedge against COROS. Needs satellite hardware + service → real BOM + partnership cost. **T3+ / stretch.**
- [ ] **ICE / medical-ID idle screen** — emergency contact, blood type, allergies, readable from the idle face by a medic checking a collapsed runner's wrist (ultras print this on bib backs; the wrist is where responders look first). **Implemented** (2026-07-29, [decisions § 358](../architecture/decisions.md)): `watch_core::ice` carries five phone-authored lines over `SET1` v6 — which spends `flags2`'s LAST free bit, so the next settings field needs a third presence byte and a version of its own — mirrored into an `ICE1` flash record because a medic reads the wrist of a watch that may have power-cycled. Every gate fails the card **whole** rather than degrading a field: a clipped allergy line reads as complete and a clipped number dials someone else, so an over-long field, an unrenderable byte, or a byte past a field's NUL terminator refuses the card, making ICE the one settings field whose own content can reject the frame. `IceCard` hand-writes its `defmt` impl to print presence only, so a name / blood type / medical history / next-of-kin number never enters a log that ends up on a cable or in a bug report. The surface is a third idle face (BTN4's walk gained a one-way third stop) plus a named `MEDICAL ID` menu row for discoverability. **Known tier-1 limit, not an oversight:** the face is idle-only, so a responder reaching a still-recording watch must stop and dismiss the run first — reaching it from a run view needs a gesture § 350 has no spare of. Host-tested + build-verified. **T1** for the card; **T2** for run-view reachability.

### Sensors & connectivity

- [ ] **BLE sensor pairing** — external HR strap, foot pod. **Not built.** The watch is a GATT *server* today (the phone is the central); pairing a strap makes it a *central* too, and the tier-1 parts list carries no strap to bench against. Retagged **T2** — the T1 half of the old tag was never real.
- [ ] **ANT+ sensor pairing** — gated on the ANT+ adoption question ([`firmware.md`](firmware.md) #2; vendor layers in [§ 88](../architecture/decisions.md#88-vendor-engagement-is-tiered-across-project-maturity)). **T2.**
- [ ] **HR broadcast** — rebroadcast wrist HR to another device / the phone. **T2.**
- [ ] **Selectable GNSS / battery modes** — single-band vs dual-band vs max-accuracy, each with a battery estimate. The power-manager surface every ultra watch ships. Firmware power management. **The tier-1 software half is implemented** (2026-07-10): `watch_core::gnss_mode` defines three modes — Performance (every ~1 s fix), Balanced (one per 15 s), Expedition (one per 60 s, the Garmin UltraTrac / COROS UltraMax class) — each with a projected-battery-hours figure (~110/~180/~220 h, derived from the `vision.md` tier-2 target + `performance_path.md`'s GNSS duty-cycling lever; projections, not measurements — the DK can't measure power). BTN3 cycles the mode on the idle face (`MODE PERF ~110H` row; mid-run BTN3 keeps cycling pages, so a run's mode is frozen for its duration), the gps task generalises its idle fix de-rate into the selected recording cadence, the recorder's jump gate scales with the interval (`MAX_SPEED_MPS * dt` past 1 s — the fixed 100 m ceiling would reject every legitimate 60 s segment; the 1 Hz filter is unchanged), and the face's staleness budget stretches to the mode's cadence so Expedition's 60 s gaps read as the chosen rhythm, not signal loss; run-view GPS rows carry the mode tag. Host-tested + sim-verified (idle BTN3 cycles the MODE row on the emulated panel; forwarded-fix cadence measured ~1 s / 15 s / 60 s per mode in the defmt stream), and the selected mode **persists** across a power cycle in a CRC-checked `CFG1` flash record. **Receiver power-down landed 2026-07-19** — the deeper half: `watch_core::gnss_power` schedules **UBX-RXM-PMREQ** (u-blox backup mode, bounded duration as the self-wake backstop) after each published fix while Recording in Balanced / Expedition, waking the receiver with the 0xFF RX-activity byte a 5 s reacquire margin ahead of the next owed fix; the schedule is publish-relative, a failed PMREQ write leaves the receiver on (L4), and a receiver that ignores PMREQ publishes an identical sequence. Sim-verified in Balanced. What stays hardware: confirming the receiver *actually* enters backup mode and wakes (issue #597), measuring the saving with a PPK2, and single-vs-dual-band selection. Stays unticked until bench-verified. **T1 (mode surface + cadence + power-down) / T2 (band selection).**
- [ ] **GNSS fix-quality tuning** — the deepest software gap in the program, and the one that shows up on a wrist as "my track drifted in the trees." The tier-1 filter is a three-rule acceptance gate (min-move / max-jump / max-speed); Garmin's is twenty years of multipath rejection, foliage-attenuated recovery, and false-fix detection tuned against the world's largest GPS corpus ([`competitive_landscape.md`](competitive_landscape.md)). We close it the way our scale allows: record raw NMEA on every bench and wear run alongside a reference watch, replay the corpus in CI (the sim's fixture rail already does exactly this shape), and tune against measured divergence. A continuous program, not a sized item — see the field-validation corpus row under Platform & lifecycle. **T2/T3, continuous.**
- [ ] **Optical-HR algorithm quality** — the tier-1 peak detector is hardened (AGC, ambient subtraction, motion-artifact classes, duty-cycling) but it is not the licensed Maxim algorithm both incumbents *start* from, let alone their tuned versions; wrist HR on a high-cadence technical descent is where the gap will show. The ADI licensing conversation is already a Layer-2 vendor ask ([§ 88](../architecture/decisions.md#88-vendor-engagement-is-tiered-across-project-maturity)); license first, then tune against the same recorded-corpus rail as GNSS. **T2/T3.**
- [ ] **Haptic + audible alert delivery** — every alert in the firmware is display-only today, and a fried runner at hour 60 in a headlamp beam misses screen banners. The BOM gap and the LRA-vs-ERM choice are owned by [`tier2_scope.md`](tier2_scope.md) (P2 + T2-OQ2); this row names the user-visible parity gap: competitors vibrate and beep, we do not, and the metronome, incident detection, workout step cues, and the ultra-critical drink/eat reminders all wait on the channel. **T2.**
- [ ] **Phone smart-notifications** — read-only notification mirroring. Low priority per the "tool for the run" framing. **T3.**

### Platform & lifecycle

- [ ] **OTA firmware updates** — already an architectural obligation ([§ 84](../architecture/decisions.md#84-tier-1-firmware-ships-no-ota-tier-2-obligated-to-a-production-grade-dual-bank-bootloader-mcuboot-default), tier-2 dual-bank bootloader). **T2.**
- [ ] **Companion-app sync** — BLE GATT run / course sync, specced in [`firmware.md`](firmware.md). Both halves are built ([§ 211](../architecture/decisions.md#211-owner-override-build-the-full-watchphonesupabase-run-sync-vertical-now-despite-the-tier-2-gate)) and the surface has grown in both directions: watch→phone `run_manifest`/`run_chunk` over the flash run store (v3, whole-blob CRC including the footer totals — [§ 321](../architecture/decisions.md)) with the phone's pull→verify→`api.saveRun` client pinned to the same golden vector, and phone→watch the `SET1` settings frame (v3, CRC32 trailer — [§ 319](../architecture/decisions.md); queued depth-4 so partial pushes can't coalesce — [§§ 329–330](../architecture/decisions.md)) plus the `CRS1` course push. All characteristics require an encrypted link with one persisted bond (#598). **Build-verified only on the radio side**; bench verification pending parts. **T1.**
- [ ] **Watch-face / data-screen customisation** — [`firmware.md`](firmware.md) #4; Garmin's Connect IQ face marketplace is part of their moat. Design the hook now, ship later. **T3.**
- [ ] **Field-validation corpus** — the meta-gap behind every row above: competitor firmware has millions of field hours, ours has zero, and no amount of sim coverage substitutes. Once tier 1 is bench-verified, every real run wearing the prototype records its raw sensor streams (NMEA, PPG, baro) as replayable fixtures; the corpus becomes the CI regression rail the GNSS and optical-HR tuning rows tune against, and the sample from which measured battery curves replace the derived ~110/180/220 h projections in [`quality_standards.md`](quality_standards.md)'s register. Unsized by design — a practice, not an item. **T2, continuous.**

## Differentiation backlog — where we can beat them

The parity backlog above is the floor — what we match so a switcher loses nothing. This section is the ceiling: the wedges where we can credibly be *better* than Garmin / COROS, not merely equal. The strategic case for most lives in [`competitive_landscape.md § Where you can credibly win`](competitive_landscape.md#where-you-can-credibly-win); this section turns the watch-relevant ones into trackable work, adds wedges that analysis missed, and applies the same ticking rule as the parity backlog — a box ticks when the wedge is real on a wrist (bench-verified and shipped), not when the code exists.

### Built at tier 1 — sharpen and own

- [ ] **The race-logistics suite.** Roadbook checkpoint schedule + fuel plan + cutoff ETA with the required-pace / `limit_passed` honesty split + grade-aware terrain splits on the pacer — all built and wired at tier 1. No incumbent ships aid-station-aware fuelling, cutoff verdicts, and crew logistics as one integrated surface: Garmin has PacePro and course ETAs, COROS has pace alerts, neither ties the wrist to the crew's view of the race. The remaining work is the seam: the phone already computes `checkpoint_projection` for the race-director / spectator surfaces, so the watch's roadbook and the crew's projection should visibly agree — one race, one schedule, three screens. **T2 (seam); the core is T1-built.**
- [ ] **Honest-data discipline as a stated product principle.** The firmware already refuses to fabricate: a stale fix withholds the cutoff ETA, a stationary runner's heading goes to `--`, unsynced pages say `NOT SYNCED`, battery projections are labelled derived ([`quality_standards.md`](quality_standards.md)). The incumbents smooth over the same states — a confident nav arrow mid-drift, best-case battery marketing. Elevate the discipline from internal convention to positioning ("the watch never lies to you") and hold every future surface to it. **Costs nothing now; state it in [`vision.md`](vision.md) when tier 2 opens.**

### New wedges — nobody ships these

- [ ] **Sleep-station mode.** The 200-mile racer's real question at 3 a.m. is "how long can I sleep and still make the next cutoff?" Both halves were already on the wrist — the roadbook's cutoff legs and `cutoff_eta`'s live margin — so the budget is *computed from the race*, not typed in. Garmin / COROS offer a generic alarm and nothing race-aware.
  **Built 2026-07-30 ([§ 373](../architecture/decisions.md), host-tested): `watch_core::sleep_station` + the `SLP` glance page.** The budget is `cutoff_eta`'s margin less a reserve of `max(30 min, 25 % of the leg ahead)`, projected off the *slower* of the run's moving pace and its race-including-stops pace, floored to whole minutes. It needs no nap timer and no new button edge: the race clock runs through a pause, so recomputing each tick makes the number fall 1:1 while the runner sleeps — the "elapsed clock that honestly keeps running" is the race clock itself. Four honest states (`Budget` / `NoBudget` / `NoCutoff` / `Unknown`); a stale fix withholds the number rather than guessing at it, and a measured `0` stays visibly distinct from a refused `--`.
  **Still owed: the wake.** There is no wake alarm and one was deliberately *not* approximated — the tier-1 BOM has no motor and no buzzer, so any alert would fire silently onto a screen a sleeping runner cannot see. The page states `WATCH CANNOT WAKE YOU` unconditionally; the tier-1 wake mechanism is a crew member reading the wrist. Also owed: the 25 % reserve fraction is a judgement call, not a measurement (registered in [`quality_standards.md`](quality_standards.md)), and while the `pages` walk now traverses `SLP` (so the page is reachable in a real cycle, and the rail has the § 368 observable a future assertion needs), **no scenario asserts the budget itself**. The box stays unticked until a haptic channel makes the mode real on a wrist. **T2 for the wake; the budget is T1-built.**
- [ ] **Backyard-ultra mode.** The last-person-standing format (the fastest-growing ultra format) maps onto nothing the incumbents ship: a bell-anchored 60:00 countdown, loop count as the primary stat, corral-return margin with 3/2/1-minute warnings, per-loop auto-reset riding the existing lap machinery. The app side already models the format (`is_dnf`, the backyard personas); the watch half is a page plus an alert schedule on engines that exist. **T2.**
- [ ] **Measured, mode-for-mode battery claims.** The whole segment markets best-case single-band numbers that drop 40–60 % in the configuration runners actually use ([`competitive_landscape.md`](competitive_landscape.md)). Post-bench, the PPK2 rigs plus the field-validation corpus give us *measured* per-mode drain curves — publish those as the marketing numbers and surface the same curves on-device as the battery time-remaining estimate. A trust wedge no incumbent will follow, because their headline numbers would shrink. **T2, after bench verification.**

### Committed elsewhere — tracked here as wedges

- [ ] **On-watch map UX.** Both incumbents are weak here (Garmin's renderer lags, COROS added vector maps late), and it is the one surface where a modern renderer beats a 20-year codebase. This is exactly the [§ 85](../architecture/decisions.md#85-map-renderer-full-pmtiles-vector-rendering-on-the-mcu--16-gb-external-nand-flash) PMTiles bet — the XL item in [`tier2_scope.md`](tier2_scope.md); the wedge framing is why it earns the XL. **T2/T3.**
- [ ] **Monthly firmware cadence.** Ship monthly vs Garmin's roughly-annual feature drops — trivial to win *once OTA exists* ([§ 84](../architecture/decisions.md#84-tier-1-firmware-ships-no-ota-tier-2-obligated-to-a-production-grade-dual-bank-bootloader-mcuboot-default)); until then the claimed wedge is unshippable, which is a reason to sequence OTA early, not late. Pair each release with a changelog surfaced in the companion app. **T2 (process, post-OTA).**
- [ ] **The AI-coach seam.** The LLM coach is genuinely uncontested space — both incumbents are rule-based — and it lives on phone/web per [§ 24](../architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive); the watch's share is the seam. The `WKT1` workout push already carries the coach's plan to the wrist: add the coach's one-line *why* ("threshold today because Saturday is long") to the push, and return the step-verdict adherence trail as the coach's next input. Small firmware cost, and unmatchable without building the coach first. **T2.**
- [ ] **Companion-app quality.** Already won — the existing web / mobile app beats Garmin Connect and the COROS app today ([`competitive_landscape.md`](competitive_landscape.md) ranks it #2), and the watch inherits it whole through the sync protocol. The work is keeping the watch surfaces inside the app at the app's quality bar: the dev-gated Sim Watch screen graduating into a real device-management surface (pairing, sync status, course / workout push, settings). **T2.**

### Positioning wedges — cheap code, brand-level payoff

- [ ] **Repairability + open formats.** The user-replaceable battery is [`vision.md`](vision.md) req #10 (hardware, stretch); the software half is nearly free — the wire formats (`run_store` v3, `SET1`, `CRS1`, `WKT1`) are versioned, CRC'd, and documented in-repo, so committing to public format docs + local export at tier 3 costs a doc, not a redesign. Nobody else lets the owner read their own watch's flash. **T3 (commitment now, publication at tier 3).**
- [ ] **Privacy-first posture.** Both incumbents are sensor-data-to-cloud businesses; our sync is phone-mediated and the app already takes minimisation / export / deletion seriously. The watch inherits none of it automatically ([§ Smaller considerations](#smaller-considerations)) — pulling those patterns in at tier 2 *is* the wedge, stated plainly: works fully offline, syncs only what you chose, exports everything. **T2.**
- [ ] **On-watch i18n.** Garmin is English-first and lukewarm beyond the top locales; the app already carries six web locales and the mobile ARB rail. The 1-bit panel's generated fonts are the real constraint (glyph budget — Latin-extended first; CJK is a separate project). Pick the locales the app already serves and be the best ultra watch in each. **T3.**
- [ ] **Physiology beyond the young-male default.** Tanaka HR-max, age-grading, cycle-aware training load — places the incumbents' defaults quietly fail large parts of the market. The models stay app-side per [§ 24](../architecture/decisions.md#24-web-is-the-canonical-feature-surface-mobile-and-watches-are-platform-additive) (`age_grade` is already ported watch-side); the watch's share is the discipline of never hard-coding a young-male constant anywhere a synced value can arrive — max HR already works this way. **T2 discipline; features land app-first.**
- [ ] **Niche-event integration.** parkrun, UTMB-style barrier races, backyard ultras — the incumbents treat all of these as generic activities. We already model cutoff barriers (roadbook), the backyard format (above), and parkrun (app-side); making the watch *know the race format* is a compounding wedge each event type deepens. **T2/T3, per format.**

- **Local-store overflow behaviour.** Current tier-1 answer (per [`apps/custom_watch/README.md`](../../apps/custom_watch/README.md) step 7): the run store is **4 × 4 KiB internal-flash slots** with a **253-record-per-run cap**. Since run-store v2 a full slot **decimates instead of truncating** (stored points thin by 2 and the incoming stream thins with them, laps never dropped), so the whole run survives at coarser resolution with a `! TRACK 1/k RES` wrist notice; eviction sacrifices a fully-synced run before an unsynced one, and an in-progress run is checkpointed across ping-ponged slots. That is still a bench-prototype foundation, not shipping capacity — an ultra's ~360k points and days off-grid need the tier-2 external NAND, and the retention policy for *that* store is an open architectural choice sized in [`tier2_scope.md`](tier2_scope.md).
- **Tier-1 development log + showcase plan.** Tier 1's stated deliverable is "knowledge + a credible technical story for ODM conversations." The log exists: [`tier1_log.md`](tier1_log.md), one dated entry per milestone (started 2026-07-09, reconstructed back to the 2026-05-28 scaffold). Photo/video slots start when parts arrive.
- **Watch face customization architecture.** Per [`firmware.md`](firmware.md) open Q#4 — almost certainly out of v1.0 scope but worth designing the UI layer with the customization hook in mind. Decide which Embassy UI primitives stay decoupled.
- **No external issue tracker.** All planning lives in markdown. Fine while it's one person; gets messy fast if anyone else joins. GitHub Projects board is the cheapest pivot.
