- [ ] **Route builder needs a reachable OSRM — design decision first, not just a deploy.** The shipped internal-track build (`mobile_android@1.0.5`, 2026-07-14) has `OSRM_URL` unset, so the route Build button throws on a phone. **Do NOT "just" expose `osrm.threkir.com`** — the previous wording of this item said that, and it contradicts a documented decision: `osrm-routed` is the upstream `osrm/osrm-backend` image with **no auth of any kind**, which is exactly why `apps/job_worker/osrm/fly.toml` attaches no public IP and `apps/job_worker/deployment.md` § DR states "OSRM has no auth; that's why it can never have a public route" (it declines to expose even `/health` directly). A naked public OSRM is an open, abusable `performance-2x`/8 GB compute service.

  The real blocker is **cross-cloud reachability + no auth**, and it has three parts:
  1. **OSRM is on Fly 6PN; its consumer is an AWS Lambda.** The `osrm-proxy` Lambda (`apps/web/lambda/osrm-proxy/`, issue #198 / decisions §242) is built, Terraformed (`infra/envs/{prod,preview}`) and bundled by `release-web.yml` — but it cannot reach `osrm.internal`. `var.osrm_url` defaults to `""`, and an empty value leaves the proxy at 501 with the **web** route builder degrading to straight-line segments. Confirm whether prod actually has it set before assuming web routing works.
  2. **Auth has to be added in front of OSRM, not to it.** The house precedent is `graph_cycle`: `[http_service]` + `force_https` + a required `GRAPH_CYCLE_API_KEY` header — but that works because `graph_cycle` is *our* Go code (`apps/graph_cycle/main.go`). OSRM is a third-party binary, so the equivalent needs a small auth reverse-proxy in front of it on Fly (or moving OSRM into AWS beside the Lambda, removing the cross-cloud hop entirely).
  3. **Mobile must go through the Lambda proxy, not straight at OSRM.** `routing.dart` currently builds `$OSRM_URL/nearest/v1/...` and `$OSRM_URL/route/v1/...` and calls them directly from the device — the precise exposure web *removed* in §242, where a user's pin coordinates (routinely their home) left the client with no server boundary. Pointing `MOBILE_OSRM_URL` at a public OSRM would re-open it on mobile. The proxy deliberately mirrors OSRM's own GET path shape, so mobile's URL building needs **no change** — set `MOBILE_OSRM_URL=https://threkir.com/api/routes/osrm` and send the Supabase JWT in the `x-supabase-authorization` header on the two fetch helpers — the standard `Authorization` header is owned by CloudFront's OAC sigv4 signing and never reaches the Lambda (`apps/web/lambda/osrm-proxy/src/index.ts`); the proxy 401s without a signed-in user.

  Until (1) and (2) are decided and provisioned, mobile route-building cannot ship past Internal, and the mobile code change in (3) is not worth landing (it would only move the failure). Operator-gated: needs `flyctl` + Fly/AWS credentials.

- [x] **A per-function edge worker could not boot without reaching `registry.npmjs.org`, which is what "the edge runtime never boots" has been all along.** Diagnosed and fixed 2026-08-19 ([decisions § 699](../architecture/decisions.md)) — the diagnosis came from the forensics the entry above added, on their first real firing (PR #793's own `Edge Function tests (Deno)` run). Cause: esm.sh's default (denonext) build of supabase-js imports `node:buffer` / `node:process`, and the runtime resolves `node:` builtin **types** from npm before a worker may boot. Reproduced deterministically outside CI — `edge-runtime start --main-service` with `--add-host registry.npmjs.org:127.0.0.1` reproduces the CI error byte for byte — and that harness is what graded the candidates:

  | candidate | offline worker boot |
  |---|---|
  | esm.sh default (denonext), i.e. before this change | **fails** |
  | `?no-dts` | **fails** — it is the `node:` specifier, not the declarations |
  | `?target=deno` | **boots** (no `node:` specifiers at all) |
  | `?target=deno` on stripe | **fails** — the stripe SDK imports `node:http` itself |
  | edge-runtime v1.73.15 / v1.74.3 (latest), default build | **fails** — a CLI bump does not fix it |
  | import map redirecting `npm:@types/node` to a local stub | not intercepted |

  Fixed where it is load-bearing rather than everywhere: `clip-public-track/index.ts` (the function every stack-using job's setup probes for its 405) and `_shared/rate_limit.ts`'s **type-only** import, which measurably re-arms the failure on its own even though it is erased at emit. Residual exposure, stated rather than hidden: the four stripe functions (`donations-checkout`, `events-cancel`, `events-checkout`, `events-connect-onboard`) and the other supabase-js functions still resolve `@types/node` at boot, so an npm outage can still fail a test that calls one — but it can no longer kill a job in setup before any test runs. Closing that residue needs a vendored/pre-seeded runtime module cache, not an import parameter. Guarded by `_shared/offline_worker_boot_guard.test.ts`, which fails the PR if either probe-path import loses `?target=deno` (mutation-checked).

(The claim that `dependabot-auto-merge.yml` "runs with a read-only token today" was wrong in both directions: it already declares `contents: write`, and that is not what blocks the automation.) **What is actually open is § 711's closing question** — that section exists only because the lockfile sits at the root of an npm workspace, so the thing worth establishing is whether deno records it at all when the lock does not sit there. A lockfile with no generated half needs no guard, no weekly chore and no bot. The experiment is cheap: move a copy of the lock under `apps/backend/`, run the same `deno check --no-remote` the sync script runs, and read what comes back.

## Surfaced while settling the iOS backup/restore contradiction (2026-08-24)

- [x] **All nine `Share.shareXFiles` call sites omit `sharePositionOrigin`, and the iOS target includes iPad.** Closed 2026-08-24 ([decisions § 714](../architecture/decisions.md)) — see the section below, which carries the measured facts. - [ ] **`parity.md` contradicts itself about what an iOS cell means.** The top banner says "a `Partial` / `✓` on iOS or Apple Watch should be read as 'wired but unverified on Mac hardware'", while the column key says "Cells stay `✗` until each row is verified on a Mac build / simulator / device" and the intentional-asymmetries list says "iOS cells stay `✗` / `Partial` *by design* until each row is simulator/device-verified". ## Surfaced by the iPad share-anchor fix (2026-08-24)

- [x] **Every mobile share reached `share_plus` without a `sharePositionOrigin`, and the app ships to iPad.** Closed 2026-08-24 ([decisions § 714](../architecture/decisions.md)). All 21 call sites — nine `Share.shareXFiles`, ten `Share.share`, two `SharePlus.instance.share` — omitted the anchor while `apps/mobile_ios/ios/Runner.xcodeproj` sets `TARGETED_DEVICE_FAMILY = "1,2"` in all three configurations. On the pinned `share_plus` 12.0.2 the iOS plugin does not crash: it detects the empty rect and returns a `FlutterError` whose message is `sharePositionOrigin: argument must be set`, so the share throws a `PlatformException` into the call site's `catch` and **no sheet opens**. All three native rails (`shareUri`, `shareFiles`, `shareText`) pass through the same `atSource:` check, so the text shares were as broken as the file shares. Replaced by one `lib/share_sheet.dart` whose `shareFilesFrom` / `shareTextFrom` take the anchoring `BuildContext` as a required positional parameter — there is no `Rect`-taking overload and no un-anchored path — plus the migration off the deprecated `Share` statics onto `SharePlus.instance.share(ShareParams(...))`, four source guards in `architecture_guards_test.dart`, 6 derivation tests, and the byte-identical iOS mirror.
- [ ] **Device gate: verify the iPad share sheet on real hardware.** Mac- and iPad-only, and nothing above was observed on a device — the fix was derived from the plugin's own `FPPSharePlusPlugin.m`, the Xcode target's device family and the workspace lockfile pin, then host-tested. Owed: on an iPad (and under **Split View / Stage Manager** specifically), confirm each of the four share shapes actually presents — a file share from a modal card sheet (run / route / period / certificate PNG), a file share from a full screen (CSV export, account backup, GPX/KML route export), a text share after a dialog has popped (route detail "share link"), and a text share from a plain button (live link, coach invite, recap). Nothing ships disabled on this; the current behaviour on iPad is strictly worse than the fixed one.
