- [ ] **Route builder needs a reachable OSRM — design decision first, not just a deploy.** The shipped internal-track build (`mobile_android@1.0.5`, 2026-07-14) has `OSRM_URL` unset, so the route Build button throws on a phone. **Do NOT "just" expose `osrm.threkir.com`** — the previous wording of this item said that, and it contradicts a documented decision: `osrm-routed` is the upstream `osrm/osrm-backend` image with **no auth of any kind**, which is exactly why `apps/job_worker/osrm/fly.toml` attaches no public IP and `apps/job_worker/deployment.md` § DR states "OSRM has no auth; that's why it can never have a public route" (it declines to expose even `/health` directly). A naked public OSRM is an open, abusable `performance-2x`/8 GB compute service.

  The real blocker is **cross-cloud reachability + no auth**, and it has three parts:
  1. **OSRM is on Fly 6PN; its consumer is an AWS Lambda.** The `osrm-proxy` Lambda (`apps/web/lambda/osrm-proxy/`, issue #198 / decisions §242) is built, Terraformed (`infra/envs/{prod,preview}`) and bundled by `release-web.yml` — but it cannot reach `osrm.internal`. `var.osrm_url` defaults to `""`, and an empty value leaves the proxy at 501 with the **web** route builder degrading to straight-line segments. Confirm whether prod actually has it set before assuming web routing works.
  2. **Auth has to be added in front of OSRM, not to it.** The house precedent is `graph_cycle`: `[http_service]` + `force_https` + a required `GRAPH_CYCLE_API_KEY` header — but that works because `graph_cycle` is *our* Go code (`apps/graph_cycle/main.go`). OSRM is a third-party binary, so the equivalent needs a small auth reverse-proxy in front of it on Fly (or moving OSRM into AWS beside the Lambda, removing the cross-cloud hop entirely).
  3. **Mobile must go through the Lambda proxy, not straight at OSRM.** `routing.dart` currently builds `$OSRM_URL/nearest/v1/...` and `$OSRM_URL/route/v1/...` and calls them directly from the device — the precise exposure web *removed* in §242, where a user's pin coordinates (routinely their home) left the client with no server boundary. Pointing `MOBILE_OSRM_URL` at a public OSRM would re-open it on mobile. The proxy deliberately mirrors OSRM's own GET path shape, so mobile's URL building needs **no change** — set `MOBILE_OSRM_URL=https://threkir.com/api/routes/osrm` and send the Supabase JWT in the `x-supabase-authorization` header on the two fetch helpers — the standard `Authorization` header is owned by CloudFront's OAC sigv4 signing and never reaches the Lambda (`apps/web/lambda/osrm-proxy/src/index.ts`); the proxy 401s without a signed-in user.

  Until (1) and (2) are decided and provisioned, mobile route-building cannot ship past Internal, and the mobile code change in (3) is not worth landing (it would only move the failure). Operator-gated: needs `flyctl` + Fly/AWS credentials.

- [x] **A per-function edge worker could not boot without reaching `registry.npmjs.org`, which is what "the edge runtime never boots" has been all along.** Diagnosed and fixed 2026-08-19 ([decisions § 699](../architecture/decisions.md)) — the diagnosis came from the forensics the entry above added, on their first real firing (PR #793's own `Edge Function tests (Deno)` run). The runtime itself starts normally; the **worker** dies: `failed to create the graph: Failed loading https://registry.npmjs.org/@types%2fnode for package "@types/node" … Network is unreachable (os error 101)`. Cause: esm.sh's default (denonext) build of supabase-js imports `node:buffer` / `node:process`, and the runtime resolves `node:` builtin **types** from npm before a worker may boot. Every probe then hangs to curl's `--max-time` and reports `000`, which is the measured signature above. Reproduced deterministically outside CI — `edge-runtime start --main-service` with `--add-host registry.npmjs.org:127.0.0.1` reproduces the CI error byte for byte — and that harness is what graded the candidates:

  | candidate | offline worker boot |
  |---|---|
  | esm.sh default (denonext), i.e. before this change | **fails** |
  | `?no-dts` | **fails** — it is the `node:` specifier, not the declarations |
  | `?target=deno` | **boots** (no `node:` specifiers at all) |
  | `?target=deno` on stripe | **fails** — the stripe SDK imports `node:http` itself |
  | edge-runtime v1.73.15 / v1.74.3 (latest), default build | **fails** — a CLI bump does not fix it |
  | import map redirecting `npm:@types/node` to a local stub | not intercepted |

  Fixed where it is load-bearing rather than everywhere: `clip-public-track/index.ts` (the function every stack-using job's setup probes for its 405) and `_shared/rate_limit.ts`'s **type-only** import, which measurably re-arms the failure on its own even though it is erased at emit. Verified by booting the real repo files against a blackholed npm registry and getting the probe's own `Method not allowed`. **Deliberately NOT applied to the other 16 functions**: `?target=deno` swaps the `node:` imports for esm.sh's `deno.land/std@0.177.1` polyfill tree, which grows one function's bundle from **228 KB to 2.4 MB** (measured with `edge-runtime bundle`), so blanket-applying it would pay a 10x cold-boot cost on every function to convert a test-time failure that names itself into a slightly earlier one. Residual exposure, stated rather than hidden: the four stripe functions (`donations-checkout`, `events-cancel`, `events-checkout`, `events-connect-onboard`) and the other supabase-js functions still resolve `@types/node` at boot, so an npm outage can still fail a test that calls one — but it can no longer kill a job in setup before any test runs. Closing that residue needs a vendored/pre-seeded runtime module cache, not an import parameter. Guarded by `_shared/offline_worker_boot_guard.test.ts`, which fails the PR if either probe-path import loses `?target=deno` (mutation-checked).

The `select('*')` source scans police the call-site half of that class; nothing policed the grant half. `column_grant_lockdown_registry_test.sql` now names all 25 withheld columns with a reason each and pins the withheld set — the direction that detects drift, since pinning the *granted* set does not move when a column arrives ungranted. Four probes, each rolled back, trip the intended assertion by name.

- [x] **The write side carries the same shape with the mirror-image drift, and no registry.** Measured 2026-08-27 alongside § 759, deliberately not bundled. Four tables hold column-level INSERT/UPDATE grants for `authenticated`: `achievements` (UPDATE `is_public` only; the other 8 columns are server-awarded), `challenge_participants` (`team_club_id` only — `completed_at` is server-recomputed), `coach_messages` (`archived_at` + `reaction`, [decisions § 29](../architecture/decisions.md)), `event_attendees` (`attendance` + `order_id` blocked on **both** verbs since `20270520_001`). Its drift runs the other way — a column added to one of these is silently **unwritable**, `42501` on a PostgREST PATCH, with no integration suite to catch it the way `clubs.is_verified` was caught — and **three of the four still hold a table-level INSERT beside a column-scoped UPDATE**, which is the exact asymmetry [§ 584](../architecture/decisions.md) records for `event_attendees` before `20270520_001` closed it (a table grant implies every column, so the UPDATE lockdown was reachable through INSERT). Each of the four has an individual pgtap pin; none has the class-level one. Extending `column_grant_lockdown_registry_test.sql` to writes is the durable fix, but it needs the same per-column provenance pass the SELECT side got — per role and per verb, where the write side has more legitimate variety — so it is a slice, not a line. **CLOSED 2026-08-27** ([decisions § 763](../architecture/decisions.md)) — both counts hold and the headline defect has never fired, while the aside at the end of the sentence was live on `main`. Only **one** of the four column-scopes INSERT (`event_attendees`, `20270520_001`), so "silently unwritable" is unconditionally true only there; on the other three a new column would have been insertable-and-not-updatable, write-once by accident — and no column has been added to any of the four since its lockdown landed, measured across all 434 migrations. `anon` holds **no** column-level write grant at all, so the write side was never the read side's both-roles-identical shape. The § 584 asymmetry is real on three tables and **bites on one**: `achievements` has no permissive INSERT or DELETE policy so both grants are dead (measured — the INSERT raises `42501 new row violates row-level security policy`, the DELETE affects zero rows), `coach_messages`' `WITH CHECK` already confined a client to `role = 'user'` so only a client-chosen `id` and a backdated `created_at` were reachable, but `challenge_participants` was a live forgery path: join and leave are both own-row verbs, so `delete` + re-`insert` with `completed_at = now()` wrote the column the lockdown reserves for `recompute_challenge_completion`, verified under the participant's own JWT. `joined_at` was backdatable the same way. **A fifth defect nobody filed:** swept across every column, table and DML verb, `coach_messages` was the *only* place in the schema where `anon` held a privilege `authenticated` lacks — a table-level UPDATE against `authenticated`'s column-scoped `(archived_at, reaction)`, left by `20260518_001` revoking from `authenticated` only and then version-controlled by `20270408_001` from the drifted prod schema. Inert (the owner policy reads `auth.uid() = user_id`) but that is RLS covering for a grant, which is what § 759 refused on the read side. `20270616_001` column-scopes the two INSERTs to exactly what the clients send, revokes `anon`'s UPDATE, and revokes `achievements`' dead INSERT + DELETE so the class invariant needs no exemption. GRANT/REVOKE take **no lock on the target relation** (measured), so no online-DDL machinery applies. `column_grant_write_lockdown_registry_test.sql` is the class guard — six assertions, seven probes tripping all six by name; it caught two unregistered `coach_messages` INSERT withholdings on its first run, and the first draft of the new `challenge_participants` pin was § 741-vacuous (a non-existent challenge id raised the same `42501` from the `WITH CHECK`) until it was rewritten to perform the exploit's own DELETE first.
